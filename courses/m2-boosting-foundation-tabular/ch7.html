7. LLMs et tables : sérialisation, text-to-SQL

Un LLM ne lit pas une table : il lit du texte. Tout passe par une sérialisation — et ce choix d'ingénierie est aussi déterminant que le prompt lui-même.

Définition 7.1 — Sérialisations usuelles d'une ligne Pour une ligne \((x_1, \dots, x_p)\) de colonnes nommées \(c_1, \dots, c_p\) : CSV aligné sur un en-tête ; JSON clé-valeur ; Markdown ; gabarit textuel (« Le patient a \(x_{age}\) ans, reçoit \(x_{dose}\) mg… ») ; le « schema » (noms de colonnes, types, description) peut précéder la série. Deux propriétés critiques : l'ordre des colonnes influence la prédiction (le modèle est sensible à la position des tokens), et les noms de colonnes activent les connaissances du pré-entraînement (« country », « dosage ») — un prior sémantique qu'aucun GBDT n'a.
Étude 7.2 — TabLLM (Hegselmann et al., 2023) En few-shot (typiquement \(\leq 64\) exemples), un LLM (T0/GPT-3.5, sérialisations textuelles) prédit des tables mieux que les méthodes profondes dédiées et rivalise avec les GBDT ; l'avantage s'inverse dès que les données abondent — le coût token par ligne devient rédhibitoire et le prior sémantique ne compense plus la capacité statistique. Le LLM gagne là où chaque exemple coûte cher (annotation médicale, industrie) ; le GBDT là où les données sont massives.
Définition 7.3 — Text-to-SQL et schema linking Quand la table est une base de données, le LLM devient interface : produire du SQL depuis une question en langue naturelle. Le schema linking désigne l'étape d'alignement question ↔ schéma : entités de la question vers cellules des tables, termes vers colonnes/tables candidates, puis jointures plausibles. Benchmarks : Spider (Yu et al., 2018 ; schémas propres, question académique) puis BIRD (Li et al., 2023 ; 95 grandes bases « sales », valeurs sales, connaissances externes, exigence d'efficacité des requêtes) — sur lequel la chute de performance des modèles entre les deux mondes est précisément mesurée. 
# Trois postures du LLM face a une table
# 1) Predire : ligne serialisee -> etiquette (TabLLM, few-shot)
prompt = f"Colonne 'dosage_mg': {x['dose']}; 'age': {x['age']}; ...\nReponse (0/1) ?"
# 2) Ingenier : proposer features / nettoyer / documenter les colonnes
#    (le LLM ecrit le code de feature engineering, le GBDT predit)
# 3) Interroger : question naturelle -> SQL (schema linking + BIRD)
question = "top 5 clients par marge en 2025, hors remboursements"
# -> SELECT c.id, SUM(o.marge) FROM ... WHERE ... GROUP BY ... ORDER BY ... LIMIT 5;
Limites structurelles Tokenisation des nombres (les scalaires sont découpés en morceaux — l'arithmétique fine reste fragile) ; fenêtre de contexte (des millions de lignes n'entreront jamais) ; confidentialité (envoyer des lignes clients à une API ; cf. module Explainability, Security and Privacy of LLMs) ; coût et nondéterminisme en production (cf. module ML Ops). D'où la posture dominante : hybride — le LLM prépare, résume, relie, programme ; le modèle tabulaire (GBDT/TabPFN) prédit.
