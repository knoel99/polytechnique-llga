1. Cycle de vie : versionner données, features, modèles

Le cycle de vie ML s'étend bien au-delà de l'entraînement : collecte → labellisation → features → entraînement → évaluation → registre → déploiement → monitoring → (ré)entraînement. Chaque flèche de ce cycle est un artefact qu'il faut identifier de façon immuable, faute de quoi aucune métrique n'est reproductible — ni en debug, ni en audit, ni devant un client.

Définition 1.1 — Artefact et lineage Un artefact est tout objet produit ou consommé par le cycle : jeu de données, schéma de features, poids, tokenizer, template de prompt, index vectoriel, configuration, image conteneur. Le lineage est le graphe des dépendances artefact → artefact. Un entraînement est reproductible lorsque code + données + configuration + environnement sont tous identifiés par des empreintes (hashes) et rejouables.
Proposition 1.2 — La triple empreinte Un run d'entraînement n'est reproductible que si l'on sait rejouer le triplet \((\text{code}, \text{données}, \text{config})\). En pratique : git versionne le code (commit hash), DVC versionne les données et les poids (empreinte du contenu, le fichier vivant hors du dépôt), et params.yaml lie les deux. Toute métrique publiée référence les trois empreintes — sinon elle n'est pas une mesure, c'est une rumeur. 
# Donnees volumineuses versionnees par contenu (DVC) -- seul le pointeur entre dans git
$ dvc add data/faq_2026.parquet          # crée data/faq_2026.parquet.dvc (hash + taille)
$ git add data/faq_2026.parquet.dvc && git commit -m "faq v3 (dedup + PII scrub)"

# Pipeline déclaratif : stages re-joués si et seulement si leurs entrées changent
# dvc.yaml
stages:
  prepare:
    cmd: python src/prepare.py data/raw/ data/train.parquet
    deps: [data/raw/, src/prepare.py]
    outs: [data/train.parquet]
  finetune:
    cmd: python src/train_lora.py --config params.yaml
    deps: [data/train.parquet, src/train_lora.py, params.yaml]
    outs: [artifacts/lora_faq_v3/]
  evaluate:
    cmd: python src/evaluate.py --run artifacts/lora_faq_v3/
    deps: [artifacts/lora_faq_v3/, data/eval_v3.parquet]
    metrics: [artifacts/lora_faq_v3/metrics.json:
              {cache: false}]

$ dvc exp run            # rejoue la chaîne, enregistre l'expérience
$ dvc metrics diff       # compare v2 -> v3

Feature stores et registres

Pour le ML tabulaire, un feature store (p. ex. Feast) sert la même définition de feature en offline (entraînement, batch) et en online (serving, low-latency), éliminant le skew entraînement/inférence — la classe de bug la plus sournoise du ML industriel. Pour les LLMs, l'équivalent fonctionnel est double : la cache de prompts (préfixes partagés ; cf. ch. 4) et la banque d'embeddings du RAG (ch. 6), dont le schéma (type de chunk, modèle d'embedding, version de l'index) doit être géré comme une feature : identifiée, versionnée, rejouable.

Le registre de modèles (MLflow, ou répertoire hf_hub privatisé) enregistre pour chaque version : les empreintes du triplet, les métriques de qualification, la signature (entrées/sorties), et le statut (staging / production / archived). Un déploiement ne référence jamais « le dernier entraînement » mais une version figée du registre.

Spécificité LLM : les prompts et les évals sont des artefacts Dans une application LLM, trois familles d'artefacts s'ajoutent au triplet classique : (i) les templates de prompts (versionnés comme du code, avec tests — ch. 2) ; (ii) les jeux d'évaluation (golden sets question → réponse attendue / documents pertinents) ; (iii) les modèles d'embedding et index du RAG, couplés : changer de modèle d'embedding invalide tout l'index (ch. 6). Oublier de versionner un prompt revient à ne pas versionner les poids.
