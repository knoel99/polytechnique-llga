2. CI/CD pour le ML : tester données et modèles

L'intégration continue d'un système ML teste quatre couches, par ordre de coût croissant : le code, les données, le modèle, l'infrastructure. La règle d'or : faire échouer le pipeline le plus tôt possible, au niveau le moins cher.

2.1. Tests de données

Les données sont une interface comme une autre : on leur écrit des contrats. Un contrat de données vérifie : le schéma (types, colonnes, bornes), les invariants métier (valeurs nulles admises, plages), et des propriétés statistiques (taux de duplication, distribution d'une colonne clé). Outils : Pandera (contrats en Python, exécutés dans le pipeline), Great Expectations (suites de validations déclaratives), serveurs de qualité intégrés aux plateformes.

import pandera as pa
import pandas as pd

schema = pa.DataFrameSchema({
    "question": pa.Column(str, pa.Check.str_length(3, 2000)),
    "answer":   pa.Column(str, pa.Check.str_length(1, 8000), nullable=True),
    "lang":     pa.Column(str, pa.Check.isin(["fr", "en"])),
    "doc_ids":  pa.Column(pa.List(str), pa.Check.list_length(1, 10)),
    "n_tokens": pa.Column(int, pa.Check.ge(0), pa.Check.le(4096)),
})

def validate(df: pd.DataFrame) -> pd.DataFrame:
    return schema.validate(df, lazy=True)   # collecte TOUTES les erreurs

2.2. Tests de modèles — et de prompts

Définition 2.1 — Test de non-régression d'un modèle Soit un jeu de qualification \(D_{\text{qual}}\) fixé et une métrique \(m\) (F1, taux d'exactitude, taux de refus, coût moyen). Le candidat \(f_{\text{new}}\) remplace \(f_{\text{prod}}\) si \(m(f_{\text{new}}) \geq m(f_{\text{prod}}) - \tau\), où \(\tau\) est la marge de tolérance. Le point subtil : \(m\) est mesurée sur un échantillon — décider avec un écart mesuré nécessite de savoir quand il est significatif.
Proposition 2.2 — Seuil de décision par concentration (Hoeffding) Soit \(\ell\) une perte bornée dans \([0,1]\), mesurée sur \(n\) exemples i.i.d. Avec probabilité \(\geq 1-\delta\) (des deux côtés) : $$\bigl|\;\mathbb{E}[\ell] - \widehat{\ell}_n\;\bigr| \;\leq\; \sqrt{\frac{\log(2/\delta)}{2n}}.$$ Pour décider d'un rollback à \(\delta = 0{,}05\) sur \(n = 1000\) exemples, deux modèles dont les pertes diffèrent de moins de \(\sqrt{\log 40 / 2000} \approx 0{,}027\) ne sont pas distinguables : l'écart observé peut être du bruit d'échantillonnage.
La borne de Hoeffding (démontrée au module ML) s'applique aux \(n\) variables i.i.d. \(\ell_i \in [0,1]\) : \(\mathbb{P}\bigl(|\overline{\ell} - \mathbb{E}\ell| \geq t\bigr) \leq 2e^{-2nt^2}\). En égalant le membre droit à \(\delta\) on obtient \(t = \sqrt{\log(2/\delta)/(2n)}\). Pour la comparaison de deux modèles on l'applique à la variable \(\ell_{\text{new}} - \ell_{\text{prod}}\) (bornée dans \([-1,1]\), facteur 2 sur la plage — d'où un facteur 2 sous la racine). Avec \(n=1000\), \(\delta = 0{,}05\) et la version signée : \(t \approx 2{,}8\,‰\). ∎
Conséquence pratique Un « +0,4 % de F1 » mesuré sur 500 exemples ne prouve rien : l'intervalle de confiance à 95 % est de l'ordre de ±4 points pour une métrique à 50 %. Les gateways de CI doivent donc exiger un écart minimal (marge \(\tau\) et significativité), sous peine de « danser sur le bruit » — un rollback par-ci, un rollback par-là, et une dérive lente de la qualité.

Les tests de modèles se déclinent aussi en tranches (slices) : performance par langue, par longueur de contexte, par topic, par catégorie d'utilisateur — un agrégat global peut masquer une chute localisée (thématique de fairness, cf. module Emerging ML ch. 6). Pour un LLM, s'ajoutent des tests de prompts : format de sortie (JSON valide, schéma), garanties de refus (phrases interdites), enrobeurs de déterminisme (température 0, seed) et un juge LLM comme oracle (ch. 5) — le juge lui-même étant versionné et testé sur un golden set.

# .github/workflows/eval-gate.yml (extrait) -- gate CPU d'abord, GPU en dernier
jobs:
  unit:                      # 1. code : tests rapides, pas de modèle
    steps: [run: pytest tests/unit -x -q]
  data:                      # 2. données : contrats pandera sur le delta du jour
    steps: [run: python -m src.validate_delta --date $(date -d yesterday +%F)]
  eval:                      # 3. modèle : golden set + juge + contrats de prompt
    steps:
      - run: python -m src.eval_llm --model staging --golden data/eval_v3.parquet
      - run: python -m src.gate --min-faithfulness 0.85 --max-regression 0.01
  deploy:                    # 4. déploiement progressif (canary 5% -> 50% -> 100%)
    needs: [unit, data, eval]
    steps: [run: ./deploy.sh --canary 5]

2.3. Livraison continue : canary et shadow

Le déploiement d'un composant ML est progressif : shadow (le nouveau modèle reçoit le trafic en double, sa sortie est journalisée mais non servie — zéro risque, coût double), canary (5 % du trafic, rollback automatique si les métriques de garde — latence, taux d'erreur, feedback négatif — se dégradent), puis généralisation. Le rollback doit être un seul bouton : la version précédente (poids + prompt + index) reste déployable en une commande, grâce au registre du ch. 1.
