The founding observation. A model reaching 92% F1 in a notebook does not “work”: it works in an environment.

The founding paper of the field (Sculley et al., NeurIPS 2015) shows that ML technical debt lives not in the model but around it: data pipelines, glue code, dependency chains, configurations, and feedback loops — the model in production influences the data that will be used to retrain it.

The LLM does not abolish this debt; it adds three specificities: the model is non-deterministic, its input space is all of natural language (hence not boundable by a schema), and its unit cost (the token) is billed on every request.

Definition 0.1 — ML Ops The set of software, data, and systems engineering practices applied to the complete lifecycle of a machine learning system: development, testing, integration, deployment, monitoring, retraining. LLM engineering is the special case where the central component is a language model (API or open weights), typically within a RAG, a fine-tuning, or an agent.

1. Lifecycle: versioning data, features, models

A business RAG assistant passes every demo, then fails on 12% of real queries in production; nobody can say which version of the chunking, the prompt or the index produced the demo results. This chapter makes every element of the system identifiable and replayable, so that such failures can be traced and measured.

What breaks Four mistakes recur across the module: prompts that are not versioned, no regression evaluation before a release (ch. 2), serving without token budgets or timeouts (ch. 3), and judging latency by its mean instead of its tail percentiles (ch. 3).

The ML lifecycle extends well beyond training: collection → labeling → features → training → evaluation → registry → deployment → monitoring → (re)training. Every arrow in this cycle is an artifact that must be identified immutably; failing that, no metric is reproducible — neither for debugging, nor for audits, nor in front of a client.

Definition 1.1 — Artifact and lineage An artifact is any object produced or consumed by the cycle: dataset, feature schema, weights, tokenizer, prompt template, vector index, configuration, container image. The lineage is the graph of artifact → artifact dependencies. A training is reproducible when code + data + configuration + environment are all identified by fingerprints (hashes) and replayable.

Proposition 1.2 — The four fingerprints A training run is reproducible only if one can replay the four components of Definition 1.1: code, data, configuration and environment.

In practice: git versions the code (commit hash), DVC versions the data and the weights (content fingerprint, the living file staying out of the repository), params.yaml links the two, and the container image digest (sha256, last table of this chapter) pins the environment: libraries, CUDA, drivers.

Every published metric references the four fingerprints — otherwise it is not a measurement, it is a rumor.

1.1. Feature stores and registries

For tabular ML, a feature store (e.g. Feast) serves the same feature definition offline (training, batch) and online (serving, low-latency), eliminating training/inference skew — the sneakiest class of bug in industrial ML. For LLMs, the functional equivalent is twofold: the prompt cache (shared prefixes; cf. ch. 4) and the embedding bank of the RAG (ch. 6), whose schema (chunk type, embedding model, index version) must be managed like a feature: identified, versioned, replayable.

The model registry (MLflow, or a privatized hf_hub directory) records for each version: the four fingerprints (Proposition 1.2), the qualification metrics, the signature (inputs/outputs), and the status (staging / production / archived). A deployment never references “the latest training” but a frozen version of the registry.

LLM specificity: prompts and evals are artifacts In an LLM application, three families of artifacts add to code, data, configuration and environment: (i) prompt templates (versioned like code, with tests — ch. 2); (ii) evaluation sets (golden sets question → expected answer / relevant documents); (iii) the embedding models and index of the RAG, coupled: changing the embedding model invalidates the whole index (ch. 6). Forgetting to version a prompt is equivalent to not versioning the weights.

2. CI/CD for ML: testing data and models

The continuous integration of an ML system tests four layers, in order of increasing cost: the code, the data, the model, the infrastructure. The golden rule: make the pipeline fail as early as possible, at the cheapest level.

2.1. Data tests

Data is an interface like any other: one writes contracts for it. A data contract checks: the schema (types, columns, bounds), business invariants (allowed nulls, ranges), and statistical properties (duplication rate, distribution of a key column). Tools: Pandera (contracts in Python, executed in the pipeline), Great Expectations (declarative validation suites), quality servers integrated into platforms.

2.2. Model tests — and prompt tests

Definition 2.1 — Model non-regression test Let a fixed qualification set D_{\text{qual}} and a metric m (F1, accuracy rate, refusal rate, mean cost). The candidate f_{\text{new}} replaces f_{\text{prod}} if m(f_{\text{new}}) \geq m(f_{\text{prod}}) - \tau, where \tau is the tolerance margin.

The subtle point: m is measured on a sample — deciding with a measured gap requires knowing when it is significant.

Proposition 2.2 — Decision threshold by concentration (Hoeffding) Let \ell be a loss bounded in [0,1], measured on n i.i.d. examples. With probability \geq 1-\delta (on both sides): \bigl|\;\mathbb{E}[\ell] - \widehat{\ell}_n\;\bigr| \;\leq\; \sqrt{\frac{\log(2/\delta)}{2n}}.

To decide a rollback at \delta = 0.05 on n = 1000 examples, the mean loss of one model is known to within \sqrt{\log 40 / 2000} \approx 0.043 . For the per-example difference of two models, which lies in [-1, 1], the bound doubles to \approx 0.086.

Two models whose mean losses differ by less than that are not distinguishable by this test: the observed gap may be sampling noise.

Hoeffding’s bound uses only the range of the loss; a paired test that uses the observed variance of the differences is usually much tighter.

Proof. The Hoeffding bound (Machine Learning, Theorem 0.3) applies to the n i.i.d. variables \ell_i \in [0,1]: \mathbb{P}\bigl(|\overline{\ell} - \mathbb{E}\ell| \geq t\bigr) \leq 2e^{-2nt^2}. Setting the right-hand side to \delta yields t = \sqrt{\log(2/\delta)/(2n)}.

To compare two models one applies it to the variable \ell_{\text{new}} - \ell_{\text{prod}}, bounded in [-1,1]: for a variable of range r, Hoeffding’s bound reads 2e^{-2nt^2/r^2}, so a range twice as large doubles t.

With n=1000 and \delta = 0.05: t \approx 0.043 for one model, t \approx 0.086 for the difference. ∎

Practical consequence A “+0.4% F1” measured on 500 examples proves nothing: the 95% confidence interval is on the order of ±4 points for a metric at 50%. CI gateways must therefore require a minimal gap (margin \tau and significance), under pain of “dancing on the noise” — a rollback here, a rollback there, and a slow drift of quality.

Hoeffding’s bound is a worst case. The gate actually run in CI pairs the two models item by item, because both models fail on the same hard items and that shared noise cancels in the difference.

Definition 2.3 — Paired non-regression gate Score both models on the same n qualification items and keep the per-item loss differences \delta_i = \ell_i(f_{\text{new}}) - \ell_i(f_{\text{prod}}), \qquad i = 1, \dots, n . With \bar\delta their mean and s_\delta their standard deviation, the candidate passes if the upper end of a one-sided 95 % interval stays below the margin: \bar\delta + 1.645\, \frac{s_\delta}{\sqrt n} \;\le\; \tau . For a metric that is not a per-item mean (F1) or is far from normal (judge win rate, RAGAS score), use instead the 95th percentile of the metric difference recomputed on 10^4 bootstrap resamples of the items.

Worked example — n = 1000 right/wrong items; the candidate loses 40 items that production gets right and wins 30 that production gets wrong.

  • The differences are +1 on 40 items, -1 on 30 and 0 elsewhere, so \bar\delta = 0.010 and s_\delta \approx 0.265.
  • The upper bound is 0.010 + 1.645 \times 0.0084 \approx 0.024; the bootstrap gives the same value.
  • The one-sided Hoeffding bound for a difference would add 0.077 instead of 0.014: pairing is about five times tighter, because the 930 concordant items carry no noise.
  • With \tau = 0.02 the candidate is held back. McNemar’s test on the 70 discordant items gives \chi^2 = 10^2/70 \approx 1.43 (p \approx 0.23): the regression is not proven, but neither is the claim that it stays under 2 points.

These are the paired comparisons of Machine Learning 4.9 and LLMs 9.6, the evaluation kit shared by every Year 2 project.

Model tests also come in slices: performance per language, per context length, per topic, per user category — a global aggregate can mask a localized drop (the subgroup evaluation of Machine Learning 4.8). For an LLM, prompt tests add on: output format (valid JSON, schema), refusal guarantees (forbidden phrases), determinism wrappers (temperature 0, seed) and an LLM judge as oracle (ch. 5) — the judge itself being versioned and tested on a golden set.

2.3. Continuous delivery: canary and shadow

The deployment of an ML component is progressive: shadow (the new model receives duplicated traffic, its output is logged but not served — zero risk, double cost), canary (5% of traffic, automatic rollback if the guard metrics — latency, error rate, negative feedback — degrade), then full rollout. Rollback must be a single button: the previous version (weights + prompt + index) stays deployable in one command, thanks to the registry of ch. 1.

3. LLM serving: continuous batching, P99 latency

A served LLM must answer many users at once, fast enough and at an acceptable cost per token. This chapter explains how a server batches requests, why the memory of the KV cache is the real limit, and how latency is specified and measured.

Reminder — LLMs module ch. 6 (inference)

Autoregressive decoding generates one token per forward pass; attention requires retaining the keys/values of all past tokens (KV cache); quantization reduces the weights and the KV; the per-token complexity grows with the context length. This chapter moves from “how it computes” to “how it holds a load”.

3.1. Batching: from one request to N

A GPU executes a decoding step in a time nearly independent of the number of sequences present in the batch (as long as memory and bandwidth allow): the operations are parallel and the GPU is memory-bound on the weights. Serving B sequences simultaneously therefore divides the cost per token by almost B — this is the economic argument for shared serving.

Naive batching (static batching) waits to have B requests, processes them as a block, and leaves the GPUs idle as soon as a short sequence finishes: yet a 20-token request ends quickly, and the batch becomes sparse.

Definition 3.1 — Continuous batching (Orca, OSDI 2022) Schedule serving at the iteration level rather than the request level: at every decoding step, finished sequences leave the batch and waiting requests enter it. The GPU no longer idles between two requests. Combined with selective batching (batched operations where possible, per-request loops elsewhere), Orca claims up to 36.9× the throughput of prior systems at equal latency.

# Continuous batching loop (simplified) -- the heart of every modern LLM server
running, queue = [], deque()

def step():
    # 1) decoding: one iteration for ALL active sequences (a single GPU call)

3.2. Memory: the KV cache and PagedAttention

Recall 3.2 — KV-cache size (stated in LLMs, Proposition 2.4)

For a transformer with n_{\text{layers}} layers and n_{\text{kv}} key/value heads (GQA) of dimension d_{\text{head}}, in precision b bytes, the cache of a sequence of T tokens occupies: M_{\text{KV}} \;=\; 2 \cdot n_{\text{layers}} \cdot n_{\text{kv}} \cdot d_{\text{head}} \cdot b \cdot T \;\text{bytes}. The count is direct: each layer stores, for each token, one key and one value of n_{\text{kv}} d_{\text{head}} coefficients each, at b bytes per coefficient. Hence the factor 2, and only the K/V heads count, however many query heads there are.

Example (Llama-3-8B: n_{\text{layers}}=32, n_{\text{kv}}=8, d_{\text{head}}=128, fp16 b=2): 2\times32\times8\times128\times2 = 131,072 bytes ≈ 128 KiB per token, i.e. 1 GiB for 8,192 tokens — as much memory as the weights of a small quantized model.

Continuous batching therefore makes memory occupancy oscillate at every iteration (sequences entering/leaving). Allocating the KV as one maximal contiguous block (maximum output length reserved in advance) wastes.

vLLM (SOSP 2023) treats the KV cache like the virtual memory of an OS — pages of 16 tokens, allocated on demand, non-contiguous, shareable between sequences derived from the same prefix (system prompt shared by thousands of requests): waste reduced to ~4% versus more than 60% for static allocation, throughput 2-4× prior systems.

Ops consequence: the real capacity of a server is measured in “available KV tokens”, not in concurrent requests.

3.3. Latency: TTFT, TPOT, P99

Definition 3.3 — LLM serving SLO TTFT (time to first token): request → first token delay — dominated by the prefill (prompt) and the waiting queue. TPOT (time per output token): generation cadence — dominated by decoding and batch contention. P99: 99th percentile of a latency distribution — the relevant contractual commitment; the average masks queues. A typical interactive assistant SLO: TTFT P99 < 1.5 s, TPOT P99 < 80 ms/token.

Theorem 3.4 — Little’s law In a stable system in steady state, with L average clients present, \lambda clients arriving per second on average and W mean sojourn time:

Key result — Little’s law L \;=\; \lambda\, W.

Serving corollary: at an imposed generation cadence (W fixed by the number of tokens and the TPOT), the number of concurrent requests supported is L = \lambda W — the necessary concurrency grows linearly with the targeted throughput.

Proof. Proof by an output argument (direct). Over an interval [0, t], let A(t) be the number of arrivals and D(t) the number of departures. The mean number of clients present is written L_t = \frac{1}{t}\int_0^t N(u)\,du, where N(u) = present at instant u.

Each request contributes to this integral exactly its sojourn time: \int_0^t N(u)\,du = \sum_{i \,\text{departed by} \leq t} W_i + \text{(residuals of requests still present)}.

Dividing by t and letting t\to\infty (stability: A(t)/t \to \lambda, bounded residuals become negligible), one obtains L = \lambda\, W — the argument requires no independence or distribution assumption; it is purely accounting. ∎

Throughput versus latency: the batch trade-off Increasing B (target batch) improves throughput (amortized cost/token) but lengthens the waiting queue — hence the TTFT P99. Modern servers expose this trade-off: max_num_seqs, token budgets per step, and preemption policies (recompute vs swap). Rule of thumb: size the target batch so that KV occupancy stays below ~90%, and let the autoscaler (section 3.4) absorb spikes rather than growing the batch beyond the SLO.

3.4. Autoscaling

The relevant signal for scaling an LLM server is not CPU but: the waiting queue length (requests pending admission), the mean waiting time (TTFT − prefill time) and the KV occupancy rate. Horizontal autoscaling (HPA on a custom Prometheus metric) adds replicas; watch out for warm-up spikes (weight loading: tens of seconds to minutes — pre-pull the images, or pay the P99). For multi-GPU models (tensor parallelism, Deep Learning P2, ch. 2), each replica is a group of GPUs; scaling changes the granularity of parallelism, not just the number of pods.

4. Costs: euros per million tokens

Every LLM architecture decision sooner or later reduces to a cost per million tokens (Mt). APIs bill the input (prompt: amortizable by caching) and the output (generation: expensive) separately; the 2025-2026 orders of magnitude roughly span, from the small open-weight model to the frontier model, from a few cents to a few tens of euros per Mt — rates that change several times a year: any precise figure in course materials would be stale; the method of computation, on the other hand, remains.

Proposition 4.1 — Unit cost of self-hosted serving If a server delivers a sustained throughput of R tokens/s (outputs, continuous batching) on GPUs costing c €/h (rental all inclusive), the operational cost per million output tokens equals:

Key result — cost per million tokens \text{cost/Mt} \;=\; \frac{c}{R} \cdot \frac{10^6}{3600} \;\approx\; 278 \cdot \frac{c}{R} \;\; \text{€/Mt}.

Example: an 8B on a GPU at ~2 €/h delivering R = 2,000 tokens/s in batch → ≈ 0.28 €/Mt; the same GPU on isolated requests (batch 1, R \approx 60) → ≈ 9 €/Mt.

Batching is a factor of 30 on the bill.

Proof. The server produces R tokens per second; each billed hour at c € therefore produces 3600\,R tokens; the cost per token is c/(3600\,R) €, and per million tokens 10^6 c/(3600 R) = 277.8\, c/R . The direct division by R: doubling the throughput halves the cost per token at constant hardware — this is the economic justification of ch. 3. ∎

4.1. The saving levers

  • Prefix cache: shared system prompt + history → the prefill is billed/consumed once; on the API side, prompt caching reduces the input cost of repeated prefixes (often billed at a discount); on the vLLM side, the KV is reused for free.
  • Model routing (cascade): small model first, escalation to the big one if the small one “is not sure” (confidence score, agreement of two candidates, or a classifier). The sequential decision formalized as a bandit (cf. RL module ch. 4): one arbitrates cost vs quality request by request.
  • Output limit: output costs ~5-10× the input; constraining max_tokens and the format (answer in k points, short JSON) is the most underrated lever.
  • Quantization (cf. LLMs ch. 6; Advanced Topics ch. 7): 4 bits ≈ ×2-3 in throughput on the weights — and smaller GPUs.
  • Deferred batch processing: non-interactive tasks (archive classification) go in nightly batches; some APIs bill these modes ~50% cheaper.

4.2. API, fine-tuning or distillation: the break-even volume

The table compares two ways of serving; the next question is which model to serve. An API model is paid per request. A model of your own, fine-tuned or distilled, adds a one-off training cost and a fixed GPU bill, then costs almost nothing per extra request. The methods are taught in LLMs 4.1 and 4.3; this section covers their economics.

Proposition 4.2 — Break-even volume An API request costs a € (its input and output tokens at their prices). An own model costs F € per month of reserved GPUs, a training cost C_{\text{train}} amortized over H months before retraining, and b < a € per request at the margin. Over a month of V requests, the own model is cheaper as soon as V \;\ge\; V^\star = \frac{F + C_{\text{train}}/H}{a - b}.

Proof. The two monthly bills, aV and F + C_{\text{train}}/H + bV, are affine in V with slopes a > b, so they cross once, at V^\star. Below it the API is cheaper; above it the own model is, provided its quality passes the gate of ch. 2. ∎

Worked example — 10 k requests a day (300 k a month), 1,500 input tokens (RAG context) and 300 output tokens, with illustrative API prices of 1 €/Mt in and 4 €/Mt out:

  • API: a = 0.0015 + 0.0012 = 0.0027 € per request, i.e. 810 € a month.
  • Fine-tuned 8B (LoRA, ch. 7) on one GPU at 2 €/h, always on: F \approx 1{,}460 € a month, C_{\text{train}} \approx 600 € (data curation and GPU) over H = 6 months, and b \approx 0, since one batched GPU serves millions of requests a month (Proposition 4.1). Then V^\star \approx 1{,}560 / 0.0027 \approx 580 k requests a month, about 19 k a day.
  • Distilled 1B student on a small GPU at 0.6 €/h: F \approx 440 € a month and C_{\text{train}} \approx 370 € (100 k teacher answers bought from the API, plus training), over the same H = 6 months. Then V^\star \approx 500 / 0.0027 \approx 185 k requests a month, about 6 k a day.
  • Verdict: at 10 k requests a day only the distilled student pays off, and only if it passes the paired gate (Definition 2.3) against the API model. A GPU idle at night still bills F: scaling it down off-peak moves V^\star as much as a change in token prices does.

5. Evaluation in production: drift and monitoring

A model that passed every test at release time degrades silently when the world it serves changes. This chapter defines the kinds of drift, gives the statistics that detect them, and organizes monitoring and LLM-based evaluation in production.

5.1. Data drift, concept drift

Definition 5.1 — Drift Data drift: the distribution of inputs changes (P(X) moves — new topics, new user population, new documentary source). Concept drift: the input → correct answer relation changes (P(Y\mid X) moves — yesterday’s “good” answer becomes wrong: regulation, company merger, vocabulary). For a RAG, a third drift: the corpus changes (ch. 6).

Proposition 5.2 — PSI = Jeffreys divergence The population stability index (PSI), summed over the bins i of a histogram: \mathrm{PSI}(p, q) \;=\; \sum_i \bigl(p_i - q_i\bigr)\, \ln\frac{p_i}{q_i} \;=\; \mathrm{KL}(p \,\|\, q) + \mathrm{KL}(q \,\|\, p), is exactly the Jeffreys divergence: symmetric, zero iff p = q.

Usual thresholds in credit risk: PSI < 0.1 stable; 0.1-0.25 to watch; > 0.25 alert.

Proof. Let us expand: \mathrm{KL}(p\|q) = \sum_i p_i \ln(p_i/q_i), \qquad \mathrm{KL}(q\|p) = \sum_i q_i \ln(q_i/p_i). The sum equals \sum_i (p_i - q_i)\ln(p_i/q_i) — precisely the PSI.

Each term is positive (the two factors p_i - q_i and \ln(p_i/q_i) have the same sign); zero if and only if p_i = q_i for all i. Symmetry is obvious from the summed form. ∎

The classic detectors: PSI/KL per feature (interpretable, bin by bin), the Kolmogorov–Smirnov test for continuous features, the MMD distance between feature distributions (Graph ML 9.6, which uses it to compare generated graphs), and stream detectors (ADWIN) for online signals.

Kolmogorov–Smirnov in three lines. Compare a reference window of n values with a current window of m values through the largest gap between their empirical distribution functions: D = \sup_x \bigl|\widehat F_{\text{ref}}(x) - \widehat F_{\text{cur}}(x)\bigr| . Under “same continuous law” and for large windows, D\sqrt{nm/(n+m)} approximately follows the Kolmogorov distribution, whose 95 % quantile is about 1.36: alert when D > 1.36\,\sqrt{(n+m)/(nm)}.

For an LLM, the “features” to monitor are: prompt length, language, topics (lightweight classifier), presence of injected documents, truncation rate — and output proxies: refusal rate, “I don’t know” rate, median answer length, JSON parse failure rate.

Without online labels, one monitors symptoms; the true metrics come from feedback and sampling.

5.3. The LLM judge in CI and production

Judge: recall and ops consequences A judge model evaluates (question, answer) pairs against a rubric (fidelity to context, completeness, tone). Zheng et al. (MT-Bench, NeurIPS 2023) show agreement with humans > 80% on conversation tasks; its biases — position, verbosity, self-preference — and their mitigations are listed in LLMs 9.2.

Ops consequences: alternated order, explicit rubric, reference provided, human golden set to calibrate the judge, judge version frozen in CI (ch. 1). The judge is a noisy sensor — one uses it to detect regressions, not to certify.

# Mini regression judge in CI: compares prod vs candidate on the golden set
def judge_pair(question, ref, ans_prod, ans_cand, judge):
    rub = "Expected answer (reference): {ref}\nA: {a}\nB: {b}\n" \
          "Which one is more faithful to the reference? Answer A, B, or EQUAL."
    first = judge(f"Q: {question}\n" + rub.format(ref=ref, a=ans_prod, b=ans_cand)).strip()
    second = judge(f"Q: {question}\n" + rub.format(ref=ref, a=ans_cand, b=ans_prod)).strip()
    # alternated order, anti-bias: the candidate wins only if it wins in both positions
    if first.startswith("B") and second.startswith("A"):
        return "cand"
    if first.startswith("A") and second.startswith("B"):
        return "prod"
    return "equal"            # EQUAL, or inconsistent verdicts (position bias)

# gate: no significant regression. "equal" verdicts carry no evidence either way,
# so test prod wins against candidate wins on the decisive pairs only (sign test,
# the logic of McNemar's test in section 2.2)
from scipy.stats import binomtest
verdicts = [judge_pair(**ex, judge=judge) for ex in golden]
w_cand, w_prod = verdicts.count("cand"), verdicts.count("prod")
n_dec = w_cand + w_prod
p = binomtest(w_prod, n_dec, 0.5, alternative="greater").pvalue if n_dec else 1.0
assert p >= 0.05, f"judge regression: prod {w_prod} vs cand {w_cand}, p = {p:.3f}"

A fixed threshold on candidate wins alone would count every tie against the candidate: a candidate identical to production would get no wins and fail. The sign test ignores ties and fails only when production wins significantly more decisive pairs.

6. RAG Ops: freshness and continuous evaluation

A RAG system is only as good as its index, and the documents behind the index change every day. This chapter keeps the index fresh without rebuilding it, and evaluates answer quality continuously without a human in the loop.

Reminder — LLMs module ch. 7 (RAG)

Pipeline: chunking → embeddings → vector index → retrieval (hybrid BM25 + dense, cf. NLP ch. 2 and 7) → reranking → conditioned generation. This chapter treats that pipeline as a data system with freshness and evaluation contracts — not as a demo.

6.1. Incremental indexing and freshness

The enterprise corpus moves: Confluence pages edited, contracts signed, FAQs enriched. The index must follow with an explicit freshness SLA (“a published document is queryable within 15 minutes”). The standard pattern: change data capture (webhooks/API of the document repository) → event queue → incremental upsert into the index, key = (source, doc_id, version).

Subtleties:

  • Idempotence: replaying the same event twice must create only one batch of vectors; deduplicate by key, mark obsolete chunks (soft delete) so as not to break the evaluation links;
  • Per-document atomicity: the chunks of a document v2 replace those of v1 as a block (otherwise retrieval mixes the versions);
  • Embeddings ↔︎ index coupling: changing the embedding model requires re-embedding the whole corpus (the spaces are mutually incompatible); dual-boot of the index during the migration, then switchover — the index is a versioned artifact in the sense of ch. 1;
  • Freshness ≠ total reindexing: measure the cost (summary tokens, GPU time) and aim for incremental everywhere possible.

6.2. Evaluating a RAG without humans: RAGAS

Definition 6.1 — RAGAS metrics (Es et al., 2023, and the ragas library) Es et al. define three reference-free metrics, computed by LLM decomposition: faithfulness (is every claim of the answer attested by the context? — anti-hallucination), answer relevance (does the answer answer the question?) and context relevance (how much of the retrieved context is actually needed?).

The open-source ragas library adds two metrics that compare the retrieval with a ground-truth reference answer: context precision (are the relevant chunks ranked first?) and context recall (are the necessary chunks retrieved?).

The context metrics isolate the retrieval, faithfulness and answer relevance the generation: this is the diagnostic grid missing from a global F1.

from ragas import evaluate

Reading a RAGAS report like an engineer Low recall, high faithfulness: retrieval is failing — improve chunking, hybrid, reranker. High recall, low faithfulness: the model invents despite the context — prompt, stronger model, forced citation. Low relevancy: off-topic or verbose answer. The trap of reference-free metrics: their judge has the biases of ch. 5 — one calibrates them on a hand-annotated sample before making them CI thresholds.

6.3. The graph to the rescue of RAG

Vector RAG fails on global questions (“what are the recurring themes of the 2025 reports?”) that require aggregating the whole corpus; GraphRAG (Edge et al., 2024; cf. Graph ML module ch. 10) builds an entity graph (LLM extraction), partitions it into communities (Leiden) and summarizes each community — the global answer becomes a map-reduce over the summaries.

The ops cost: LLM indexing is expensive (every document goes through extraction calls), hence incremental by necessity; communities are recomputed periodically.

The arbitration (vector vs graph vs hybrid) belongs in the system’s ablation table — and must be re-measured at every model migration (ch. 2).

Freshness of a graph index or KG snapshot A GraphRAG index, or a knowledge-graph snapshot fed to the model, is a derived artifact with its own version, and it ages differently from a vector index.

  • Local vs global parts: entity and relation extraction is incremental per document, keyed by (doc_id, version) as in 6.1; communities and their summaries are global, since one new document can merge or split several communities.
  • Two freshness numbers: the SLA states when a document is retrievable by vector search (minutes) and when it reaches graph-based answers (after the next community run, e.g. nightly). Re-summarize only the communities whose membership changed.
  • Lineage: the snapshot id (extraction model and prompt hash, community run, date) goes into the registry (ch. 1) and every trace (ch. 8), like the vector index version.
  • Deletion: removing a document removes its triples and invalidates the summaries that cited it — the right to erasure applies to derived artifacts too.

7. Fine-tuning Ops: versioned LoRAs

Fine-tuning produces small adapters that are trained often and deployed on a shared base model; without strict bookkeeping, an adapter ends up running on the wrong base or with the wrong prompt. This chapter defines what must be versioned and organizes the fine-tuning cycle in production.

Reminder — SFT and DPO (LLMs module, ch. 4–5), and LoRA

Instruction fine-tuning (SFT, LLMs module ch. 4) adapts the model. LoRA (Hu et al., ICLR 2022), introduced in LLMs 4.3, makes this affordable: it freezes the weights W and learns only \Delta W = BA of rank r \ll d: a few tens of MB instead of GB, trainable on a single GPU. DPO/RLHF (LLMs module, ch. 5) then align the preferences. This chapter is the operations view of LoRA.

Definition 7.1 — Versioned adapter An adapter (LoRA) is usable only when coupled with: (i) its exact base (name + version of the weights); (ii) its prompt template; (iii) its training data (hash); (iv) its hyperparameters (r, \alpha, target modules).

The unit of versioning is not the .safetensors file but this quintuple — a LoRA on the “wrong” base (same architecture, different checkpoint) produces silently degraded outputs.

7.1. The fine-tuning cycle in production

  1. Collect: feedback 👍/👎, expert corrections, questions without a good answer (failed queries from monitoring — ch. 5);
  2. Clean / deduplicate / anonymize: deduplication reduces memorization (Explainability, Security, Privacy of LLMs, ch. 7);
  3. Build the pairs (SFT) then preferences (DPO) — balance of domains, slices evaluated separately (ch. 2);
  4. Train LoRA on the frozen base; log the quintuple;
  5. Qualify: golden set + judge + safety tests (fine-tuning can degrade refusals!) — gate of ch. 2;
  6. Deploy in canary with rollback (ch. 2.3);
  7. Measure the impact (winrate, cost, latency) before generalization — fine-tuning must win against simply improving the prompt and against RAG, otherwise it has no reason to exist.

Multi-LoRA serving Use case: a single 8B engine serves ten clients, each with its own LoRA (tone, domain, language). Modern servers load several adapters on a base shared in memory — a single copy of the weights, the \Delta W (a few tens of MB) being applied per request.

The ops work consists of guaranteeing the routing (client header → adapter) and the isolation of evaluations per tenant (slices of ch. 2). The base rarely changes; the adapters often: two distinct deployment cadences in the same pipeline.

Proposition 7.2 — Size of a LoRA A rank-r LoRA on a layer W \in \mathbb{R}^{d_{\text{out}} \times d_{\text{in}}} stores B \in \mathbb{R}^{d_{\text{out}} \times r} and A \in \mathbb{R}^{r \times d_{\text{in}}}, i.e. r\,(d_{\text{out}} + d_{\text{in}}) \text{ parameters instead of } d_{\text{out}} d_{\text{in}}.

On the q and v projections of the 32 layers of an 8B model (d = 4096; with GQA the v projection has output dimension 1024) at r = 16: 16 \times (4096 + 4096) + 16 \times (4096 + 1024) \approx 2.1 \times 10^5 parameters per layer, about 6.8 M in total — ~0.1% of the parameters, about 14 MB in fp16.

The storage saving is a bonus; the decisive saving is the training cost (no optimizer state on the frozen weights) and the deployment cadence (adapter hot-swap).

8. Agents in production: tracing and guardrails

An agent makes dozens of model and tool calls per request, and any of them can fail, loop or be hijacked. This chapter makes agents observable, bounds what they can spend and do, and explains how to evaluate them.

Reminder — LLMs module ch. 8 (agents)

An agent = an LLM in a loop (observation → reasoning → action via tools), with memory and possibly multi-step planning. This chapter adds no intelligence: it adds observability, the budgets and the permissions without which an agent is undebuggable and dangerous.

8.1. Tracing: the tree of calls

An agent request unfolds in dozens of nested LLM and tool calls. The central datum is the trace: a tree of spans (one span per call: input, output, token cost, latency, model, attempt), OpenTelemetry-compliant — the vendors Langfuse/W&B Weave plug into it.

Without a trace: no ability to answer “why did the agent send this email?”. With a trace: deterministic replay (by logging the seeds/times), bottleneck analysis (which tool dominates the latency?), per-step costs, and detection of behavioral anomalies (loops: same tool, same arguments, N times).

Example 8.1 — The budget as the first guardrail A monitoring agent performs on average 6 LLM calls + 3 tool calls per task. A malicious user (or a booby-trapped document — indirect injection, LLMs 9.4) can make it loop: each iteration re-injects a bit of context. Cap per task: steps ≤ 15, tokens ≤ 50 k, cost ≤ 0.10 € — and cut off cleanly (degraded answer: “I could not finish”): the failure becomes a bounded cost instead of a billing incident.

Proposition 8.2 — Per-task success collapses with length If each step succeeds independently with probability p, a task of k steps succeeds with p^k: p = 0.95 and k = 20 give 36%.

Hence: (i) shorten the chains (more reliable tools, shallower plans); (ii) local retries and reflexivity; (iii) evaluate agents per complete task, never per step.

8.3. Evaluating an agent

Agent metrics: success rate per task (on scripted tasks with an initial state and a success criterion — e.g. “the ticket is created with the right fields”), average cost per task (tokens × price + tools), end-to-end P95 latency, human intervention rate. The evaluation environments must be replayable: simulated tools (mock Confluence, mock mail) for CI, a sampled real environment for production — the simulation runs hundreds of tasks for a few cents.

Definition 8.3 — Error budget (Beyer et al., Site Reliability Engineering, 2016) An SLO with target s over a window of N requests or tasks allows (1 - s)\,N failures: this allowance is the error budget. While budget remains, releases go ahead; once it is spent, releases freeze and the team works on reliability until the window rolls over.

For an agent, the SLO is stated per complete task. With a 95 % task-success SLO and 10,000 tasks a month, the budget is 500 failed tasks. Proposition 8.2 tells how fast a longer plan spends it: at p = 0.997 per step, a 10-step plan fails about 3 % of tasks (some 300 failures, within budget), a 20-step plan about 5.8 % (some 580, over budget) — unless its steps become more reliable.

9. Operational security: secrets, sandbox, supply chain

An LLM application holds credentials, executes generated code and depends on weights and libraries downloaded from elsewhere; each is an entry point for an attacker. This chapter secures the system around the model.

Scope The attacks against the model (jailbreaks, injections, poisoning, extraction) are introduced in LLMs 9.4 and treated in depth by the M2 P2 co-requisite Explainability, Security, Privacy of LLMs (ESP, ch. 5–6). Here: the security of the system around the model — the ops of an LLM application; the reference checklist of the field is the OWASP Top 10 for LLM Applications.

9.1. Secrets and identities

  • API keys, database passwords, index tokens: never in the code nor the images — a vault (Vault, Secret Manager) injected at startup; periodic rotation; repository scanners in CI (a secret committed = compromised, even “just on a branch”);
  • Each service has its identity (service account) and least privilege: the RAG engine does not need write access to the corpus; the agent does not need the credentials of the administrative database;
  • The outputs of the LLM are data, never instructions: a model’s response must never be evaluated/executed (eval, shell, SQL) without validation — the flaw class “the model generated the code, we execute it” is a special case of indirect injection (LLMs 9.4; ESP 5.3).

9.2. Sandbox and isolation

When the agent executes code (notebooks, “calculator” tools, plugins), execution must be confined: an ephemeral container, a temporary file system, outbound network blocked by default, CPU/RAM limits, a hardened runtime (e.g. gVisor/Firecracker for kernel-level isolation), and filtering of exfiltrations — including over slow channels (DNS queries, timing).

An agent compromised by injection will try to exfiltrate via the only channel it was left (the tools! the mail! the displayed output?). Hence the duo permissions (ch. 8) + sandbox: the same principle as in system security — compromise is likely, blast radius minimal.

9.3. Supply chain

  • Model weights: downloaded from verified sources, sha256 fingerprint recorded in the registry (ch. 1) — an open-weight model is a dependency like a library, with “logical” CVEs (backdoors: ESP 5.4; Security and Robustness, ch. 6) and no automatic scanner;
  • Dependencies: lockfiles, SBOM, classic vulnerability scans in CI (same as any app);
  • Prompts and adapters: mandatory review — a prompt is code in disguise; a LoRA trained on unvalidated data is an opaque dependency;
  • Logs: the traces contain user text (personal data?) — limited retention, anonymization, controlled access; cf. ESP ch. 8–10, whose ch. 10 covers the AI Act.

10.2. Green ops: measuring energy

The energy cost of LLMs concentrates (i) in pre-training — Patterson et al. (2021) formalize the carbon accounting of large trainings (consumption, regional electricity mix, PUE); Luccioni et al. (2022) do the same for BLOOM including the amortization of training; (ii) in aggregated inference — billions of requests of a few Wh each.

For a developer, the useful unit is the consumption per request: measurable with CodeCarbon (CPU/GPU/PUE meter) around each serving point.

from codecarbon import EmissionsTracker

with EmissionsTracker(measure_power_secs=1, log_level="warning") as tracker:
    answer = rag_pipeline.answer(question)      # full request

print(f"{tracker.total_energy_kWh * 1000:.1f} Wh for this request",
      f"({tracker.total_emissions * 1e3:.1f} gCO2e on the local mix)")

Proposition 10.1 — The four green levers, in order of effectiveness

  1. Functional sobriety: routing to small models, shorter outputs, cache (ch. 4) — divides the energy without touching the hardware.
  2. Quantization: ~2-4× on the energy throughput per token (cf. LLMs ch. 6).
  3. Batching: the same GPU delivers more tokens per Wh in batch (ch. 3). Proposition 4.1 holds with the power drawn, P watts (GPU, host share and PUE), in place of the price c €/h, since P watts for one hour is P Wh: \text{energy/Mt} \;=\; \frac{P}{R} \cdot \frac{10^6}{3600} \;\approx\; 278 \cdot \frac{P}{R} \;\; \text{Wh/Mt}. At P = 500 W and R = 2{,}000 tokens/s this is about 70 Wh/Mt; at batch 1 (R \approx 60) and the same power, about 2.3 kWh/Mt — the factor of 30 of the bill. A lightly loaded GPU draws less power, so the real energy factor is somewhat smaller.
  4. Geographic and temporal scheduling: moving the nightly batches to the low-carbon-mix regions at the right moment.

The order matters: one does not buy green GPUs before having shortened the outputs.

Written exam (proposal)

Format: 2 hours; one handwritten A4 sheet and a non-programmable calculator allowed; 4 questions — a course question, a computation, a short proof and a drift exercise.

  1. Question (5 points). A team releases a new prompt template with a new LoRA adapter for the enterprise assistant. (a) List the artifacts and fingerprints the release must record (2 pts). (b) Give the CI layers in order, the deployment stages and the rollback unit (2 pts). (c) On 100 decisive pairs, the order-swapped judge prefers the candidate 55 times: may the team claim an improvement (1 pt)?

    Expected:

      1. The four fingerprints (code commit, data hash, configuration, container digest); the prompt-template version; the exact base-model hash, adapter data hash and hyperparameters (Definition 7.1); the evaluation-set hash and the judge version.
      1. Code tests, data contracts, model and prompt tests on the golden set with the paired gate, then infrastructure; shadow, canary at 5 %, full rollout. The rollback unit is a registry version (weights, adapter, prompt, index), redeployed in one command.
      1. No. Under “no difference”, 55 or more wins out of 100 has probability about 0.18, so 55 % is within the noise; ties carry no evidence either way.

  2. Question (6 points). A model has 32 layers and 8 KV heads of dimension 128 (fp16 cache); 60 GiB of GPU memory are left for the cache. Requests have 1,500 prompt and 300 output tokens; TTFT is 0.5 s and TPOT 50 ms. (a) KV bytes per token and KV tokens available (1.5 pts). (b) Maximum concurrent requests, each counted at full length (1 pt). (c) With Little’s law, the largest sustainable arrival rate (1.5 pts). (d) At that rate, the cost per million output tokens and per request on a GPU rented at 3 €/h (2 pts).

    Expected:

      1. 2 \times 32 \times 8 \times 128 \times 2 = 131{,}072 bytes, i.e. 128 KiB per token; 60 \times 2^{30} / 2^{17} = 491{,}520 tokens.
      1. 491{,}520 / 1{,}800 \approx 273 requests.
      1. W = 0.5 + 299 \times 0.05 \approx 15.5 s (299 gaps after the first token), so \lambda \le 273 / 15.5 \approx 17.6 requests/s. Check: 273 sequences at 20 tokens/s each decode about 5,460 tokens/s, close to R = 17.6 \times 300 \approx 5{,}280 tokens/s.
      1. Proposition 4.1 gives 278 \times 3 / 5{,}280 \approx 0.16 €/Mt; per request, 3 / (17.6 \times 3600) \approx 4.7 \times 10^{-5} €, about 5 cents per thousand requests.

  3. Question (5 points). Two models are scored on the same n i.i.d. items.

      1. The per-item losses have variances \sigma_1^2 and \sigma_2^2 and correlation \rho. Show that the mean paired difference has variance (\sigma_1^2 + \sigma_2^2 - 2\rho\sigma_1\sigma_2)/n, and say when pairing helps (2 pts).
      1. For right/wrong scores, let a count the items only the candidate gets right, b those only production gets right, and m = a + b. Show that under “equal accuracy”, conditionally on m, a \sim \mathrm{Bin}(m, 1/2); deduce McNemar’s statistic (a - b)^2/(a + b) (2 pts).
      1. Apply it with a = 30 and b = 40 (1 pt).

    Expected:

      1. The differences \delta_i are i.i.d. with variance \sigma_1^2 + \sigma_2^2 - 2\rho\sigma_1\sigma_2, and averaging n i.i.d. terms divides the variance by n. Pairing helps when \rho > 0, i.e. when both models fail on the same hard items; independent test sets would give \rho = 0.
      1. Equal accuracy forces the two kinds of discordance to be equally likely, so each discordant item favours either model with probability 1/2, independently: a has mean m/2 and variance m/4. Hence z = \frac{a - m/2}{\sqrt{m}/2} = \frac{a - b}{\sqrt{a + b}} is approximately standard normal, and z^2, McNemar’s statistic, approximately follows \chi^2_1.
      1. \chi^2 = 100/70 \approx 1.43 < 3.84: no significant difference at 5 % (p \approx 0.23), as in the worked example of 2.2.

  4. Question (4 points). A prompt-length feature is split into three bins. The reference week has proportions (0.5, 0.3, 0.2), the current week (0.3, 0.3, 0.4). (a) Compute the PSI and classify it with the usual thresholds (2 pts). (b) What happens if a bin is empty in the current week, and how is it fixed (1 pt)? (c) Which monitoring loop of 5.2 handles this signal, and with what action (1 pt)?

    Expected:

      1. 0.2 \ln(5/3) + 0 + 0.2 \ln 2 \approx 0.102 + 0.139 = 0.24: “to watch” (0.1–0.25), just under the alert threshold.
      1. The term \ln(p_i/0) is infinite, and so is the PSI. Smooth the histograms (add a small \epsilon to every bin) or merge sparse bins.
      1. The daily loop: open a ticket and investigate (a new user population? a new document source?), and confirm on the refreshed golden set before any retraining.
