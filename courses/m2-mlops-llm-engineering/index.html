The founding observation. A model reaching 92% F1 in a notebook does not “work”: it works in an environment. The founding paper of the field (Sculley et al., NeurIPS 2015) shows that ML technical debt lives not in the model but around it: data pipelines, glue code, dependency chains, configurations, and feedback loops — the model in production influences the data that will be used to retrain it. The LLM does not abolish this debt; it adds three specificities: the model is non-deterministic, its input space is all of natural language (hence not boundable by a schema), and its unit cost (the token) is billed on every request.

Definition 0.1 — ML Ops The set of software, data, and systems engineering practices applied to the complete lifecycle of a machine learning system: development, testing, integration, deployment, monitoring, retraining. LLM engineering is the special case where the central component is a language model (API or open weights), typically within a RAG, a fine-tuning, or an agent.

1. Lifecycle: versioning data, features, models

Concrete scene: a business RAG passes demos and fails in prod on 12% of queries (chunks too large, no golden set). This chapter fixes measurement loops.

What breaks Unversioned prompts; no regression eval; serving without token budgets / timeouts; confusing mean latency with p95.

The ML lifecycle extends well beyond training: collection → labeling → features → training → evaluation → registry → deployment → monitoring → (re)training. Every arrow in this cycle is an artifact that must be identified immutably; failing that, no metric is reproducible — neither for debugging, nor for audits, nor in front of a client.

Definition 1.1 — Artifact and lineage An artifact is any object produced or consumed by the cycle: dataset, feature schema, weights, tokenizer, prompt template, vector index, configuration, container image. The lineage is the graph of artifact → artifact dependencies. A training is reproducible when code + data + configuration + environment are all identified by fingerprints (hashes) and replayable.

Proposition 1.2 — The triple fingerprint A training run is reproducible only if one can replay the triplet (\text{code}, \text{data}, \text{config}). In practice: git versions the code (commit hash), DVC versions the data and the weights (content fingerprint, the living file staying out of the repository), and params.yaml links the two. Every published metric references the three fingerprints — otherwise it is not a measurement, it is a rumor.

# Bulky data versioned by content (DVC) -- only the pointer goes into git
$ dvc add data/faq_2026.parquet          # creates data/faq_2026.parquet.dvc (hash + size)
$ git add data/faq_2026.parquet.dvc && git commit -m "faq v3 (dedup + PII scrub)"

# Declarative pipeline: stages re-run if and only if their inputs change
# dvc.yaml
stages:
  prepare:
    cmd: python src/prepare.py data/raw/ data/train.parquet
    deps: [data/raw/, src/prepare.py]
    outs: [data/train.parquet]
  finetune:
    cmd: python src/train_lora.py --config params.yaml
    deps: [data/train.parquet, src/train_lora.py, params.yaml]
    outs: [artifacts/lora_faq_v3/]
  evaluate:
    cmd: python src/evaluate.py --run artifacts/lora_faq_v3/
    deps: [artifacts/lora_faq_v3/, data/eval_v3.parquet]
    metrics: [artifacts/lora_faq_v3/metrics.json:
              {cache: false}]

$ dvc exp run            # replays the chain, records the experiment
$ dvc metrics diff       # compares v2 -> v3

1.1. Feature stores and registries

For tabular ML, a feature store (e.g. Feast) serves the same feature definition offline (training, batch) and online (serving, low-latency), eliminating training/inference skew — the sneakiest class of bug in industrial ML. For LLMs, the functional equivalent is twofold: the prompt cache (shared prefixes; cf. ch. 4) and the embedding bank of the RAG (ch. 6), whose schema (chunk type, embedding model, index version) must be managed like a feature: identified, versioned, replayable.

The model registry (MLflow, or a privatized hf_hub directory) records for each version: the fingerprints of the triplet, the qualification metrics, the signature (inputs/outputs), and the status (staging / production / archived). A deployment never references “the latest training” but a frozen version of the registry.

LLM specificity: prompts and evals are artifacts In an LLM application, three families of artifacts add to the classic triplet: (i) prompt templates (versioned like code, with tests — ch. 2); (ii) evaluation sets (golden sets question → expected answer / relevant documents); (iii) the embedding models and index of the RAG, coupled: changing the embedding model invalidates the whole index (ch. 6). Forgetting to version a prompt is equivalent to not versioning the weights.

2. CI/CD for ML: testing data and models

The continuous integration of an ML system tests four layers, in order of increasing cost: the code, the data, the model, the infrastructure. The golden rule: make the pipeline fail as early as possible, at the cheapest level.

2.1. Data tests

Data is an interface like any other: one writes contracts for it. A data contract checks: the schema (types, columns, bounds), business invariants (allowed nulls, ranges), and statistical properties (duplication rate, distribution of a key column). Tools: Pandera (contracts in Python, executed in the pipeline), Great Expectations (declarative validation suites), quality servers integrated into platforms.

import pandera as pa
import pandas as pd

schema = pa.DataFrameSchema({
    "question": pa.Column(str, pa.Check.str_length(3, 2000)),
    "answer":   pa.Column(str, pa.Check.str_length(1, 8000), nullable=True),
    "lang":     pa.Column(str, pa.Check.isin(["fr", "en"])),
    "doc_ids":  pa.Column(pa.List(str), pa.Check.list_length(1, 10)),
    "n_tokens": pa.Column(int, pa.Check.ge(0), pa.Check.le(4096)),
})

def validate(df: pd.DataFrame) -> pd.DataFrame:
    return schema.validate(df, lazy=True)   # collects ALL errors

2.2. Model tests — and prompt tests

Definition 2.1 — Model non-regression test Let a fixed qualification set D_{\text{qual}} and a metric m (F1, accuracy rate, refusal rate, mean cost). The candidate f_{\text{new}} replaces f_{\text{prod}} if m(f_{\text{new}}) \geq m(f_{\text{prod}}) - \tau, where \tau is the tolerance margin. The subtle point: m is measured on a sample — deciding with a measured gap requires knowing when it is significant.

Proposition 2.2 — Decision threshold by concentration (Hoeffding) Let \ell be a loss bounded in [0,1], measured on n i.i.d. examples. With probability \geq 1-\delta (on both sides): \bigl\|\;\mathbb{E}[\ell] - \widehat{\ell}_n\;\bigr\| \;\leq\; \sqrt{\frac{\log(2/\delta)}{2n}}. To decide a rollback at \delta = 0.05 on n = 1000 examples, two models whose losses differ by less than \sqrt{\log 40 / 2000} \approx 0.027 are not distinguishable: the observed gap may be sampling noise.

Proof. The Hoeffding bound (proved in the ML module) applies to the n i.i.d. variables \ell_i \in [0,1]: \mathbb{P}\bigl(\|\overline{\ell} - \mathbb{E}\ell\| \geq t\bigr) \leq 2e^{-2nt^2}. Setting the right-hand side to \delta yields t = \sqrt{\log(2/\delta)/(2n)}. To compare two models one applies it to the variable \ell_{\text{new}} - \ell_{\text{prod}} (bounded in [-1,1], a factor 2 over the range — hence a factor 2 under the root). With n=1000, \delta = 0.05 and the signed version: t \approx 2.8\,‰. ∎

Practical consequence A “+0.4% F1” measured on 500 examples proves nothing: the 95% confidence interval is on the order of ±4 points for a metric at 50%. CI gateways must therefore require a minimal gap (margin \tau and significance), under pain of “dancing on the noise” — a rollback here, a rollback there, and a slow drift of quality.

Model tests also come in slices: performance per language, per context length, per topic, per user category — a global aggregate can mask a localized drop (a fairness theme, cf. Emerging ML module ch. 6). For an LLM, prompt tests add on: output format (valid JSON, schema), refusal guarantees (forbidden phrases), determinism wrappers (temperature 0, seed) and an LLM judge as oracle (ch. 5) — the judge itself being versioned and tested on a golden set.

2.3. Continuous delivery: canary and shadow

The deployment of an ML component is progressive: shadow (the new model receives duplicated traffic, its output is logged but not served — zero risk, double cost), canary (5% of traffic, automatic rollback if the guard metrics — latency, error rate, negative feedback — degrade), then full rollout. Rollback must be a single button: the previous version (weights + prompt + index) stays deployable in one command, thanks to the registry of ch. 1.

3. LLM serving: continuous batching, P99 latency

Reminder — LLMs module ch. 6 (inference)

Autoregressive decoding generates one token per forward pass; attention requires retaining the keys/values of all past tokens (KV cache); quantization reduces the weights and the KV; the per-token complexity grows with the context length. This chapter moves from “how it computes” to “how it holds a load”.

3.1. Batching: from one request to N

A GPU executes a decoding step in a time nearly independent of the number of sequences present in the batch (as long as memory and bandwidth allow): the operations are parallel and the GPU is memory-bound on the weights. Serving B sequences simultaneously therefore divides the cost per token by almost B — this is the economic argument for shared serving. Naive batching (static batching) waits to have B requests, processes them as a block, and leaves the GPUs idle as soon as a short sequence finishes: yet a 20-token request ends quickly, and the batch becomes sparse.

Definition 3.1 — Continuous batching (Orca, OSDI 2022) Schedule serving at the iteration level rather than the request level: at every decoding step, finished sequences leave the batch and waiting requests enter it. The GPU no longer idles between two requests. Combined with selective batching (batched operations where possible, per-request loops elsewhere), Orca claims up to 36.9× the throughput of prior systems at equal latency.

# Continuous batching loop (simplified) -- the heart of every modern LLM server
running, queue = [], deque()

def step():
    # 1) decoding: one iteration for ALL active sequences (a single GPU call)
    outputs = model.forward_batch([s.tokens for s in running])
    # 2) remove finished sequences (EOS or max length)
    for s in [s for s in running if s.finished(outputs)]:
        running.remove(s); s.finalize()
    # 3) admit new requests as long as the KV memory allows
    while queue and kv_pool.has_room(queue[0].prompt_len):
        running.append(queue.popleft().prefill())
    # 4) preemptive scheduling: if the KV saturates, evict (recompute/swap)

3.2. Memory: the KV cache and PagedAttention

Proposition 3.2 — KV cache size For a transformer with L layers, h\_{\\text{kv}} key/value heads (GQA) of dimension d_h, in precision b bytes, the cache of a sequence of T tokens occupies: M_{\text{KV}} \;=\; 2 \cdot L \cdot h_{\text{kv}} \cdot d_h \cdot b \cdot T \;\text{bytes}. Example (Llama-3-8B: L=32, h\_{\\text{kv}}=8, d_h=128, fp16 b=2): 2\\times32\\times8\\times128\\times2 = 131,072 bytes ≈ 128 KiB per token, i.e. 1 GiB for 8,192 tokens — more than some models weigh in significant bits.

Proof. Direct counting. Each layer l stores, for each token t, a key k_t\^{(l)} and a value v_t\^{(l)}, each a vector of h\_{\\text{kv}} \\cdot d_h coefficients (the “query” attention heads may be more numerous — GQA — but only the K/V heads are cached). Each coefficient costs b bytes: per layer and per token, 2\\,h\_{\\text{kv}}d_h b bytes; multiplying by L layers and T tokens gives the formula. ∎

Continuous batching therefore makes memory occupancy oscillate at every iteration (sequences entering/leaving). Allocating the KV as one maximal contiguous block (maximum output length reserved in advance) wastes: vLLM (SOSP 2023) treats the KV cache like the virtual memory of an OS — pages of 16 tokens, allocated on demand, non-contiguous, shareable between sequences derived from the same prefix (system prompt shared by thousands of requests): waste reduced to ~4% versus more than 60% for static allocation, throughput 2-4× prior systems. Ops consequence: the real capacity of a server is measured in “available KV tokens”, not in concurrent requests.

3.3. Latency: TTFT, TPOT, P99

Definition 3.3 — LLM serving SLO TTFT (time to first token): request → first token delay — dominated by the prefill (prompt) and the waiting queue. TPOT (time per output token): generation cadence — dominated by decoding and batch contention. P99: 99th percentile of a latency distribution — the relevant contractual commitment; the average masks queues. A typical interactive assistant SLO: TTFT P99 < 1.5 s, TPOT P99 < 80 ms/token.

Theorem 3.4 — Little’s law In a stable system in steady state, with L average clients present, \\lambda clients arriving per second on average and W mean sojourn time: L \;=\; \lambda\, W. Serving corollary: at an imposed generation cadence (W fixed by the number of tokens and the TPOT), the number of concurrent requests supported is L = \\lambda W — the necessary concurrency grows linearly with the targeted throughput.

Proof. Proof by an output argument (direct). Over an interval [0, t], let A(t) be the number of arrivals and D(t) the number of departures. The mean number of clients present is written L_t = \\frac{1}{t}\\int_0\^t N(u)\\,du, where N(u) = present at instant u. Each request contributes to this integral exactly its sojourn time: $\int_0^t N(u)\,du = \sum_{i \,\text{departed by} \leq t} W_i + $ (residuals of requests still present). Dividing by t and letting t\\to\\infty (stability: A(t)/t \\to \\lambda, bounded residuals become negligible), one obtains L = \\lambda\\, W — the argument requires no independence or distribution assumption; it is purely accounting. ∎

Throughput versus latency: the batch trade-off Increasing B (target batch) improves throughput (amortized cost/token) but lengthens the waiting queue — hence the TTFT P99. Modern servers expose this trade-off: max_num_seqs, token budgets per step, and preemption policies (recompute vs swap). Rule of thumb: size the target batch so that KV occupancy stays below ~90%, and let the autoscaler (ch. 3.4) absorb spikes rather than growing the batch beyond the SLO.

3.4. Autoscaling

The relevant signal for scaling an LLM server is not CPU but: the waiting queue length (requests pending admission), the mean waiting time (TTFT − prefill time) and the KV occupancy rate. Horizontal autoscaling (HPA on a custom Prometheus metric) adds replicas; watch out for warm-up spikes (weight loading: tens of seconds to minutes — pre-pull the images, or pay the P99). For multi-GPU models (tensor parallel; cf. Emerging ML module ch. 2 on distributed computing), each replica is a group of GPUs; scaling changes the granularity of parallelism, not just the number of pods.

# Launch a vLLM server exposing an (OpenAI-compatible) API on port 8000

# Async benchmark: TTFT / TPOT P50-P99 as a function of concurrency
import asyncio, time, statistics, httpx

async def one(client, prompt, n_out=256):
    t0 = time.perf_counter(); first = None; n = 0
    async with client.stream("POST", "/v1/chat/completions",
            json={"model": "...", "messages": [{"role": "user", "content": prompt}],
                  "max_tokens": n_out, "stream": True}) as r:
        async for chunk in r.aiter_lines():
            if chunk.startswith("data:") and '"content"' in chunk:
                first = first or time.perf_counter() - t0   # TTFT
                n += 1
    return first, (time.perf_counter() - t0 - first) / n    # (TTFT, TPOT)

async def main(conc=64):
    async with httpx.AsyncClient(base_url="http://localhost:8000",
                                 timeout=300) as c:
        res = await asyncio.gather(*[one(c, "Summarize this report in 5 points.")
                                     for _ in range(conc)])
    p = lambda x, q: sorted(x)[int(q * len(x))]
    ttft = [r[0] for r in res]; tpot = [r[1] for r in res]
    print(f"conc={conc}  TTFT p50/p99 = {p(ttft,.5):.2f}/{p(ttft,.99):.2f}s"
          f"  TPOT p99 = {p(tpot,.99)*1e3:.0f}ms")

for conc in (1, 4, 16, 64, 256): asyncio.run(main(conc))

4. Costs: euros per million tokens

Every LLM architecture decision sooner or later reduces to a cost per million tokens (Mt). APIs bill the input (prompt: amortizable by caching) and the output (generation: expensive) separately; the 2025-2026 orders of magnitude roughly span, from the small open-weight model to the frontier model, from a few cents to a few tens of euros per Mt — rates that change several times a year: any precise figure in course materials would be stale; the method of computation, on the other hand, remains.

Proposition 4.1 — Unit cost of self-hosted serving If a server delivers a sustained throughput of R tokens/s (outputs, continuous batching) on GPUs costing c €/h (rental all inclusive), the operational cost per million output tokens equals: \text{cost/Mt} \;=\; \frac{c}{R} \cdot \frac{10^6}{3600} \;\approx\; 278 \cdot \frac{c}{R} \;\; \text{€/Mt}. Example: an 8B on a GPU at ~2 €/h delivering R = 2,000 tokens/s in batch → ≈ 0.28 €/Mt; the same GPU on isolated requests (batch 1, R \approx 60) → ≈ 9 €/Mt. Batching is a factor of 30 on the bill.

Proof. The server produces R tokens per second; each billed hour at c € therefore produces 3600\,R tokens; the cost per token is c/(3600\,R) €, and per million tokens 10^6 c/(3600 R) = 277.8\, c/R. The direct division by R: doubling the throughput halves the cost per token at constant hardware — this is the economic justification of ch. 3. ∎

4.1. The saving levers

  • Prefix cache: shared system prompt + history → the prefill is billed/consumed once; on the API side, prompt caching reduces the input cost of repeated prefixes (often billed at a discount); on the vLLM side, the KV is reused for free.
  • Model routing (cascade): small model first, escalation to the big one if the small one “is not sure” (confidence score, agreement of two candidates, or a classifier). The sequential decision formalized as a bandit (cf. RL module ch. 6): one arbitrates cost vs quality request by request.
  • Output limit: output costs ~5-10× the input; constraining max_tokens and the format (answer in k points, short JSON) is the most underrated lever.
  • Quantization (cf. LLMs ch. 6; Advanced Topics ch. 6): 4 bits ≈ ×2-3 in throughput on the weights — and smaller GPUs.
  • Deferred batch processing: non-interactive tasks (archive classification) go in nightly batches; some APIs bill these modes ~50% cheaper.

Multilingual and real costs The per-token bill interacts with tokenization (cf. LLMs module ch. 1): a French corpus typically costs 15-25% more tokens than an equivalent English corpus with the dominant tokenizers. The “price per word” therefore depends on the language — an argument for measuring (exercise 5) rather than trusting round conversion tables.

5. Evaluation in production: drift and monitoring

5.1. Data drift, concept drift

Definition 5.1 — Drift Data drift: the distribution of inputs changes (P(X) moves — new topics, new user population, new documentary source). Concept drift: the input → correct answer relation changes (P(Y\mid X) moves — yesterday’s “good” answer becomes wrong: regulation, company merger, vocabulary). For a RAG, a third drift: the corpus changes (ch. 6).

Proposition 5.2 — PSI = Jeffreys divergence The population stability index (PSI), summed over the bins i of a histogram: \mathrm{PSI}(p, q) \;=\; \sum_i \bigl(p_i - q_i\bigr)\, \ln\frac{p_i}{q_i} \;=\; \mathrm{KL}(p \,\|\, q) + \mathrm{KL}(q \,\|\, p), is exactly the Jeffreys divergence: symmetric, zero iff p = q. Usual thresholds in credit risk: PSI < 0.1 stable; 0.1-0.25 to watch; > 0.25 alert.

Proof. Let us expand: \mathrm{KL}(p\|q) = \sum_i p_i \ln(p_i/q_i) and \mathrm{KL}(q\|p) = \sum_i q_i \ln(q_i/p_i). The sum equals \sum_i (p_i - q_i)\ln(p_i/q_i) — precisely the PSI. Each term is positive (the two factors p_i - q_i and \ln(p_i/q_i) have the same sign); zero if and only if p_i = q_i for all i. Symmetry is obvious from the summed form. ∎

The classic detectors: PSI/KL per feature (interpretable, bin by bin), Kolmogorov-Smirnov test (comparison of continuous distributions, cf. Refresher Statistics), MMD distance (ML module), and stream detectors (ADWIN) for online signals. For an LLM, the “features” to monitor are: prompt length, language, topics (lightweight classifier), presence of injected documents, truncation rate — and output proxies: refusal rate, “I don’t know” rate, median answer length, JSON parse failure rate. Without online labels, one monitors symptoms; the true metrics come from feedback and sampling.

Documenting this loop is part of the audit (ch. 9; Emerging ML module ch. 6 on fairness).

5.3. The LLM judge in CI and production

Judge: how, and with which biases A judge model evaluates (question, answer) pairs against a rubric (fidelity to context, completeness, tone); Zheng et al. (MT-Bench, NeurIPS 2023) show agreement with humans > 80% on conversation tasks — but with documented biases: preference for the first position, for long answers, and self-preference (the judge favors its own style). Good practices: alternated order, explicit rubric, reference provided, human golden set to calibrate the judge, judge version frozen in CI (ch. 1). The judge is a noisy sensor — one uses it to detect regressions, not to certify.

# Mini regression judge in CI: compares prod vs candidate on the golden set
def judge_pair(question, ref, ans_prod, ans_cand, judge):
    rub = "Expected answer (reference): {ref}\nA: {a}\nB: {b}\n" \
          "Which one is more faithful to the reference? Answer A, B, or EQUAL."
    out = judge(f"Q: {question}\n" + rub.format(ref=ref, a=ans_prod, b=ans_cand))
    out_sw = judge(f"Q: {question}\n" + rub.format(ref=ref, a=ans_cand, b=ans_prod))
    pair = {out.strip()[:4], out_sw.strip()[:4]}      # alternated order, anti-bias
    return "cand" if pair == {"A", "B"} else ("prod" if pair == {"B", "A"} else "equal")

# gate: no significant regression (cf. prop. 2.2 for the minimal margin)
wins = sum(judge_pair(**ex) == "cand" for ex in golden)
assert wins >= 0.45 * len(golden), f"judge regression: {wins}/{len(golden)}"

6. RAG Ops: freshness and continuous evaluation

Reminder — LLMs module ch. 7 (RAG)

Pipeline: chunking → embeddings → vector index → retrieval (hybrid BM25 + dense, cf. NLP ch. 2 and 7) → reranking → conditioned generation. This chapter treats that pipeline as a data system with freshness and evaluation contracts — not as a demo.

6.1. Incremental indexing and freshness

The enterprise corpus moves: Confluence pages edited, contracts signed, FAQs enriched. The index must follow with an explicit freshness SLA (“a published document is queryable within 15 minutes”). The standard pattern: change data capture (webhooks/API of the document repository) → event queue → incremental upsert into the index, key = (source, doc_id, version). Subtleties:

  • Idempotence: replaying the same event twice must create only one batch of vectors; deduplicate by key, mark obsolete chunks (soft delete) so as not to break the evaluation links;
  • Per-document atomicity: the chunks of a document v2 replace those of v1 as a block (otherwise retrieval mixes the versions);
  • Embeddings ↔︎ index coupling: changing the embedding model requires re-embedding the whole corpus (the spaces are mutually incompatible); dual-boot of the index during the migration, then switchover — the index is a versioned artifact in the sense of ch. 1;
  • Freshness ≠ total reindexing: measure the cost (summary tokens, GPU time) and aim for incremental everywhere possible.

6.2. Evaluating a RAG without humans: RAGAS

Definition 6.1 — RAGAS metrics (Es et al., 2023) Four reference-free metrics, computed by LLM decomposition: faithfulness (is every claim of the answer attested by the context? — anti-hallucination), answer relevancy (does the answer answer the question?), context precision (are the relevant chunks indeed ranked first?) and context recall (are the necessary chunks retrieved? — requires a reference answer). The last two isolate the retrieval, the first two the generation: this is the diagnostic grid missing from a global F1.

from ragas import evaluate
from ragas.metrics import (faithfulness, answer_relevancy,
                           context_precision, context_recall)
from datasets import Dataset

ds = Dataset.from_dict({
    "question":     q_list,          # golden set (ch. 1: version this set!)
    "answer":       answers,         # outputs of the candidate pipeline
    "contexts":     retrieved_chunks,
    "ground_truth": ref_answers,     # for context_recall
})
report = evaluate(ds, metrics=[faithfulness, answer_relevancy,
                               context_precision, context_recall])
# CI gate: faithfulness >= 0.85; weekly panel: the 4 time series

Reading a RAGAS report like an engineer Low recall, high faithfulness: retrieval is failing — improve chunking, hybrid, reranker. High recall, low faithfulness: the model invents despite the context — prompt, stronger model, forced citation. Low relevancy: off-topic or verbose answer. The trap of reference-free metrics: their judge has the biases of ch. 5 — one calibrates them on a hand-annotated sample before making them CI thresholds.

6.3. The graph to the rescue of RAG

Vector RAG fails on global questions (“what are the recurring themes of the 2025 reports?”) that require aggregating the whole corpus; GraphRAG (Edge et al., 2024; cf. Graph ML module ch. 11) builds an entity graph (LLM extraction), partitions it into communities (Leiden) and summarizes each community — the global answer becomes a map-reduce over the summaries. The ops cost: LLM indexing is expensive (every document goes through extraction calls), hence incremental by necessity; communities are recomputed periodically. The arbitration (vector vs graph vs hybrid) belongs in the system’s ablation table — and must be re-measured at every model migration (ch. 2).

7. Fine-tuning Ops: versioned LoRAs

Reminder — LLMs module ch. 4-5: SFT, LoRA, DPO

Instruction fine-tuning (SFT) adapts the model; LoRA (Hu et al., ICLR 2022) freezes the weights W and learns only \Delta W = BA of rank r \ll d: a few tens of MB instead of GB, trainable on a single GPU. DPO/RLHF (ch. 5) then align the preferences.

Definition 7.1 — Versioned adapter An adapter (LoRA) is usable only when coupled with: (i) its exact base (name + version of the weights); (ii) its prompt template; (iii) its training data (hash); (iv) its hyperparameters (r, \alpha, target modules). The unit of versioning is not the .safetensors file but this quintuple — a LoRA on the “wrong” base (same architecture, different checkpoint) produces silently degraded outputs.

# Adapter registry: the record is the authority (MLflow / private HF Hub / simple CSV)
adapter:        faq-v3-lora
base:           meta-llama/Meta-Llama-3-8B-Instruct@9c6b4c1d   # exact hash
template:       prompts/faq_chat_v2.jinja                      # git version
data:           data/faq_2026.parquet @ sha256=4f2a...         # DVC
lora_config:    {r: 16, alpha: 32, target: [q_proj, v_proj]}
metrics:        {eval_v3_f1: 0.91, faithfulness: 0.88, judge_winrate: 0.56}
trained_by:     pipeline#2026-03-11, run_id 7c3e...
deployed:       canary 5% since 2026-03-13, SLO OK

7.1. The fine-tuning cycle in production

  1. Collect: feedback 👍/👎, expert corrections, questions without a good answer (failed queries from monitoring — ch. 5);
  2. Clean / deduplicate / anonymize: deduplication reduces memorization (cf. Explainability/Security module ch. 7);
  3. Build the pairs (SFT) then preferences (DPO) — balance of domains, slices evaluated separately (ch. 2);
  4. Train LoRA on the frozen base; log the quintuple;
  5. Qualify: golden set + judge + safety tests (fine-tuning can degrade refusals!) — gate of ch. 2;
  6. Deploy in canary with rollback (ch. 2.3);
  7. Measure the impact (winrate, cost, latency) before generalization — fine-tuning must win against simply improving the prompt and against RAG, otherwise it has no reason to exist.

Multi-LoRA serving Use case: a single 8B engine serves ten clients, each with its own LoRA (tone, domain, language). Modern servers load several adapters on a base shared in memory — a single copy of the weights, the \Delta W (a few tens of MB) being applied per request. The ops work consists of guaranteeing the routing (client header → adapter) and the isolation of evaluations per tenant (slices of ch. 2). The base rarely changes; the adapters often: two distinct deployment cadences in the same pipeline.

Proposition 7.2 — Size of a LoRA A rank-r LoRA on a layer W \in \mathbb{R}^{d_{\text{out}} \times d_{\text{in}}} stores B \in \mathbb{R}^{d_{\text{out}} \times r} and A \in \mathbb{R}^{r \times d_{\text{in}}}, i.e. r\,(d_{\text{out}} + d_{\text{in}}) parameters instead of d_{\text{out}} d_{\text{in}}. On the attention projections of an 8B (d = 4096, ≈ 7 targeted layers of the q/v type out of 32, r = 16): ~0.1% of the parameters — a few tens of MB in fp16. The storage saving is a bonus; the decisive saving is the training cost (no optimizer state on the frozen weights) and the deployment cadence (adapter hot-swap).

8. Agents in production: tracing and guardrails

Reminder — LLMs module ch. 8 (agents)

An agent = an LLM in a loop (observation → reasoning → action via tools), with memory and possibly multi-step planning. This chapter adds no intelligence: it adds observability, the budgets and the permissions without which an agent is undebuggable and dangerous.

8.1. Tracing: the tree of calls

An agent request unfolds in dozens of nested LLM and tool calls. The central datum is the trace: a tree of spans (one span per call: input, output, token cost, latency, model, attempt), OpenTelemetry-compliant — the vendors Langfuse/W&B Weave plug into it. Without a trace: no ability to answer “why did the agent send this email?”. With a trace: deterministic replay (by logging the seeds/times), bottleneck analysis (which tool dominates the latency?), per-step costs, and detection of behavioral anomalies (loops: same tool, same arguments, N times).

8.2. Guardrails: in layers, around the loop

Layer Mechanism Example
Input validation, injection classifiers, quota block 500 kB prompts, injection detector (Security module ch. 5-6)

Observation behavioral alerts loop rate, success per task, cost drift

Example 8.1 — The budget as the first guardrail A monitoring agent performs on average 6 LLM calls + 3 tool calls per task. A malicious user (or a booby-trapped document — indirect injection, cf. Security module ch. 5) can make it loop: each iteration re-injects a bit of context. Cap per task: steps ≤ 15, tokens ≤ 50 k, cost ≤ 0.10 € — and cut off cleanly (degraded answer: “I could not finish”): the failure becomes a bounded cost instead of a billing incident.

Proposition 8.2 — Per-task success collapses with length If each step succeeds independently with probability p, a task of k steps succeeds with p^k: p = 0.95 and k = 20 give 36%. Hence: (i) shorten the chains (more reliable tools, shallower plans); (ii) local retries and reflexivity; (iii) evaluate agents per complete task, never per step.

8.3. Evaluating an agent

Agent metrics: success rate per task (on scripted tasks with an initial state and a success criterion — e.g. “the ticket is created with the right fields”), average cost per task (tokens × price + tools), end-to-end P95 latency, human intervention rate. The evaluation environments must be replayable: simulated tools (mock Confluence, mock mail) for CI, a sampled real environment for production — the simulation runs hundreds of tasks for a few cents.

9. Operational security: secrets, sandbox, supply chain

Scope The attacks against the model (jailbreaks, injections, poisoning, extraction) are the subject of the M2 module Explainability, Security, Privacy of LLMs. Here: the security of the system around the model — the ops of an LLM application; the reference checklist of the field is the OWASP Top 10 for LLM Applications.

9.1. Secrets and identities

  • API keys, database passwords, index tokens: never in the code nor the images — a vault (Vault, Secret Manager) injected at startup; periodic rotation; repository scanners in CI (a secret committed = compromised, even “just on a branch”);
  • Each service has its identity (service account) and least privilege: the RAG engine does not need write access to the corpus; the agent does not need the credentials of the administrative database;
  • The outputs of the LLM are data, never instructions: a model’s response must never be evaluated/executed (eval, shell, SQL) without validation — the flaw class “the model generated the code, we execute it” is a special case of indirect injection (Security module ch. 5).

9.2. Sandbox and isolation

When the agent executes code (notebooks, “calculator” tools, plugins), execution must be confined: an ephemeral container, a temporary file system, outbound network blocked by default, CPU/RAM limits, a hardened runtime (e.g. gVisor/Firecracker for kernel-level isolation), and filtering of exfiltrations — including over slow channels (DNS queries, timing): an agent compromised by injection will try to exfiltrate via the only channel it was left (the tools! the mail! the displayed output?). Hence the duo permissions (ch. 8) + sandbox: the same principle as in system security — compromise is likely, blast radius minimal.

9.3. Supply chain

  • Model weights: downloaded from verified sources, sha256 fingerprint recorded in the registry (ch. 1) — an open-weight model is a dependency like a library, with “logical” CVEs (backdoors; cf. Security module ch. 5) and no automatic scanner;
  • Dependencies: lockfiles, SBOM, classic vulnerability scans in CI (same as any app);
  • Prompts and adapters: mandatory review — a prompt is code in disguise; a LoRA trained on unvalidated data is an opaque dependency;
  • Logs: the traces contain user text (personal data?) — limited retention, anonymization, controlled access; cf. Security module ch. 8-10 and the AI Act (ch. 10).

Why not GraphRAG? If the dominant usage becomes “which teams work on topic X?” (relational questions), the entity graph (Graph ML module ch. 11; GraphRAG of Edge et al.) becomes profitable despite its indexing cost: the answer to the question “do we need a graph?” is a measured trade-off (RAGAS eval + ablation), not a fad.

10.2. Green ops: measuring energy

The energy cost of LLMs concentrates (i) in pre-training — Patterson et al. (2021) formalize the carbon accounting of large trainings (consumption, regional electricity mix, PUE); Luccioni et al. (2022) do the same for BLOOM including the amortization of training; (ii) in aggregated inference — billions of requests of a few Wh each. For a developer, the useful unit is the consumption per request: measurable with CodeCarbon (CPU/GPU/PUE meter) around each serving point.

from codecarbon import EmissionsTracker

with EmissionsTracker(measure_power_secs=1, log_level="warning") as tracker:
    answer = rag_pipeline.answer(question)      # full request

print(f"{tracker.total_energy_kWh * 1000:.1f} Wh for this request",
      f"({tracker.total_emissions * 1e3:.1f} gCO2e on the local mix)")

Proposition 10.1 — The four green levers, in order of effectiveness (1) Functional sobriety: routing to small models, shorter outputs, cache (ch. 4) — divides the energy without touching the hardware; (2) Quantization: ~2-4× on the energy throughput per token (cf. LLMs ch. 6); (3) Batching: the same GPU delivers more tokens/Wh in batch (ch. 3 — the two propositions 4.1 and 10.1 are the same equation, in euros and in Wh); (4) Geographic and temporal scheduling: moving the nightly batches to the low-carbon-mix regions at the right moment. The order matters: one does not buy green GPUs before having shortened the outputs.
