Le constat fondateur. Un modèle qui atteint 92 % de F1 dans un notebook ne « marche » pas : il marche dans un environnement. Le papier fondateur du domaine (Sculley et al., NeurIPS 2015) montre que la dette technique du ML ne loge pas dans le modèle mais autour : pipelines de données, glue code, chaînes de dépendances, configurations, et feedback loops — le modèle en production influence les données qui serviront au réentraîner. 1. Cycle de vie : versionner données, features, modèles

Le cycle de vie ML s'étend bien au-delà de l'entraînement : collecte → labellisation → features → entraînement → évaluation → registre → déploiement → monitoring → (ré)entraînement. Chaque flèche de ce cycle est un artefact qu'il faut identifier de façon immuable, faute de quoi aucune métrique n'est reproductible — ni en debug, ni en audit, ni devant un client.

Définition 1.1 — Artefact et lineage Un artefact est tout objet produit ou consommé par le cycle : jeu de données, schéma de features, poids, tokenizer, template de prompt, index vectoriel, configuration, image conteneur. Le lineage est le graphe des dépendances artefact → artefact. Un entraînement est reproductible lorsque code + données + configuration + environnement sont tous identifiés par des empreintes (hashes) et rejouables.
Proposition 1.2 — La triple empreinte Un run d'entraînement n'est reproductible que si l'on sait rejouer le triplet \((\text{code}, \text{données}, \text{config})\). En pratique : git versionne le code (commit hash), DVC versionne les données et les poids (empreinte du contenu, le fichier vivant hors du dépôt), et params.yaml lie les deux. Toute métrique publiée référence les trois empreintes — sinon elle n'est pas une mesure, c'est une rumeur. 
# Donnees volumineuses versionnees par contenu (DVC) -- seul le pointeur entre dans git

1.1. Feature stores et registres

Pour le ML tabulaire, un feature store (p. ex. Feast) sert la même définition de feature en offline (entraînement, batch) et en online (serving, low-latency), éliminant le skew entraînement/inférence — la classe de bug la plus sournoise du ML industriel. Pour les LLMs, l'équivalent fonctionnel est double : la cache de prompts (préfixes partagés ; cf. ch. 4) et la banque d'embeddings du RAG (ch. 6), dont le schéma (type de chunk, modèle d'embedding, version de l'index) doit être géré comme une feature : identifiée, versionnée, rejouable.

Le registre de modèles (MLflow, ou répertoire hf_hub privatisé) enregistre pour chaque version : les empreintes du triplet, les métriques de qualification, la signature (entrées/sorties), et le statut (staging / production / archived). Un déploiement ne référence jamais « le dernier entraînement » mais une version figée du registre.

Spécificité LLM : les prompts et les évals sont des artefacts Dans une application LLM, trois familles d'artefacts s'ajoutent au triplet classique : (i) les templates de prompts (versionnés comme du code, avec tests — ch. 2) ; (ii) les jeux d'évaluation (golden sets question → réponse attendue / documents pertinents) ; (iii) les modèles d'embedding et index du RAG, couplés : changer de modèle d'embedding invalide tout l'index (ch. 6). 2. CI/CD pour le ML : tester données et modèles

L'intégration continue d'un système ML teste quatre couches, par ordre de coût croissant : le code, les données, le modèle, l'infrastructure. La règle d'or : faire échouer le pipeline le plus tôt possible, au niveau le moins cher.

2.1. Tests de données

Les données sont une interface comme une autre : on leur écrit des contrats. Un contrat de données vérifie : le schéma (types, colonnes, bornes), les invariants métier (valeurs nulles admises, plages), et des propriétés statistiques (taux de duplication, distribution d'une colonne clé). Outils : Pandera (contrats en Python, exécutés dans le pipeline), Great Expectations (suites de validations déclaratives), serveurs de qualité intégrés aux plateformes.

2.2. Tests de modèles — et de prompts

Définition 2.1 — Test de non-régression d'un modèle Soit un jeu de qualification \(D_{\text{qual}}\) fixé et une métrique \(m\) (F1, taux d'exactitude, taux de refus, coût moyen). Le candidat \(f_{\text{new}}\) remplace \(f_{\text{prod}}\) si \(m(f_{\text{new}}) \geq m(f_{\text{prod}}) - \tau\), où \(\tau\) est la marge de tolérance. Le point subtil : \(m\) est mesurée sur un échantillon — décider avec un écart mesuré nécessite de savoir quand il est significatif.
Proposition 2.2 — Seuil de décision par concentration (Hoeffding) Soit \(\ell\) une perte bornée dans \([0,1]\), mesurée sur \(n\) exemples i.i.d. Avec probabilité \(\geq 1-\delta\) (des deux côtés) : $$\bigl|\;\mathbb{E}[\ell] - \widehat{\ell}_n\;\bigr| \;\leq\; \sqrt{\frac{\log(2/\delta)}{2n}}.$$ Pour décider d'un rollback à \(\delta = 0{,}05\) sur \(n = 1000\) exemples, deux modèles dont les pertes diffèrent de moins de \(\sqrt{\log 40 / 2000} \approx 0{,}027\) ne sont pas distinguables : l'écart observé peut être du bruit d'échantillonnage.
La borne de Hoeffding (démontrée au module ML) s'applique aux \(n\) variables i.i.d. \(\ell_i \in [0,1]\) : \(\mathbb{P}\bigl(|\overline{\ell} - \mathbb{E}\ell| \geq t\bigr) \leq 2e^{-2nt^2}\). En égalant le membre droit à \(\delta\) on obtient \(t = \sqrt{\log(2/\delta)/(2n)}\). Pour la comparaison de deux modèles on l'applique à la variable \(\ell_{\text{new}} - \ell_{\text{prod}}\) (bornée dans \([-1,1]\), facteur 2 sur la plage — d'où un facteur 2 sous la racine). Avec \(n=1000\), \(\delta = 0{,}05\) et la version signée : \(t \approx 2{,}8\,‰\). ∎
Conséquence pratique Un « +0,4 % de F1 » mesuré sur 500 exemples ne prouve rien : l'intervalle de confiance à 95 % est de l'ordre de ±4 points pour une métrique à 50 %. Les gateways de CI doivent donc exiger un écart minimal (marge \(\tau\) et significativité), sous peine de « danser sur le bruit » — un rollback par-ci, un rollback par-là, et une dérive lente de la qualité.

Les tests de modèles se déclinent aussi en tranches (slices) : performance par langue, par longueur de contexte, par topic, par catégorie d'utilisateur — un agrégat global peut masquer une chute localisée (thématique de fairness, cf. module Emerging ML ch. 6). Pour un LLM, s'ajoutent des tests de prompts : format de sortie (JSON valide, schéma), garanties de refus (phrases interdites), enrobeurs de déterminisme (température 0, seed) et un juge LLM comme oracle (ch. 5) — le juge lui-même étant versionné et testé sur un golden set.

2.3. Livraison continue : canary et shadow

Le déploiement d'un composant ML est progressif : shadow (le nouveau modèle reçoit le trafic en double, sa sortie est journalisée mais non servie — zéro risque, coût double), canary (5 % du trafic, rollback automatique si les métriques de garde — latence, taux d'erreur, feedback négatif — se dégradent), puis généralisation. Le rollback doit être un seul bouton : la version précédente (poids + prompt + index) reste déployable en une commande, grâce au registre du ch. 1.

3. Serving des LLMs : batching continu, latence P99

Rappel — module LLMs ch. 6 (inférence)
Le décodage autorégressif génère un token par passe avant ; l'attention exige de retenir les clés/valeurs de tous les tokens passés (KV cache) ; la quantification réduit les poids et le KV ; la complexité par token croît avec la longueur de contexte. Le présent chapitre passe du « comment ça calcule » au « comment ça tient une charge ».

3.1. Le batching : d'une requête à N

Un GPU exécute un pas de décodage en un temps quasi indépendant du nombre de séquences présentes dans le batch (tant que la mémoire et le débit le permettent) : les opérations sont parallèles et le GPU est memory-bound sur les poids. Servir \(B\) séquences simultanément divise donc presque par \(B\) le coût par token — c'est l'argument économique du serving mutualisé. Le batching naïf (static batching) attend d'avoir \(B\) requêtes, les traite en bloc, et laisse les GPU inactifs dès qu'une séquence courte termine : or une requête de 20 tokens finit vite, et le batch devient clairsemé.

Définition 3.1 — Batching continu (Orca, OSDI 2022) Ordonnancer le serving au niveau de l'itération plutôt que de la requête : à chaque pas de décodage, les séquences terminées sortent du batch et des requêtes en attente y entrent. Le GPU ne chôme plus entre deux requêtes. Combiné au selective batching (opérations batchées là où c'est possible, boucles par requête ailleurs), Orca revendique jusqu'à 36,9× le débit de systèmes antérieurs à parité de latence. 
# Boucle de batching continu (simplifiée) -- le coeur de tout serveur LLM moderne

3.2. Mémoire : le KV cache et PagedAttention

Proposition 3.2 — Taille du KV cache Pour un transformer à \(L\) couches, \(h_{\text{kv}}\) têtes de clé/valeur (GQA) de dimension \(d_h\), en précision \(b\) octets, la cache d'une séquence de \(T\) tokens occupe : $$M_{\text{KV}} \;=\; 2 \cdot L \cdot h_{\text{kv}} \cdot d_h \cdot b \cdot T \;\text{octets}.$$ Exemple (Llama-3-8B : \(L=32\), \(h_{\text{kv}}=8\), \(d_h=128\), fp16 \(b=2\)) : \(2\times32\times8\times128\times2 = 131\,072\) octets ≈ 128 Kio par token, soit 1 Gio pour 8 192 tokens — davantage que certains modèles ne pèsent par bits de poids.
Comptage direct. Chaque couche \(l\) stocke, pour chaque token \(t\), une clé \(k_t^{(l)}\) et une valeur \(v_t^{(l)}\), chacune un vecteur de \(h_{\text{kv}} \cdot d_h\) coefficients (les têtes d'attention « requêtes » peuvent être plus nombreuses — GQA — mais seules les têtes K/V sont mises en cache). Chaque coefficient coûte \(b\) octets : par couche et par token, \(2\,h_{\text{kv}}d_h b\) octets ; multiplier par \(L\) couches et \(T\) tokens donne la formule. ∎

Le batching continu fait donc osciller l'occupation mémoire à chaque itération (entrées/sorties de séquences). Allouer le KV en bloc contigu maximal (longueur maximale de sortie réservée d'avance) gaspille : vLLM (SOSP 2023) traite le KV cache comme la mémoire virtuelle d'un OS — pages de 16 tokens, allouées à la demande, non contiguës, partageables entre séquences issues d'un même préfixe (prompt système partagé par des milliers de requêtes) : gaspillage réduit à ~4 % contre plus de 60 % pour l'allocation statique, débit 2-4× les systèmes antérieurs. Conséquence ops : la capacité réelle d'un serveur se mesure en « tokens de KV disponibles », pas en requêtes concurrentes.

3.3. Latence : TTFT, TPOT, P99

Définition 3.3 — SLO de serving LLM TTFT (time to first token) : délai requête → premier token — dominé par le pré-remplissage (prompt) et la file d'attente. TPOT (time per output token) : cadence de génération — dominée par le décodage et la contention du batch. P99: quantile à 99 % d'une distribution de latence — l'engagement contractuel pertinent ; la moyenne masque les files. Un SLO typique d'assistant interactif : TTFT P99 < 1,5 s, TPOT P99 < 80 ms/token.
Théorème 3.4 — Loi de Little Dans un système stable en régime permanent, avec \(L\) clients moyens présents, \(\lambda\) clients arrivant par seconde en moyenne et \(W\) temps de séjour moyen : $$L \;=\; \lambda\, W.$$ Corollaire serving : à cadence de génération imposée (\(W\) fixé par le nombre de tokens et le TPOT), le nombre de requêtes concurrentes supportées est \(L = \lambda W\) — la concurrence nécessaire croît linéairement avec le débit visé.
Preuve par argument de sortie (direct) . Sur un intervalle \([0, t]\), notons \(A(t)\) le nombre d'arrivées et \(D(t)\) le nombre de départs. La moyenne du nombre de clients présents s'écrit \(L_t = \frac{1}{t}\int_0^t N(u)\,du\), où \(N(u)\) = présents à l'instant \(u\). Chaque requête contribue à cette intégrale exactement son temps de séjour : \(\int_0^t N(u)\,du = \sum_{i \,\text{partie en } \leq t} W_i + \) (résidus des requêtes encore présentes). En divisant par \(t\) et en faisant \(t\to\infty\) (stabilité : \(A(t)/t \to \lambda\), les résidus bornés deviennent négligeables), on obtient \(L = \lambda\, W\) — l'argument ne requiert aucune hypothèse d'indépendance ni de distribution ; il est purement comptable. ∎
Débit contre latence : l'arbitrage du batch Augmenter \(B\) (batch cible) améliore le débit (coût/token amorti) mais allonge la file d'attente — donc le TTFT P99. Les serveurs modernes exposent ce compromis : max_num_seqs, budgets de tokens par pas, et politiques de préemption (recompute vs swap). Règle pratique : dimensionner le batch cible pour que l'occupation KV reste sous ~90 %, et laisser l'autoscaler (ch. 3.4) absorber les pics plutôt que de grossir le batch au-delà du SLO.

3.4. Autoscaling

Le signal pertinent pour scaler un serveur LLM n'est pas le CPU mais : la longueur de file d'attente (requêtes en attente d'admission), le temps d'attente moyen (TTFT − temps de pré-remplissage) et le taux d'occupation KV. L'autoscaling horizontal (HPA sur métrique personnalisée Prometheus) ajoute des réplicas ; attention aux pics de pré-chauffe (chargement des poids : dizaines de secondes à minutes — pré-tirer les images, ou payer le P99). Pour les modèles multi-GPU (tenseur parallèle ; cf. module Emerging ML ch. 2 sur le distribué), chaque réplica est un groupe de GPU ; scaler change la granularité du parallélisme, pas seulement le nombre de pods.

4. Coûts : euros par million de tokens

Toute décision d'architecture LLM se ramène tôt ou tard à un coût par million de tokens (Mt). Les API facturent séparément l'entrée (prompt : lecture amortissable par cache) et la sortie (génération : chère) ; les ordres de grandeur 2025-2026 couvrent grossièrement, du petit modèle open-weight au modèle de front, de quelques centimes à quelques dizaines d'euros par Mt — des tarifs qui changent plusieurs fois par an : toute chiffre précis dans un support de cours serait périmé ; la méthode de calcul, elle, demeure.

Proposition 4.1 — Coût unitaire d'un serving auto-hébergé Si un serveur délivre un débit soutenu de \(R\) tokens/s (sorties, batching continu) sur des GPU coûtant \(c\) €/h (location tout compris), le coût opérationnel par million de tokens de sortie vaut : $$\text{coût/Mt} \;=\; \frac{c}{R} \cdot \frac{10^6}{3600} \;\approx\; 278 \cdot \frac{c}{R} \;\; \text{€/Mt}.$$ Exemple : un 8B sur un GPU à ~2 €/h débitant \(R = 2\,000\) tokens/s en batch → ≈ 0,28 €/Mt ; le même GPU en requêtes isolées (batch 1, \(R \approx 60\)) → ≈ 9 €/Mt. Le batching est un facteur 30 sur la facture.
Le serveur produit \(R\) tokens par seconde, chaque heure facturée \(c\) € produit donc \(3600\,R\) tokens ; le coût par token est \(c/(3600\,R)\) €, et par million de tokens \(10^6 c/(3600 R) = 277{,}8\, c/R\). La division par \(R\) directe : doubler le débit divise le coût par token par deux, à matériel constant — c'est la justification économique du ch. 3. ∎

4.1. Les leviers d'économie

  • Cache de préfixe : prompt système + historique partagés → le pré-remplissage est facturé/consommé une fois ; côté API, la prompt caching réduit le coût d'entrée des préfixes répétés (souvent facturés avec décote) ; côté vLLM, le KV est réutilisé gratuitement.
  • Routage de modèles (cascade) : petit modèle d'abord, escalade vers le gros si le petit « n'est pas sûr » (score de confiance, accord de deux candidats, ou classeur). Décision séquentielle formalisée comme un bandit (cf. module RL ch. 6) : on arbitre coût vs qualité requête par requête.
  • Limite de sortie : la sortie coûte ~5-10× l'entrée ; contraindre max_tokens et le format (réponse en k points, JSON court) est le levier le plus sous-estimé.
  • Quantification (cf. LLMs ch. 6 ; Advanced Topics ch. 6) : 4 bits ≈ ×2-3 en débit sur les poids — et des GPU plus petits.
  • Traitement par lots différé : les tâches non interactives (classification d'archives) partent en batch nocturne ; certaines API facturent ces modes ~50 % moins cher.

5. Évaluation en production : drift et monitoring

5.1. Drift de données, drift de concept

Définition 5.1 — Dérives (drift) Dérive de données : la distribution des entrées change (\(P(X)\) bouge — nouveaux topics, nouvelle population d'utilisateurs, nouvelle source documentaire). Dérive de concept : la relation entrée → réponse juste change (\(P(Y\mid X)\) bouge — la « bonne » réponse d'hier devient fausse : réglementation, fusion d'entreprises, vocabulaire). Pour un RAG, une troisième dérive : le corpus change (ch. 6).
Proposition 5.2 — PSI = divergence de Jeffreys L'indice de stabilité de population (PSI), somme sur les bacs \(i\) d'un histogramme : $$\mathrm{PSI}(p, q) \;=\; \sum_i \bigl(p_i - q_i\bigr)\, \ln\frac{p_i}{q_i} \;=\; \mathrm{KL}(p \,\|\, q) + \mathrm{KL}(q \,\|\, p),$$ est exactement la divergence de Jeffreys : symétrique, nulle ssi \(p = q\). Seuils usuels en risque de crédit : PSI < 0,1 stable ; 0,1-0,25 à surveiller ; > 0,25 alerte.
Développons : \(\mathrm{KL}(p\|q) = \sum_i p_i \ln(p_i/q_i)\) et \(\mathrm{KL}(q\|p) = \sum_i q_i \ln(q_i/p_i)\). La somme vaut \(\sum_i (p_i - q_i)\ln(p_i/q_i)\) — précisément le PSI. Chaque terme est positif (les deux facteurs \(p_i - q_i\) et \(\ln(p_i/q_i)\) ont le même signe) ; nul si et seulement si \(p_i = q_i\) pour tout \(i\). La symétrie est évidente par la forme somme. ∎

Les détecteurs classiques : PSI/KL par feature (interprétable, bac par bac), test de Kolmogorov-Smirnov (comparaison de distributions continues, cf. Refresher Statistics), distance MMD (module ML), et détecteurs de flux (ADWIN) pour les signes en ligne. Pour un LLM, les « features » à surveiller sont : longueur de prompt, langue, topics (classifieur léger), présence de documents injectés, taux de troncature — et des proxy de sortie : taux de refus, taux de « je ne sais pas », longueur médiane de réponse, taux d'échec de parse JSON. Sans labels en ligne, on surveille des symptômes ; les vraies métriques viennent du feedback et de l'échantillonnage.

5.3. Le LLM-judge en CI et en production

Juge : comment, et avec quels biais Un modèle juge évalue des paires (question, réponse) selon une grille (fidélité au contexte, complétude, ton) ; Zheng et al. (MT-Bench, NeurIPS 2023) montrent un accord avec les humains > 80 % sur des tâches de conversation — mais avec des biais documentés : préférence pour la première position, pour les réponses longues, et auto-préférence (le juge favorise son propre style). Bonnes pratiques : ordre alterné, rubrique explicite, référence fournie, golden set humain pour étalonner le juge, version du juge figée en CI (ch. 1). Le juge est un capteur bruité — on l'utilise pour détecter les régressions, pas pour certifier. 
# Mini-judge de regression en CI : compare prod vs candidate sur le golden set
def judge_pair(question, ref, ans_prod, ans_cand, judge):
    rub = "Reponse attendue (reference) : {ref}\nA : {a}\nB : {b}\n" \
          "Laquelle est la plus fidele a la reference ? Reponds A, B ou EGAL."
    out = judge(f"Q: {question}\n" + rub.format(ref=ref, a=ans_prod, b=ans_cand))
    out_sw = judge(f"Q: {question}\n" + rub.format(ref=ref, a=ans_cand, b=ans_prod))
    pair = {out.strip()[:4], out_sw.strip()[:4]}      # ordre alterne anti-biais
    return "cand" if pair == {"A", "B"} else ("prod" if pair == {"B", "A"} else "egal")

6. RAG Ops : fraîcheur et évaluation continue

Rappel — module LLMs ch. 7 (RAG)
Pipeline : chunking → embeddings → index vectoriel → retrieval (hybride BM25 + dense, cf. NLP ch. 2 et 7) → reranking → génération conditionnée. Le présent chapitre traite ce pipeline comme un système de données avec contrats de fraîcheur et d'évaluation — pas comme une démo.

6.1. Indexation incrémentale et fraîcheur

Le corpus d'entreprise bouge : pages Confluence éditées, contrats signés, FAQ enrichies. L'index doit suivre avec un SLA de fraîcheur explicite (« un document publié est interrogeable sous 15 minutes »). Le pattern standard : change data capture (webhooks/API du dépôt documentaire) → file d'événements → upsert incrémental dans l'index, clé = (source, doc_id, version). Subtilités :

  • Idempotence : rejouer deux fois le même événement ne doit créer qu'un lot de vecteurs ; dédoublonner par clé, marquer les chunks obsolètes (soft delete) pour ne pas casser les liens des évaluations ;
  • Atomicité par document : les chunks d'un document v2 remplacent en bloc ceux de v1 (sinon le retrieval mélange les versions) ;
  • Couplage embeddings ↔ index : changer de modèle d'embedding exige de ré-embedder tout le corpus (les espaces sont incompatibles entre eux) ; dual-boot de l'index le temps de la migration, puis bascule — l'index est un artefact versionné au sens du ch. 1 ;
  • Fraîcheur ≠ reindexation totale : mesurer le coût (tokens de résumé, temps GPU) et viser l'incrémental partout où c'est possible.

6.2. Évaluer un RAG sans humain : RAGAS

Définition 6.1 — Métriques RAGAS (Es et al., 2023) Quatre métriques sans référence, calculées par décomposition LLM : faithfulness (chaque affirmation de la réponse est-elle attestée par le contexte ? — anti-hallucination), answer relevancy (la réponse répond-elle à la question ?), context precision (les chunks pertinents sont-ils bien classés devant ?) et context recall (les chunks nécessaires sont-ils retrouvés ? — nécessite une réponse de référence). Les deux dernières isolent le retrieval, les deux premières la génération : c'est la grille de diagnostic qui manque au F1 global. 
from ragas import evaluate

Lire un rapport RAGAS comme un ingénieur Recall bas, faithfulness haut : le retrieval rate — améliorer chunking, hybride, reranker. Recall haut, faithfulness bas : le modèle invente malgré le contexte — prompt, modèle plus fort, citation forcée. Relevancy basse : réponse hors-sujet ou verbeuse. Le piège des métriques sans référence : leur juge a les biais du ch. 5 — on les étalonne sur un échantillon annoté à la main avant d'en faire des seuils de CI.

6.3. Le graphe au secours du RAG

Le RAG vectoriel échoue sur les questions globales (« quels sont les thèmes récurrents des rapports 2025 ? ») qui exigent d'agréger le corpus entier ; GraphRAG (Edge et al., 2024 ; cf. module Graph ML ch. 11) construit un graphe d'entités (extraction LLM), le partitionne en communautés (Leiden) et résume chaque communauté — la réponse globale devient un map-reduce sur les résumés. Le coût ops : l'indexation LLM est chère (chaque document passe par des appels d'extraction), donc incrémentale par nécessité ; les communautés se recomputent périodiquement. Arbitrage (vectoriel vs graphique vs hybride) à inscrire dans la table d'ablation du système — et à re-mesurer à chaque migration de modèle (ch. 2).

7. Fine-tuning Ops : LoRA versionnés

Rappel — module LLMs ch. 4-5 : SFT, LoRA, DPO
Le fine-tuning par instructions (SFT) adapte le modèle ; LoRA (Hu et al., ICLR 2022) gèle les poids \(W\) et n'apprend que \(\Delta W = BA\) de rang \(r \ll d\) : quelques dizaines de Mo au lieu de Go, entraînables sur un seul GPU. DPO/RLHF (ch. 5) alignent ensuite les préférences.
Définition 7.1 — Adaptateur versionné Un adaptateur (LoRA) n'est utilisable que couplé à : (i) sa base exacte (nom + version des poids) ; (ii) son template de prompt ; (iii) ses données d'entraînement (hash) ; (iv) ses hyperparamètres (\(r\), \(\alpha\), modules cibles). L'unité de versioning n'est pas le fichier .safetensors mais ce quintuplet — un LoRA sur la « mauvaise » base (même architecture, autre checkpoint) produit des sorties silencieusement dégradées.

7.1. Le cycle fine-tuning en production

  1. Collecter : feedback 👍/👎, corrections d'experts, questions sans bonne réponse (requêtes échouées du monitoring — ch. 5) ;
  2. Nettoyer / dédoublonner / anonymiser : la déduplication réduit la mémorisation (cf. module Explainability/Security ch. 7) ;
  3. Construire les paires (SFT) puis préférences (DPO) — équilibre des domaines, tranches évaluées séparément (ch. 2) ;
  4. Entraîner LoRA sur la base figée ; jaloner le quintuplet ;
  5. Qualifier : golden set + juge + tests de sûreté (le fine-tuning peut dégrader les refus !) — gate du ch. 2 ;
  6. Déployer en canary avec rollback (ch. 2.3) ;
  7. Mesurer l'impact (winrate, coût, latence) avant généralisation — le fine-tuning doit gagner contre la simple amélioration du prompt et contre le RAG, sinon il n'a pas lieu d'être.
Serving multi-LoRA Cas d'usage : un même moteur 8B sert dix clients, chacun son LoRA (ton, métier, langue). Les serveurs modernes chargent plusieurs adaptateurs sur une base partagée en mémoire — une seule copie des poids, les \(\Delta W\) (quelques dizaines de Mo) étant per-request. L'ops consiste à garantir l'aiguillage (header client → adaptateur) et l'isolation des évaluations par locataire (tranches du ch. 2). La base bouge rarement ; les adaptateurs souvent : deux cadences de déploiement distinctes dans le même pipeline.
Proposition 7.2 — Taille d'un LoRA Un LoRA de rang \(r\) sur une couche \(W \in \mathbb{R}^{d_{\text{out}} \times d_{\text{in}}}\) stocke \(B \in \mathbb{R}^{d_{\text{out}} \times r}\) et \(A \in \mathbb{R}^{r \times d_{\text{in}}}\), soit \(r\,(d_{\text{out}} + d_{\text{in}})\) paramètres au lieu de \(d_{\text{out}} d_{\text{in}}\). Sur les projections d'attention d'un 8B (\(d = 4096\), \(\approx\) 7 couches ciblées type q/v sur 32, \(r = 16\)) : ~0,1 % des paramètres — quelques dizaines de Mo en fp16. L'économie de stockage est un bonus ; l'économie déterminante est le coût d'entraînement (pas d'optimiseur sur les poids gelés) et la cadence de déploiement (adapter hot-swap).

8. Agents en production : tracing et garde-fous

Rappel — module LLMs ch. 8 (agents)
Un agent = LLM dans une boucle (observation → raisonnement → action via outils), avec mémoire et éventuellement planification multi-étapes. Ce chapitre n'ajoute pas d'intelligence : il ajoute l'observabilité, les budgets et les permissions sans lesquels un agent est indébuggable et dangereux.

8.1. Tracing : l'arbre des appels

Une requête d'agent se déroule en dizaines d'appels LLM et d'outils imbriqués. La donnée centrale est la trace : un arbre de spans (un span par appel : entrée, sortie, coût en tokens, latence, modèle, tentative), conforme OpenTelemetry — les vendor Langfuse/W&B Weave s'y raccordent. Sans trace : aucune capacité à répondre « pourquoi l'agent a-t-il envoyé ce mail ? ». Avec trace : replay déterministe (en journalisant les graines/temps), analyse des goulets (quel outil domine la latence ?), des coûts par étape, et détection d'anomalies comportementales (boucles : même outil, mêmes arguments, N fois).

Exemple 8.1 — Le budget comme garde-fou premier Un agent de veille effectue en moyenne 6 appels LLM + 3 appels d'outil par tâche. Un utilisateur malveillant (ou un document piégé — injection indirecte, cf. module Sécurité ch. 5) peut le faire boucler : chaque itération ré-injecte un peu de contexte. Plafonner par tâche : étapes ≤ 15, tokens ≤ 50 k, coût ≤ 0,10 € — et couper proprement (réponse dégradée : « je n'ai pas pu terminer ») : la panne devient un coût borné au lieu d'un incident de facturation.
Proposition 8.2 — Le succès par tâche s'effondre avec la longueur Si chaque étape réussit indépendamment avec probabilité \(p\), une tâche de \(k\) étapes réussit avec \(p^k\) : \(p = 0{,}95\) et \(k = 20\) donnent 36 %. D'où : (i) raccourcir les chaînes (outils plus fiables, plans moins profonds) ; (ii) retries locaux et réflexivité ; (iii) évaluer les agents par tâche complète, jamais par étape.

8.3. Évaluer un agent

Métriques agents : taux de succès par tâche (sur des tâches scénarisées avec état initial et critère de réussite — p. ex. « le ticket est créé avec les bons champs »), coût moyen par tâche (tokens × tarif + outils), latence P95 de bout en bout, taux d'intervention humaine. Les environnements d'évaluation doivent être rejouables : outils simulés (mock du Confluence, du mail) pour la CI, environnement réel échantillonné pour la production — la simulation exécute des centaines de tâches pour quelques centimes.

9. Sécurité opérationnelle : secrets, sandbox, supply chain

Périmètre Les attaques contre le modèle (jailbreaks, injections, empoisonnement, extraction) sont le sujet du module M2 Explainability, Security, Privacy of LLMs. Ici : la sécurité du système autour du modèle — les ops d'une application LLM ; la checklist de référence du domaine est l'OWASP Top 10 for LLM Applications.

9.1. Secrets et identités

  • Clés d'API, mots de passe de base, tokens d'index : jamais dans le code ni les images — coffre-fort (Vault, Secret Manager) injecté au démarrage ; rotation périodique ; scanners de dépôt en CI (un secret commité = compromis, même « juste sur une branche ») ;
  • Chaque service a sa identité (service account) et le moindre privilège : le moteur RAG n'a pas besoin du droit d'écriture sur le corpus ; l'agent n'a pas besoin des credentials de la base administrative ;
  • Les sorties du LLM sont des données, jamais des instructions : la réponse d'un modèle ne doit jamais être évaluée/exécutée (eval, shell, SQL) sans validation — la classe de failles « le modèle a généré le code, on l'exécute » est un cas particulier d'injection indirecte (module Sécurité ch. 5).

9.2. Sandbox et isolation

Quand l'agent exécute du code (notebooks, tools « calculator », plugins), l'exécution doit être confinée : conteneur éphémère, système de fichiers temporaire, réseau sortant bloqué par défaut, limites CPU/RAM, runtime durci (p. ex. gVisor/Firecracker pour l'isolation à noyau), et filtrage des exfiltrations — y compris par canal lent (requêtes DNS, temporisation) : un agent compromis par injection tentera d'exfiltrer via le seul canal qu'on lui a laissé (les outils ! le mail ! la sortie affichée ?). D'où le duo permissions (ch. 8) + sandbox : même principe qu'en sécurité système — compromission probable, rayon d'action minimal.

9.3. Supply chain

  • Poids de modèles : téléchargés depuis des sources vérifiées, empreinte sha256 enregistrée dans le registre (ch. 1) — un modèle open-weight est une dépendance comme une librairie, avec CVE « logiques » (backdoors ; cf. module Sécurité ch. 5) sans scanner automatique ;
  • Dépendances : lockfiles, SBOM, scans de vulnérabilités classiques en CI (pareil que toute app) ;
  • Prompts et adaptateurs : review obligatoire — un prompt est du code déguisé ; un LoRA appris sur données non validées est une dépendance opaque ;
  • Journaux : les traces contiennent du texte utilisateur (données personnelles ?) — rétention limitée, anonymisation, accès contrôlé ; cf. module Sécurité ch. 8-10 et le AI Act (ch. 10).

10.2. Green ops : mesurer l'énergie

Le coût énergétique des LLMs se concentre (i) au pré-entraînement — Patterson et al. (2021) formalisent la comptabilité carbone des grands entraînements (consommation, mix électrique régional, PUE) ; Luccioni et al. (2022) font de même pour BLOOM y compris l'amortissement de l'entraînement ; (ii) à l'inférence agrégée — des milliards de requêtes de quelques Wh chacune. Pour un développeur, l'unité utile est la consommation par requête : mesurable avec CodeCarbon (compteur CPU/GPU/PUE) autour de chaque point de service.

from codecarbon import EmissionsTracker

with EmissionsTracker(measure_power_secs=1, log_level="warning") as tracker:
    answer = rag_pipeline.answer(question)      # requete complete

print(f"{tracker.total_energy_kWh * 1000:.1f} Wh pour cette requete",
      f"({tracker.total_emissions * 1e3:.1f} gCO2e au mix local)")
Proposition 10.1 — Les quatre leviers verts, par ordre d'efficacité (1) Sobriété fonctionnelle : routage vers de petits modèles, sorties plus courtes, cache (ch. 4) — divise l'énergie sans toucher au matériel ; (2) Quantification : ~2-4× sur le débit énergétique par token (cf. LLMs ch. 6) ; (3) Batching : le même GPU fait plus de tokens/Wh en batch (ch. 3 — les deux propositions 4.1 et 10.1 sont la même équation, en euros et en Wh) ; (4) Scheduling géographique et temporel : déporter les batchs nocturnes vers les régions à mix bas-carbone au moment opportun. L'ordre compte : on n'achète pas de GPU verts avant d'avoir raccourci les sorties.

Exercices / Labs

  1. Reproductibilité (ch. 1). Construire un mini-pipeline DVC (prepare → embed → eval) sur 100 documents ; modifier un seul document et prédire quels stages se ré-exécutent ; vérifier. Montrer qu'une métrique sans les trois empreintes n'est pas rejouable.
  2. Contrats de données (ch. 2). Écrire un schéma Pandera pour un jeu FAQ (question/réponse/langue/tokens) et faire échouer la CI sur : doublon exact, réponse vide, langue inconnue, longueur anormale. Ajouter le rapport d'erreur en artefact.
  3. Significativité d'un gate (ch. 2). Simuler deux modèles de pertes 0,30 et 0,31 sur n = 500 ; combien de fois le test « pas de régression » échoue-t-il à tort sur 100 tirages ? En déduire une marge minimale réaliste pour votre CI.
  4. Serving (ch. 3). Déployer un 8B en vLLM ; tracer les courbes TTFT P50/P99 et TPOT P99 pour une concurrence 1 → 256 ; localiser le point de rupture (occupation KV) ; comparer batch statique (faire varier) et batching continu.
  5. Loi de Little en pratique (ch. 3). À partir des traces du lab 4, estimer \(\lambda\), \(W\) et \(L\) sur une fenêtre de 10 minutes ; vérifier \(L = \lambda W\) à ±10 % ; expliquer l'écart (non-stationnarité, préemption).
  6. Comptabilité (ch. 4). Pour un workload donné (questions courtes, réponses 300 tokens, 10 k req/jour), chiffrer : API (entrée × tarif in, sortie × tarif out, cache de préfixe), self-hosted (proposition 4.1 avec R mesuré au lab 4). Identifier le point de bascule en requêtes/jour et sa sensibilité au taux d'utilisation.
  7. Drift (ch. 5). Générer deux semaines de « logs » simulés avec une dérive de topic au jour 9 ; implémenter PSI (prop. 5.2) et KS sur les longueurs et topics ; régler le seuil pour ≤ 1 fausse alerte par semaine ; documenter le compromis délai de détection / fausses alertes.
  8. RAG Ops (ch. 6). Reprendre le RAG du module LLMs ch. 7 : passer à l'indexation incrémentale (ajout de 20 documents à J+1 sans réindexation totale) ; mesurer RAGAS avant/après ; provoquer une migration d'embeddings et dérouler le dual-boot d'index.
  9. LoRA versionnés (ch. 7). Entraîner deux LoRA (r = 8, 32) sur le même jeu ; enregistrer les quintuplets ; servir les deux en multi-LoRA ; évaluer ; « oublier » volontairement la version de base et observer la dégradation silencieuse — puis ajouter le contrôle de compatibilité au registre.
  10. Agent observable (ch. 8). Instrumenter un agent recherche + rédaction avec spans OTel ; injecter trois pannes (outil qui timeout, boucle de relance, contexte trop long) ; diagnostiquer chacune uniquement via les traces ; ajouter budgets et plafonds, rejouer.
  11. Audit ops (ch. 9). Passer une mini-application LLM au crible de l'OWASP Top 10 LLM : lister les constats, sévérité, correctifs ; vérifier en particulier : secrets, permissions des outils, validation des sorties, rétention des logs.
  12. Lab fil rouge (ch. 10). Assembler l'assistant : RAG hybride + reranker + LoRA + garde-fous + dashboard (latence, PSI, RAGAS, coût/req, Wh/req via CodeCarbon) ; présenter un « post-mortem simulé » : une régression de faithfulness est injectée, l'équipe doit la détecter (dashboard ?) et rouler arrière (registre) en moins de 15 minutes.
