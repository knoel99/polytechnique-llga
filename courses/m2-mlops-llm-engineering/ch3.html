3. Serving des LLMs : batching continu, latence P99

Rappel — module LLMs ch. 6 (inférence)
Le décodage autorégressif génère un token par passe avant ; l'attention exige de retenir les clés/valeurs de tous les tokens passés (KV cache) ; la quantification réduit les poids et le KV ; la complexité par token croît avec la longueur de contexte. Le présent chapitre passe du « comment ça calcule » au « comment ça tient une charge ».

3.1 Le batching : d'une requête à N

Un GPU exécute un pas de décodage en un temps quasi indépendant du nombre de séquences présentes dans le batch (tant que la mémoire et le débit le permettent) : les opérations sont parallèles et le GPU est memory-bound sur les poids. Servir \(B\) séquences simultanément divise donc presque par \(B\) le coût par token — c'est l'argument économique du serving mutualisé. Le batching naïf (static batching) attend d'avoir \(B\) requêtes, les traite en bloc, et laisse les GPU inactifs dès qu'une séquence courte termine : or une requête de 20 tokens finit vite, et le batch devient clairsemé.

Définition 3.1 — Batching continu (Orca, OSDI 2022) Ordonnancer le serving au niveau de l'itération plutôt que de la requête : à chaque pas de décodage, les séquences terminées sortent du batch et des requêtes en attente y entrent. Le GPU ne chôme plus entre deux requêtes. Combiné au selective batching (opérations batchées là où c'est possible, boucles par requête ailleurs), Orca revendique jusqu'à 36,9× le débit de systèmes antérieurs à parité de latence. 
# Boucle de batching continu (simplifiée) -- le coeur de tout serveur LLM moderne
running, queue = [], deque()

def step():
    # 1) decodage : une iteration pour TOUTES les sequences actives (un seul appel GPU)
    outputs = model.forward_batch([s.tokens for s in running])
    # 2) on retire les sequences terminees (EOS ou longueur max)
    for s in [s for s in running if s.finished(outputs)]:
        running.remove(s); s.finalize()
    # 3) on admet de nouvelles requetes tant que la memoire KV le permet
    while queue and kv_pool.has_room(queue[0].prompt_len):
        running.append(queue.popleft().prefill())
    # 4) scheduling preemption : si le KV sature, on decharge (recompute/swap)

3.2 Mémoire : le KV cache et PagedAttention

Proposition 3.2 — Taille du KV cache Pour un transformer à \(L\) couches, \(h_{\text{kv}}\) têtes de clé/valeur (GQA) de dimension \(d_h\), en précision \(b\) octets, la cache d'une séquence de \(T\) tokens occupe : $$M_{\text{KV}} \;=\; 2 \cdot L \cdot h_{\text{kv}} \cdot d_h \cdot b \cdot T \;\text{octets}.$$ Exemple (Llama-3-8B : \(L=32\), \(h_{\text{kv}}=8\), \(d_h=128\), fp16 \(b=2\)) : \(2\times32\times8\times128\times2 = 131\,072\) octets ≈ 128 Kio par token, soit 1 Gio pour 8 192 tokens — davantage que certains modèles ne pèsent par bits de poids.
Comptage direct. Chaque couche \(l\) stocke, pour chaque token \(t\), une clé \(k_t^{(l)}\) et une valeur \(v_t^{(l)}\), chacune un vecteur de \(h_{\text{kv}} \cdot d_h\) coefficients (les têtes d'attention « requêtes » peuvent être plus nombreuses — GQA — mais seules les têtes K/V sont mises en cache). Chaque coefficient coûte \(b\) octets : par couche et par token, \(2\,h_{\text{kv}}d_h b\) octets ; multiplier par \(L\) couches et \(T\) tokens donne la formule. ∎

Le batching continu fait donc osciller l'occupation mémoire à chaque itération (entrées/sorties de séquences). Allouer le KV en bloc contigu maximal (longueur maximale de sortie réservée d'avance) gaspille : vLLM (SOSP 2023) traite le KV cache comme la mémoire virtuelle d'un OS — pages de 16 tokens, allouées à la demande, non contiguës, partageables entre séquences issues d'un même préfixe (prompt système partagé par des milliers de requêtes) : gaspillage réduit à ~4 % contre plus de 60 % pour l'allocation statique, débit 2-4× les systèmes antérieurs. Conséquence ops : la capacité réelle d'un serveur se mesure en « tokens de KV disponibles », pas en requêtes concurrentes.

3.3 Latence : TTFT, TPOT, P99

Définition 3.3 — SLO de serving LLM TTFT (time to first token) : délai requête → premier token — dominé par le pré-remplissage (prompt) et la file d'attente. TPOT (time per output token) : cadence de génération — dominée par le décodage et la contention du batch. P99: quantile à 99 % d'une distribution de latence — l'engagement contractuel pertinent ; la moyenne masque les files. Un SLO typique d'assistant interactif : TTFT P99 < 1,5 s, TPOT P99 < 80 ms/token.
Théorème 3.4 — Loi de Little Dans un système stable en régime permanent, avec \(L\) clients moyens présents, \(\lambda\) clients arrivant par seconde en moyenne et \(W\) temps de séjour moyen : $$L \;=\; \lambda\, W.$$ Corollaire serving : à cadence de génération imposée (\(W\) fixé par le nombre de tokens et le TPOT), le nombre de requêtes concurrentes supportées est \(L = \lambda W\) — la concurrence nécessaire croît linéairement avec le débit visé.
Preuve par argument de sortie (direct) . Sur un intervalle \([0, t]\), notons \(A(t)\) le nombre d'arrivées et \(D(t)\) le nombre de départs. La moyenne du nombre de clients présents s'écrit \(L_t = \frac{1}{t}\int_0^t N(u)\,du\), où \(N(u)\) = présents à l'instant \(u\). Chaque requête contribue à cette intégrale exactement son temps de séjour : \(\int_0^t N(u)\,du = \sum_{i \,\text{partie en } \leq t} W_i + \) (résidus des requêtes encore présentes). En divisant par \(t\) et en faisant \(t\to\infty\) (stabilité : \(A(t)/t \to \lambda\), les résidus bornés deviennent négligeables), on obtient \(L = \lambda\, W\) — l'argument ne requiert aucune hypothèse d'indépendance ni de distribution ; il est purement comptable. ∎
Débit contre latence : l'arbitrage du batch Augmenter \(B\) (batch cible) améliore le débit (coût/token amorti) mais allonge la file d'attente — donc le TTFT P99. Les serveurs modernes exposent ce compromis : max_num_seqs, budgets de tokens par pas, et politiques de préemption (recompute vs swap). Règle pratique : dimensionner le batch cible pour que l'occupation KV reste sous ~90 %, et laisser l'autoscaler (ch. 3.4) absorber les pics plutôt que de grossir le batch au-delà du SLO.

3.4 Autoscaling

Le signal pertinent pour scaler un serveur LLM n'est pas le CPU mais : la longueur de file d'attente (requêtes en attente d'admission), le temps d'attente moyen (TTFT − temps de pré-remplissage) et le taux d'occupation KV. L'autoscaling horizontal (HPA sur métrique personnalisée Prometheus) ajoute des réplicas ; attention aux pics de pré-chauffe (chargement des poids : dizaines de secondes à minutes — pré-tirer les images, ou payer le P99). Pour les modèles multi-GPU (tenseur parallèle ; cf. module Emerging ML ch. 2 sur le distribué), chaque réplica est un groupe de GPU ; scaler change la granularité du parallélisme, pas seulement le nombre de pods.

# Benchmark async : TTFT / TPOT P50-P99 en fonction de la concurrence
import asyncio, time, statistics, httpx

async def one(client, prompt, n_out=256):
    t0 = time.perf_counter(); first = None; n = 0
    async with client.stream("POST", "/v1/chat/completions",
            json={"model": "...", "messages": [{"role": "user", "content": prompt}],
                  "max_tokens": n_out, "stream": True}) as r:
        async for chunk in r.aiter_lines():
            if chunk.startswith("data:") and '"content"' in chunk:
                first = first or time.perf_counter() - t0   # TTFT
                n += 1
    return first, (time.perf_counter() - t0 - first) / n    # (TTFT, TPOT)

async def main(conc=64):
    async with httpx.AsyncClient(base_url="http://localhost:8000",
                                 timeout=300) as c:
        res = await asyncio.gather(*[one(c, "Resume ce rapport en 5 points.")
                                     for _ in range(conc)])
    p = lambda x, q: sorted(x)[int(q * len(x))]
    ttft = [r[0] for r in res]; tpot = [r[1] for r in res]
    print(f"conc={conc}  TTFT p50/p99 = {p(ttft,.5):.2f}/{p(ttft,.99):.2f}s"
          f"  TPOT p99 = {p(tpot,.99)*1e3:.0f}ms")

for conc in (1, 4, 16, 64, 256): asyncio.run(main(conc))
