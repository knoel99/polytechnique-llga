6. RAG Ops : fraîcheur et évaluation continue

Rappel — module LLMs ch. 7 (RAG)
Pipeline : chunking → embeddings → index vectoriel → retrieval (hybride BM25 + dense, cf. NLP ch. 2 et 7) → reranking → génération conditionnée. Le présent chapitre traite ce pipeline comme un système de données avec contrats de fraîcheur et d'évaluation — pas comme une démo.

6.1 Indexation incrémentale et fraîcheur

Le corpus d'entreprise bouge : pages Confluence éditées, contrats signés, FAQ enrichies. L'index doit suivre avec un SLA de fraîcheur explicite (« un document publié est interrogeable sous 15 minutes »). Le pattern standard : change data capture (webhooks/API du dépôt documentaire) → file d'événements → upsert incrémental dans l'index, clé = (source, doc_id, version). Subtilités :

  • Idempotence : rejouer deux fois le même événement ne doit créer qu'un lot de vecteurs ; dédoublonner par clé, marquer les chunks obsolètes (soft delete) pour ne pas casser les liens des évaluations ;
  • Atomicité par document : les chunks d'un document v2 remplacent en bloc ceux de v1 (sinon le retrieval mélange les versions) ;
  • Couplage embeddings ↔ index : changer de modèle d'embedding exige de ré-embedder tout le corpus (les espaces sont incompatibles entre eux) ; dual-boot de l'index le temps de la migration, puis bascule — l'index est un artefact versionné au sens du ch. 1 ;
  • Fraîcheur ≠ reindexation totale : mesurer le coût (tokens de résumé, temps GPU) et viser l'incrémental partout où c'est possible.

6.2 Évaluer un RAG sans humain : RAGAS

Définition 6.1 — Métriques RAGAS (Es et al., 2023) Quatre métriques sans référence, calculées par décomposition LLM : faithfulness (chaque affirmation de la réponse est-elle attestée par le contexte ? — anti-hallucination), answer relevancy (la réponse répond-elle à la question ?), context precision (les chunks pertinents sont-ils bien classés devant ?) et context recall (les chunks nécessaires sont-ils retrouvés ? — nécessite une réponse de référence). Les deux dernières isolent le retrieval, les deux premières la génération : c'est la grille de diagnostic qui manque au F1 global. 
from ragas import evaluate
from ragas.metrics import (faithfulness, answer_relevancy,
                           context_precision, context_recall)
from datasets import Dataset

ds = Dataset.from_dict({
    "question":     q_list,          # golden set (ch. 1 : versionne ce jeu !)
    "answer":       answers,         # sorties du pipeline candidat
    "contexts":     retrieved_chunks,
    "ground_truth": ref_answers,     # pour context_recall
})
report = evaluate(ds, metrics=[faithfulness, answer_relevancy,
                               context_precision, context_recall])
# gate CI : faithfulness >= 0.85 ; panneau hebdo : les 4 series temporelles
Lire un rapport RAGAS comme un ingénieur Recall bas, faithfulness haut : le retrieval rate — améliorer chunking, hybride, reranker. Recall haut, faithfulness bas : le modèle invente malgré le contexte — prompt, modèle plus fort, citation forcée. Relevancy basse : réponse hors-sujet ou verbeuse. Le piège des métriques sans référence : leur juge a les biais du ch. 5 — on les étalonne sur un échantillon annoté à la main avant d'en faire des seuils de CI.

6.3 Le graphe au secours du RAG

Le RAG vectoriel échoue sur les questions globales (« quels sont les thèmes récurrents des rapports 2025 ? ») qui exigent d'agréger le corpus entier ; GraphRAG (Edge et al., 2024 ; cf. module Graph ML ch. 11) construit un graphe d'entités (extraction LLM), le partitionne en communautés (Leiden) et résume chaque communauté — la réponse globale devient un map-reduce sur les résumés. Le coût ops : l'indexation LLM est chère (chaque document passe par des appels d'extraction), donc incrémentale par nécessité ; les communautés se recomputent périodiquement. Arbitrage (vectoriel vs graphique vs hybride) à inscrire dans la table d'ablation du système — et à re-mesurer à chaque migration de modèle (ch. 2).
