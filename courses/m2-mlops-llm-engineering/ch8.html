8. Agents en production : tracing et garde-fous

Rappel — module LLMs ch. 8 (agents)
Un agent = LLM dans une boucle (observation → raisonnement → action via outils), avec mémoire et éventuellement planification multi-étapes. Ce chapitre n'ajoute pas d'intelligence : il ajoute l'observabilité, les budgets et les permissions sans lesquels un agent est indébuggable et dangereux.

8.1 Tracing : l'arbre des appels

Une requête d'agent se déroule en dizaines d'appels LLM et d'outils imbriqués. La donnée centrale est la trace : un arbre de spans (un span par appel : entrée, sortie, coût en tokens, latence, modèle, tentative), conforme OpenTelemetry — les vendor Langfuse/W&B Weave s'y raccordent. Sans trace : aucune capacité à répondre « pourquoi l'agent a-t-il envoyé ce mail ? ». Avec trace : replay déterministe (en journalisant les graines/temps), analyse des goulets (quel outil domine la latence ?), des coûts par étape, et détection d'anomalies comportementales (boucles : même outil, mêmes arguments, N fois).

Exemple 8.1 — Le budget comme garde-fou premier Un agent de veille effectue en moyenne 6 appels LLM + 3 appels d'outil par tâche. Un utilisateur malveillant (ou un document piégé — injection indirecte, cf. module Sécurité ch. 5) peut le faire boucler : chaque itération ré-injecte un peu de contexte. Plafonner par tâche : étapes ≤ 15, tokens ≤ 50 k, coût ≤ 0,10 € — et couper proprement (réponse dégradée : « je n'ai pas pu terminer ») : la panne devient un coût borné au lieu d'un incident de facturation.
Proposition 8.2 — Le succès par tâche s'effondre avec la longueur Si chaque étape réussit indépendamment avec probabilité \(p\), une tâche de \(k\) étapes réussit avec \(p^k\) : \(p = 0{,}95\) et \(k = 20\) donnent 36 %. D'où : (i) raccourcir les chaînes (outils plus fiables, plans moins profonds) ; (ii) retries locaux et réflexivité ; (iii) évaluer les agents par tâche complète, jamais par étape.

8.3 Évaluer un agent

Métriques agents : taux de succès par tâche (sur des tâches scénarisées avec état initial et critère de réussite — p. ex. « le ticket est créé avec les bons champs »), coût moyen par tâche (tokens × tarif + outils), latence P95 de bout en bout, taux d'intervention humaine. Les environnements d'évaluation doivent être rejouables : outils simulés (mock du Confluence, du mail) pour la CI, environnement réel échantillonné pour la production — la simulation exécute des centaines de tâches pour quelques centimes.
