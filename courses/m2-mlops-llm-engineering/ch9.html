9. Sécurité opérationnelle : secrets, sandbox, supply chain

Périmètre Les attaques contre le modèle (jailbreaks, injections, empoisonnement, extraction) sont le sujet du module M2 Explainability, Security, Privacy of LLMs. Ici : la sécurité du système autour du modèle — les ops d'une application LLM ; la checklist de référence du domaine est l'OWASP Top 10 for LLM Applications.

9.1 Secrets et identités

  • Clés d'API, mots de passe de base, tokens d'index : jamais dans le code ni les images — coffre-fort (Vault, Secret Manager) injecté au démarrage ; rotation périodique ; scanners de dépôt en CI (un secret commité = compromis, même « juste sur une branche ») ;
  • Chaque service a sa identité (service account) et le moindre privilège : le moteur RAG n'a pas besoin du droit d'écriture sur le corpus ; l'agent n'a pas besoin des credentials de la base administrative ;
  • Les sorties du LLM sont des données, jamais des instructions : la réponse d'un modèle ne doit jamais être évaluée/exécutée (eval, shell, SQL) sans validation — la classe de failles « le modèle a généré le code, on l'exécute » est un cas particulier d'injection indirecte (module Sécurité ch. 5).

9.2 Sandbox et isolation

Quand l'agent exécute du code (notebooks, tools « calculator », plugins), l'exécution doit être confinée : conteneur éphémère, système de fichiers temporaire, réseau sortant bloqué par défaut, limites CPU/RAM, runtime durci (p. ex. gVisor/Firecracker pour l'isolation à noyau), et filtrage des exfiltrations — y compris par canal lent (requêtes DNS, temporisation) : un agent compromis par injection tentera d'exfiltrer via le seul canal qu'on lui a laissé (les outils ! le mail ! la sortie affichée ?). D'où le duo permissions (ch. 8) + sandbox : même principe qu'en sécurité système — compromission probable, rayon d'action minimal.

9.3 Supply chain

  • Poids de modèles : téléchargés depuis des sources vérifiées, empreinte sha256 enregistrée dans le registre (ch. 1) — un modèle open-weight est une dépendance comme une librairie, avec CVE « logiques » (backdoors ; cf. module Sécurité ch. 5) sans scanner automatique ;
  • Dépendances : lockfiles, SBOM, scans de vulnérabilités classiques en CI (pareil que toute app) ;
  • Prompts et adaptateurs : review obligatoire — un prompt est du code déguisé ; un LoRA appris sur données non validées est une dépendance opaque ;
  • Journaux : les traces contiennent du texte utilisateur (données personnelles ?) — rétention limitée, anonymisation, accès contrôlé ; cf. module Sécurité ch. 8-10 et le AI Act (ch. 10).
