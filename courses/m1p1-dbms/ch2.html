2. SQL : requêtes, agrégats, fenêtrage

SQL est un langage déclaratif : on décrit le résultat, pas l'algorithme. Sa sémantique logique se comprend en trois temps, qu'il faut connaître pour prédire ce qu'une requête renvoie — et que tout optimiseur réécrit à sa manière (ch. 8) : le FROM produit le produit cartésien/jointures, le WHERE sélectionne ligne à ligne, puis le GROUP BY + SELECT regroupent, agrègent et projettent.

Définition 2.1 — Sémantique du bloc de base La requête SELECT [DISTINCT] L FROM R1, …, Rk WHERE p renvoie $$\pi_L\big(\sigma_p(R_1 \times \cdots \times R_k)\big)$$ (multiensemble si DISTINCT est absent, ensemble sinon). Une sous-requête est une requête imbriquée ; IN et EXISTS correspondent à des semi-jointures : WHERE EXISTS (SELECT …) teste la non-vide-té de la réponse, ce qui permet notamment d'exprimer des différences avec NOT EXISTS.
Proposition 2.2 — Traduction des quantificateurs « Les \(x\) tels que \(\forall y \in S,\; \theta(x,y)\) » se traduit en SQL par anti-jointure : … WHERE NOT EXISTS (SELECT 1 FROM S WHERE NOT θ). « Il existe » est un simple EXISTS. Cette double négation est l'héritage direct du fait que SQL n'a pas de quantificateur universel — et de la propriété 1.7 : la division du ch. 1 n'existe pas comme opérateur, elle se programme.
Définition 2.3 — Agrégats et clause HAVING Une requête avec GROUP BY g partitionne les lignes sélectionnées selon les valeurs de \(g\), et chaque groupe produit une ligne : le SELECT ne peut plus mentionner que \(g\) et des agrégats. La clause HAVING filtre les groupes (après agrégation), là où WHERE filtre les lignes (avant) : $$\pi_{g,f}\big({}_g\gamma_f( \sigma_p(R))\big) \;=\; \texttt{SELECT g, f(a) … WHERE p GROUP BY g HAVING q(f)}.$$

Les fenêtres, normalisées en 2003, sont aujourd'hui l'outil standard du top-\(k\) par groupe, des cumuls (running sums via ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) et des comparaisons inter-périodes.
Définition 2.5 — NULL et logique trivaluée SQL distingue « valeur inconnue » (NULL) des valeurs réelles. Toute comparaison avec NULL renvoie UNKNOWN, et WHERE ne garde que les lignes TRUE — les UNKNOWN sont éliminés silencieusement. Les tables de vérité s'étendent naturellement :
ETTUF
TTUF
UUUF
FFFF
Conséquence piège : NOT (a = 1) n'est pas a != 1 si a peut être NULL ; il faut a IS DISTINCT FROM 1 (SQL :1999) ou un OR a IS NULL explicite. Les agrégats ignorent les NULL (AVG divise par le nombre de non-NULL), et COUNT(*) les compte — deux COUNT qui diffèrent sont le symptôme classique de données incomplètes.
Définition 2.6 — Récursion : WITH RECURSIVE SQL :1999 a comblé la limite du théorème 1.7 : une CTE récursive WITH RECURSIVE T AS (base UNION ALL SELECT … FROM T …) calcule le plus petit point fixe de l'équation : on part de la requête base, on itère la partie récursive jusqu'à ne plus produire de nouveaux tuples. C'est exactement une fermeture transitive : les SGBD en font un graphe-de-données semi-naïf (réécriture « delta » qui ne réévalue que les tuples nouveaux), et le ch. 9 retrouvera cette sémantique de point fixe pour interroger les graphes de connaissances.
Exemple 2.7 — Ancêtres dans un arbre en SQLite 
-- graphe orienté parent(y, x) : y est parent de x
WITH RECURSIVE ancetre(a, d) AS (          -- a ancêtre de d
  SELECT parent, enfant FROM parent
  UNION                                    -- UNION (sans ALL) = dédupliqué
  SELECT p.parent, a.d
  FROM ancetre a JOIN parent p ON p.enfant = a.a
)
SELECT d, COUNT(DISTINCT a) AS nb_ancetres FROM ancetre GROUP BY d;
-- sémantique : point fixe ; à chaque itération, on ne développe
-- que les tuples produits à l'itération précédente (évaluation semi-naïve).
Exemple 2.8 — SQLite et SQLAlchemy en Python 
import sqlite3
from sqlalchemy import create_engine, MetaData, Table, Column, Integer, String, ForeignKey, select

# --- 1. SQLite : tout est dans un fichier, transactions ACID incluses
con = sqlite3.connect("scolarite.db")
con.execute("PRAGMA foreign_keys = ON")        # optionnel mais recommandé
con.executescript("""
CREATE TABLE IF NOT EXISTS etudiant(
  nb INTEGER PRIMARY KEY, nom TEXT NOT NULL, majeure TEXT);
CREATE TABLE IF NOT EXISTS cours(
  code TEXT PRIMARY KEY, intitule TEXT, credits INTEGER CHECK (credits > 0));
CREATE TABLE IF NOT EXISTS inscrit(
  nb INTEGER REFERENCES etudiant(nb),
  code TEXT REFERENCES cours(code),
  annee INTEGER, PRIMARY KEY (nb, code));
""")
con.executemany("INSERT OR IGNORE INTO etudiant VALUES (?,?,?)",
                [(1043, "Anna", "DS"), (1088, "Bruno", "IA"), (2101, "Chloé", "DS")])

# moyenne par étudiant, avec fenêtre pour classer les cours de chacun
q = """
SELECT e.nom, c.intitule, i.annee,
       RANK() OVER (PARTITION BY e.nb ORDER BY i.annee) AS rang_annee,
       COUNT(*) OVER (PARTITION BY e.nb)                AS nb_cours
FROM inscrit i
JOIN etudiant e ON e.nb = i.nb
JOIN cours    c ON c.code = i.code
WHERE c.credits >= 3
"""
for row in con.execute(q):
    print(row)

# transaction explicite : tout ou rien
try:
    con.execute("BEGIN")
    con.execute("UPDATE etudiant SET majeure='IA' WHERE nb=2101")
    con.execute("INSERT INTO inscrit VALUES (2101, 'DB', 2026)")
    con.commit()
except sqlite3.IntegrityError as err:        # ex. clé étrangère violée
    con.rollback()
    print("annulé :", err)

# plan d'exécution (utile au ch. 8) :
for row in con.execute("EXPLAIN QUERY PLAN " + q):
    print(row)

# --- 2. SQLAlchemy Core : requêtes composables, indépendantes du SGBD
engine = create_engine("sqlite:///scolarite.db", echo=False)
md = MetaData()
etudiant = Table("etudiant", md, Column("nb", Integer, primary_key=True),
                 Column("nom", String), Column("majeure", String))
inscrit   = Table("inscrit", md, Column("nb", Integer, ForeignKey("etudiant.nb"),
                 primary_key=True), Column("code", String, primary_key=True),
                 Column("annee", Integer))
with engine.connect() as cn:
    stmt = (select(etudiant.c.nom, inscrit.c.code)
            .join(inscrit, etudiant.c.nb == inscrit.c.nb)
            .where(inscrit.c.annee == 2025).order_by(etudiant.c.nom))
    print(cn.execute(stmt).fetchall())
Note — Vues et contraintes Une vue est une requête nommée et stockée, réutilisée comme une table (réévaluée ou matérialisée selon le moteur) : une abstraction au même titre qu'une fonction. Les contraintes (PRIMARY KEY, FOREIGN KEY, CHECK, UNIQUE, NOT NULL) sont vérifiées à chaque écriture : repousser la validation après chargement (approche « data lake » du ch. 10) déplace le coût, ne le supprime pas.
