7. Agents autonomes à l'ère des LLMs

Définition 7.1 — POMDP : quand l'état n'est pas observable Un POMDP est un tuple \((\mathcal{S}, \mathcal{A}, \mathcal{O}, P, \Omega, r, \gamma)\) : comme un MDP, mais l'agent n'observe que \(O_t \sim \Omega(\cdot \mid S_{t+1}, A_t)\) — pas l'état latent. L'objet central est la croyance \(b_t(s) = \mathbb{P}[S_t = s \mid O_1, \dots, O_t, A_1, \dots, A_{t-1}]\), qui se met à jour par Bayes à chaque observation. Résultat fondamental : le POMDP se réécrit comme un MDP sur l'espace (continu) des croyances, de récompense \(\bar r(b, a) = \sum_s b(s) r(s, a)\) — optimalité préservée, mais espace d'états continu et problème PSPACE-dur en général. Tout agent réel est un POMDP : la perception est toujours partielle (capteurs bruités, écran, texte).
  • Définir un agent : percevoir → décider → agir → observer, en boucle (l'agent = politique \(\pi\) sur un POMDP) ; perception = contexte (texte, mémoire), action = tool calls, API, code. La mémoire/estimation d'état du POMDP se matérialise par : fenêtre de contexte (mémoire à court terme — bornée), mémoires vectorielles (récupération par similarité = estimation de croyance approximative), réseaux récurrents/état caché (littéralement un filtre appris) ;
  • LLM + outils : le LLM est le moteur de décision ; le « prompt » = observation ; function calling = espace d'actions. La boucle ReAct (Yao et al., 2023) alterne raisonnement explicite et actions :
# Trace ReAct (extrait, traduit) — question : "Le prix de l'action X a-t-il
# augmente apres le dernier produit phare du fournisseur Y ?"
Thought: Je dois identifier le dernier produit phare de Y, puis la date de
  sortie, puis comparer le cours de X autour de cette date.
Action: search[produits recents de Y]
Observation: Y a lance le produit P le 14 mars 2026.
Thought: Je cherche maintenant le cours de X autour du 14 mars 2026.
Action: lookup[cours de l'action X mars 2026]
Observation: X cote 102,4 le 13 mars ; 109,9 le 15 mars.
Thought: J'ai les deux donnees, je peux conclure (+7,3% en deux seances).
Action: finish[oui, en hausse de ~7%]

Le format function calling / tool use déclare l'espace d'actions (structuration JSON, schémas validés) :

{
  "name": "get_stock_price",
  "description": "Cours de cloture d'une action",
  "parameters": {
    "type": "object",
    "properties": {
      "ticker": {"type": "string"},
      "date":   {"type": "string", "format": "date"}
    },
    "required": ["ticker"]
  }
}
// reponse de l'agent : {"ticker": "X", "date": "2026-03-15"}
// -> l'orchestrateur execute, reinjecte le resultat comme observation
  • Mémoire et RAG : l'état dépasse la fenêtre de contexte ⇒ mémoire externe (vector stores). GraphRAG : indexer les connaissances en graphe (entités-relations) et requêter par voisinage/multi-sauts — la récupération devient une requête sur graphe de connaissances ; intersection exacte du master : NLP × Graph ML × LLM (cf. module Graph Machine and Deep Learning for Generative AI, chapitre 8, et module NLP pour la génération conditionnée par récupération) ;
  • Multi-agents : systèmes d'agents = graphes — nœuds : agents spécialisés (contexte et prompt propres), arêtes : flux d'information, topologie DAG ou cyclique (orchestrateur-travailleurs, débats, vérificateurs). Le self-play (l'agent apprend contre lui-même — AlphaGo/AlphaZero, Silver et al.) est la version entraînement ; les équipes d'agents LLM (générateur/critique/vérificateur) en sont la version inférence. Les workflows « deep research » actuels orchestrent >100 agents en phases parallèles ; ce « graph engineering » est l'un des débouchés du master (cf. LangGraph, AutoGen) ; l'orchestration est elle-même une politique — un méta-niveau sequential decision (renvoi chapitre 4) ;
  • Distribution, robustesse, confidentialité des systèmes multi-agents : quand les travailleurs sont répartis (ou malveillants), l'agrégation de leurs sorties pose les mêmes questions que l'agrégation de gradients — cf. module Emerging Subjects in ML, chapitres 2 (distribué) et 4 (byzantin) ;
  • Évaluation des agents : environnements (benchmarks tool-use), récompenses vérifiables (programmes de test, contraintes formelles — lien RLVR, chapitre 6), coûts (tokens, appels, latence — un agent = un MDP dont chaque pas coûte cher : optimiser le retour par token) ;
  • Sûreté : permissions par outil (liste blanche d'actions autorisées = restriction de l'espace d'actions), sandboxing d'exécution (code, réseau), supervision humaine aux points critiques (human-in-the-loop = politique avec interruption), journalisation complète des trajectoires pour audit.
TP fil rouge Coder un mini-agent « deep research » : un orchestrateur (LLM) qui décompose une question en sous-tâches, des travailleurs qui cherchent et résumment, un vérificateur qui exige des sources, un rédacteur qui compile — le tout représenté et exécuté comme un DAG d'agents (cf. Refresher CS, tri topologique) ; mesurer taux de réussite, coût en tokens, profondeur du DAG.
