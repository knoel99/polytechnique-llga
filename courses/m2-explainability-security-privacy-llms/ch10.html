10. Évaluer la sûreté : red teaming, AI Act

10.1 Red teaming : attaquer son propre système, méthodiquement

Définition 10.1 — Red team Équipe mandatée pour attaquer un système (modèle + application) selon un protocole : politique de contenu à violer → hypothèses d'attaque (taxonomie du ch. 5) → suites d'attaques (humaines et automatisées) → mesure (ASR par famille, sévérité, rayon d'action) → corrections et suite de régression (les attaques qui ont marché deviennent des tests de CI — cf. module ML Ops ch. 2).

Deux résultats pivots : Ganguli et al. (2022) décrivent le programme Anthropic — red team humain dès la conception, attaques automatisées ciblées, trouvent des « jailbreaks » inédits ; Perez et al. (2022) font attaquer le modèle par un autre modèle (RL : le attaquant est récompensé quand la cible produit du contenu interdit) — scaling : de plus gros attaquants trouvent plus d'attaques, transférables. Le red teaming devient une boucle d'entraînement : les échecs alimentent les données de préférence pour durcir l'alignement (ch. 6), qui re-red-teamé — le cycle ne s'arrête jamais, il se stabilise.

Mesurer sans se mentir Rapporter « ASR = 0 % sur 50 attaques » est un intervalle de confiance de ±[0-7] % (rule of three) : sans volume, l'absence d'échec n'est pas une absence de vulnérabilité. Rapporter les attaques adaptatives (ch. 6, prop. 6.2), la sévérité pire-cas, et le rayon d'action autorisé par les permissions — trois nombres plus honnêtes qu'un ASR unique.

10.2 Le cadre réglementaire : AI Act

Le règlement (UE) 2024/1689 (« AI Act ») organise l'IA par niveaux de risque : inacceptable (interdit : notation sociale, manipulation subliminale…), haut risque (exigences lourdes : gestion du risque, données, documentation, supervision humaine), risque limité (transparence), minimal. Points clés pour un LLM :

  • Modèles à usage général (GPAI) : obligations de transparence technique (documentation, politique de respect du droit d'auteur, résumé des données d'entraînement) ; pour les modèles présentant un risque systémique (seuil de capacité) : évaluations, atténuation, signalement d'incidents ;
  • Transparence des contenus : interaction avec une IA à divulguer ; contenus générés (profonds, « deepfakes ») à marquer lisible-machine — le watermarking (ch. 9) devient un outil de conformité ;
  • Calendrier : entrée en vigueur août 2024, montée en charge progressive des obligations jusqu'à 2026-2027 (interdictions et GPAI d'abord, haut risque ensuite) ;
  • Complémentaire : NIST AI RMF (govern / map / measure / manage) — la grille opérationnelle ; ISO/IEC 42001 (management) ; RGPD pour les traitements de données ; les codes de conduite sectoriels.
Proposition 10.2 — La conformité est un pipeline ML Ops Chaque exigence du AI Act/NIST se matérialise en artefacts du module ML Ops : registres de données et de modèles (traçabilité), évaluations versionnées (y compris sûreté : suites de red team en CI), monitoring et incident response (signalement), documentation générée du pipeline. La « gouvernance » sans l'ingénierie des chapitres 5-9 de ce module serait un dossier vide ; l'ingénierie sans gouvernance, une pile de logs illisible. Le loop : politique → threat model → défenses → éval → audit → politique.
Position LLGA Ce module est le volet « confiance » du master : il consomme les briques du module ML Ops (éval, monitoring, registres) et prépare le séminaire Advanced Topics (module suivant), où les questions d'alignement et d'évaluation à l'échelle sont des sujets de recherche ouverts. Les enseignants de ce cours proposé ne sont pas confirmés : les standards (AI Act, NIST, OWASP) et les papiers cités constituent le socle ; le groupe LLGA (LLMs & Graphs) de l'X y contribue quand c'est pertinent.
