10. Entraîner en pratique

Un réseau qui n'apprend pas a presque toujours un bug banal. Ce chapitre est le protocole de diagnostic que nous appliquerons en TP, dans l'ordre où il faut l'appliquer.

10.1 La recette d'entraînement, dans l'ordre

  1. Sanity check des formes : une passe avant sans erreur, les dimensions de chaque activation vérifiées (règle du ch. 0 : les gradients ont la forme de leur variable).
  2. Overfit un seul batch : 32 exemples, entraîner jusqu'à perte \(\approx 0\). Si le modèle n'y arrive pas, le bug est structurel (données, perte, initialisation, learning rate aberrant) — inutile d'entraîner plus. Un modèle incapable de mémoriser 32 exemples est cassé ou trop petit ; c'est LE test qui évite des semaines d'erreur silencieuse.
  3. LR range test (Smith, 2015) : \(\eta\) croissant géométriquement de \(10^{-7}\) à \(10^{0}\), tracer la perte : plateau → descente → divergence. Prendre le \(\eta\) du creux (ou un peu avant), c'est le réglage d'AdamW/SGD en une époque.
  4. Petit entraînement complet sur ~10 % des données, avec les courbes train/val : vérifier que la dynamique est saine avant de scaler.
  5. Scaling + régularisation : batch plus grand (ou gradient accumulation), précision mixte, data augmentation, dropout, weight decay — dans cet ordre de rentabilité (ch. 3).
  6. Checkpointing: sauver régulièrement (poids + état de l'optimiseur + pas courant + seed du générateur de données), pour reprendre exactement.

10.3 GPU : les leviers qui comptent

  • Précision mixte (bf16 de préférence) : ~2× throughput, mémoire divisée ~2 — le premier réflexe (ch. 2).
  • Batch et accumulation : saturer le GPU (mesurer l'utilisation) ; si la mémoire manque, accumuler des petits batchs ; ajuster les statistiques BatchNorm en conséquence.
  • DataLoader : workers > 0, pin_memory, prefetch — un GPU qui attend les données est un GPU gaspillé (le prétraitement CPU est souvent le goulot réel).
  • torch.compile, noyaux fusionnés (FlashAttention, ch. 6), éviter les synchronisations CPU→GPU dans la boucle (les .item() / prints par pas).

10.4 Reproductibilité

import torch, numpy as np, random

def seed_everything(seed=42):
    random.seed(seed); np.random.seed(seed); torch.manual_seed(seed)
    torch.cuda.manual_seed_all(seed)

seed_everything(42)
torch.backends.cudnn.deterministic = True    # determinisme (cout en vitesse)
torch.backends.cudnn.benchmark = False       # desactive l'autotuning non deterministe

Fixer les graines (python/numpy/torch/cuda), le brassage des données, et noter la version des bibliothèques ; certains noyaux CUDA restent non déterministes par nature (atomics) ; viser la reproductibilité à tolérance près plutôt qu'au bit près, et documenter configurations et graines dans chaque expérience. La reproductibilité est aussi un outil de debug : un bug aléatoire que l'on sait reproduire est à moitié corrigé.
