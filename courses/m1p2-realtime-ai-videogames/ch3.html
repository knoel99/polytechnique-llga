3. Comportements : machines à états, behavior trees, utility

3.1 Machines à états finis (FSM)

Définition 3.1 — FSM Une machine à états finis est un quintuplet \((S, s_0, E, \delta, \lambda)\) : ensemble fini d'états (Patrouille, Poursuite, Attaque, Fuite), état initial \(s_0\), événements/conditions \(E\), fonction de transition \(\delta : S \times E \to S\), et actions \(\lambda(s)\) exécutées dans l'état \(s\) (entrée dans l'état, chaque tick, sortie).

La FSM est le plus vieux et le plus lisible des outils — l'IA d'Pac-Man (1980) est un contre-exemple fameux (les fantômes suivent des règles de ciblage différentes, sans états), tandis que les gardes de la série Metal Gear ou les unités de Warcraft en sont des archétypes. Sa limite est connue : explosion combinatoire des transitions dès qu'on ajoute des états (20 états ⇒ jusqu'à 400 transitions à maintenir), et comportements « à cloison » (un NPC ne peut pas patrouiller et écouter un bruit). 3.2 Behavior trees (BT)

Définition 3.2 — Arbre de comportement Un BT est un arbre dont les feuilles sont des conditions (tester) et des actions (agir : se déplacer, tirer, jouer une animation), et dont les nœuds internes sont des compositeurs :
  • Séquence (≈ ET) : exécute les enfants dans l'ordre ; échoue dès qu'un enfant échoue ; réussit quand tous réussissent ;
  • Sélecteur / fallback (≈ OU) : essaie les enfants dans l'ordre ; réussit dès qu'un enfant réussit ; échoue si tous échouent ;
  • Décorateurs : inverser, répéter, temporiser, verrouiller (« une fois », cooldown), timeout.
Chaque tick, le signal part de la racine et se propage vers le bas ; chaque nœud retourne Réussi, Échoué ou En cours (running) ; les actions longues restent « en cours » sur plusieurs frames. L'ordre des enfants encode la priorité : un sélecteur teste d'abord la survie (fuir si touché), puis le combat, puis la patrouille.
Proposition 3.3 — Les BT « subsomment » les FSM Tout comportement exprimable par une FSM peut l'être par un BT : les états deviennent des branches d'un sélecteur racine, les conditions de transition deviennent les conditions de garde des branches — la transition est remplacée par la ré-évaluation du sélecteur à chaque tick.
(Esquisse constructive.) Pour une FSM d'états \(\{s_1, \dots, s_k\}\) : construire Sélecteur(Séquence(garde_1, action_1), …, Séquence(garde_k, action_k)) où \(\mathrm{garde}_i\) est la conjonction des conditions qui rendent \(s_i\) actif (état courant + événements). À chaque tick, le sélecteur évalue les gardes dans l'ordre et active la première satisfaite — exactement la transition FSM (état courant inclus dans sa propre garde pour la persistance). La réciproque est fausse en pratique : un BT ré-évalue toutes ses gardes chaque tick (interruptible), là où une FSM ne quitte un état que par ses transitions sortantes explicites — les BT sont plus réactifs, au prix du tick. ∎ 
# Behavior tree minimal : compositeurs + actions a la main
class Noeud:
    REUSSI, ECHOU, ENCOURS = "R", "E", "C"
    def tick(self, agent): raise NotImplementedError

class Action(Noeud):
    def __init__(self, nom, fn): self.nom, self.fn = nom, fn
    def tick(self, agent): return self.fn(agent)      # "R"/"E"/"C"

class Sequence(Noeud):                                # ET : premier echec arrete
    def __init__(self, *enfants): self.enfants = enfants
    def tick(self, agent):
        for e in self.enfants:
            r = e.tick(agent)
            if r != Noeud.REUSSI: return r
        return Noeud.REUSSI

class Selecteur(Noeud):                               # OU : premiere reussite gagne
    def __init__(self, *enfants): self.enfants = enfants
    def tick(self, agent):
        for e in self.enfants:
            r = e.tick(agent)
            if r != Noeud.ECHOU: return r
        return Noeud.ECHOU

# --- utilisation : un garde combine ------------------------------------
bt = Selecteur(
    Sequence(Action("blesse?",  lambda a: Noeud.REUSSI if a.hp < 30 else Noeud.ECHOU),
             Action("fuir",     lambda a: a.fuir() or Noeud.REUSSI)),
    Sequence(Action("voit ennemi?", lambda a: Noeud.REUSSI if a.voisin() else Noeud.ECHOU),
             Action("attaquer", lambda a: a.attaquer())),   # renvoie ENCOURS tant que...
    Action("patrouiller", lambda a: a.patrouiller()))
# chaque frame : bt.tick(agent) — la branche "blesse" interrompt "patrouiller".
Note — Pourquoi les studios ont adopté les BT Modularité (réutiliser la branche « se soigner » pour plusieurs types d'agents), outillage graphique, réactivité (interruptibilité), lisibilité des priorités. Les BT sont introduits dans l'industrie par Halo 2 (Isla, GDC 2005) et formalisés académiquement par Colledanchise & Ögren (2018) ; les moteurs les intègrent nativement (Unreal — Behavior Tree ; Unity — packages). GOAP (F.E.A.R., 2006) et STRIPS-style planners occupent une case intermédiaire : l'IA planifie une suite d'actions vers un but par une recherche A* dans l'espace des états du monde — puissant, moins prévisible pour le game design.

3.3 Utility AI : décider par scores continus

Définition 3.4 — Utility system À chaque tick, chaque action candidate \(a\) reçoit un score \(U(a) = f_a(\text{monde}) \in [0, 1]\) obtenu en combinant des courbes de réponse (linéaires, sigmoïdes, seuils doux) appliquées aux variables du monde (santé, distance, faim, menace), puis on choisit l'action de score maximal — ou un tirage pondéré. Deux ingrédients anti-oscillation : l'inertie (bonus au maintien de l'action courante) et l'hystérésis (seuils d'entrée/sortie différents).
Exemple 3.5 — Deux courbes et un compromis \(U_{\mathrm{fuir}} = \mathrm{sigmoide}(30 - \mathrm{hp})\) et \(U_{\mathrm{ramasser}} = \mathrm{sigmoide}(50 - \mathrm{munitions})\) ; avec hp = 45 et munitions = 20 : fuir ≈ sigmoïde(−15) ≈ 0,18, ramasser ≈ sigmoïde(30) ≈ 0,99 → l'agent va chercher des munitions ; à hp = 15 : fuir ≈ sigmoïde(15) ≈ 0,998 l'emporte. L'intérêt : les transitions sont continues et paramétrables par les game designers (déplacer un seuil = éditer une courbe), là où un BT exige une règle explicite. Les Sims en sont l'exposition la plus connue (chaque « besoin » est une courbe) ; la pratique est documentée dans les volumes Game AI Pro (Mark, Graham).
