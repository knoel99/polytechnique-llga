8. Query optimization

SQL is declarative: the execution plan — the order of operations, the join algorithms, the indexes used — is chosen by the optimizer. The principle: rewrite the query as an algebraic tree, generate the equivalent plans via the laws of Proposition 1.4, estimate their cost with a model, keep the cheapest. It is a closed loop between theory (equivalences) and physics (the cost model of ch. 4).

Definition 8.1 — Cost model and selectivity For each table, the catalog stores \(n\) (number of tuples), \(b\) (pages), and for each column \(ND(A)\) (number of distinct values) or even a histogram. The selectivity of a predicate is the expected fraction of rows: \(sel(A = c) \approx 1/ND(A)\), \(sel(A < c)\) via histogram, \(sel(p_1 \wedge p_2) \approx sel(p_1)\cdot sel(p_2)\) (independence — a false but convenient assumption, corrected by modern engines via dynamic sampling). Estimated cardinality of a node = selectivity × cardinality of the child.
Definition 8.2 — Join algorithms Let \(R\) (\(B_R\) pages) and \(S\) (\(B_S\) pages), with a buffer of \(M\) pages:
  • nested loops (NLJ): for each page of \(R\), scan \(S\) — cost \(B_R + B_R\!\cdot\!B_S\); by blocks of \(M-1\) pages: \(B_R + \lceil B_R/(M-1)\rceil \cdot B_S\);
  • sort-merge join: sort \(R\) and \(S\) (Thm 4.3) then merge — cost \(2B_R(1+\lceil\log_{M-1}\lceil B_R/M\rceil\rceil) + 2B_S(\dots) + B_R + B_S\), zero if already sorted (B+ index);
  • hash join: partition both relations on the join key with the same hash (one pass if everything fits in \(M\)), then build a hash table per partition and probe — cost \(\approx 3(B_R+B_S)\), in memory if \(B_R\) or \(B_S\) fits in RAM.
Example 8.3 — Numbers: the winning plan cannot be guessed \(B_R = 1000\) pages, \(B_S = 500\), \(M = 50\). Simple nested loops: \(1000 + 1000\times500 = 501\,000\) pages. By blocks: \(1000 + \lceil 1000/49\rceil \times 500 = 1000 + 21\times500 = 11\,500\). Sort-merge: sorting \(R\) in 2 passes → 4000, sorting \(S\) in 2 passes → 2000, merge 1500: total 7500. Hash: \(3\times(1000+500) = 4500\) — and if \(S\) fits in memory, \(1000 + 500 = 1500\).

The optimizer makes this table for every join and every nesting order: a query with 10 joins admits \(\sim 10!\times 2^{10}\) equivalent trees. System R's dynamic programming (sets of relations, Cartesian joins avoided) makes the exploration polynomial in \(2^n\) tables; the general case is NP-hard, and beyond a dozen tables engines switch to randomized searches.
Proposition 8.4 — Safe heuristic rewrites Before any cost-based search, one applies the "always winning" rewrites: push down selections (Prop. 1.4), push down projections (reduce tuple width), reject Cartesian products outside useful joins, eliminate redundant subqueries, transform IN into semi-joins. Each selection pushed down divides the cardinality of the subtree involved: with \(sel = 1/100\), filtering \(10^6\) rows before rather than after a join gains a factor ~100 on that stream. Engines add costly but profitable rewrites: elimination of unnecessary joins (a join by foreign key without reading the columns of \(S\) and without multiplicity is superfluous), materialized CTEs, plan reuse (plan cache).
Definition 8.5 — Evaluating selection: access paths Even before the joins, each relational operator comes in several implementations that the optimizer compares:
  • selection: sequential scan (\(B_R\) pages, Def. 4.2), or B+ tree descent when an index covers the predicate (\(\lceil \log_F B_R \rceil + 1\) pages), or an index-only scan if the index contains all requested columns (zero table access);
  • projection and aggregation: tuple stream, with sorting or hashing to eliminate duplicates and group (sort-agg vs hash-agg, depending on available memory);
  • union, difference: merge of sorted streams or hash tables, in the same spirit as the joins of Def. 8.2.
The cost of each variant combines the selectivity model (Def. 8.1), the buffer pool (Def. 4.5), and the available indexes (ch. 5): reading an EXPLAIN is seeing this choice materialized node by node.
Note — Reading an EXPLAIN EXPLAIN QUERY PLAN (SQLite) or EXPLAIN (ANALYZE, BUFFERS) (PostgreSQL) shows the chosen tree and the real cardinalities. Typical diagnosis: an estimate off by a factor of 1000 (stale statistics, unmodeled correlation) → nested loops where hashing would be needed. Reflex: compare estimated vs actual rows node by node, and trace back to the first divergence.
