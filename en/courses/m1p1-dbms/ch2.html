2. SQL: queries, aggregates, windowing

SQL is a declarative language: one describes the result, not the algorithm. Its logical semantics is understood in three stages, which one must know in order to predict what a query returns — and which every optimizer rewrites in its own way (ch. 8): FROM produces the Cartesian product/joins, WHERE selects row by row, then GROUP BY + SELECT group, aggregate, and project.

Definition 2.1 — Semantics of the basic block The query SELECT [DISTINCT] L FROM R1, …, Rk WHERE p returns $$\pi_L\big(\sigma_p(R_1 \times \cdots \times R_k)\big)$$ (multiset if DISTINCT is absent, set otherwise). A subquery is a nested query; IN and EXISTS correspond to semi-joins: WHERE EXISTS (SELECT …) tests that the answer is non-empty, which makes it possible in particular to express differences with NOT EXISTS.
Proposition 2.2 — Translating quantifiers "The \(x\) such that \(\forall y \in S,\; \theta(x,y)\)" is translated in SQL by anti-join: … WHERE NOT EXISTS (SELECT 1 FROM S WHERE NOT θ). "There exists" is a simple EXISTS. This double negation is the direct legacy of the fact that SQL has no universal quantifier — and of Proposition 1.7: the division of ch. 1 does not exist as an operator, it is programmed.
Definition 2.3 — Aggregates and the HAVING clause A query with GROUP BY g partitions the selected rows according to the values of \(g\), and each group produces one row: the SELECT may mention only \(g\) and aggregates. The HAVING clause filters the groups (after aggregation), whereas WHERE filters the rows (before): $$\pi_{g,f}\big({}_g\gamma_f( \sigma_p(R))\big) \;=\; \texttt{SELECT g, f(a) … WHERE p GROUP BY g HAVING q(f)}.$$

Windows, standardized in 2003, are today the standard tool for top-\(k\) per group, running totals (running sums via ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW), and cross-period comparisons.
Definition 2.5 — NULL and three-valued logic SQL distinguishes "unknown value" (NULL) from actual values. Any comparison with NULL returns UNKNOWN, and WHERE keeps only the TRUE rows — the UNKNOWN ones are silently eliminated. Truth tables extend naturally:
ANDTUF
TTUF
UUUF
FFFF
Trapping consequence: NOT (a = 1) is not a != 1 if a can be NULL; one needs a IS DISTINCT FROM 1 (SQL:1999) or an explicit OR a IS NULL. Aggregates ignore NULLs (AVG divides by the number of non-NULL values), while COUNT(*) counts them — two COUNTs that differ are the classic symptom of incomplete data.
Definition 2.6 — Recursion: WITH RECURSIVE SQL:1999 filled the gap of Theorem 1.7: a recursive CTE WITH RECURSIVE T AS (base UNION ALL SELECT … FROM T …) computes the least fixed point of the equation: one starts from the base query and iterates the recursive part until no new tuples are produced. This is exactly a transitive closure: DBMSs implement it as a semi-naive data graph (a "delta" rewrite that re-evaluates only the new tuples), and ch. 9 will find this fixed-point semantics again for querying knowledge graphs.
Example 2.7 — Ancestors in a tree in SQLite 
-- directed graph parent(y, x): y is a parent of x
WITH RECURSIVE ancestor(a, d) AS (          -- a ancestor of d
  SELECT parent, child FROM parent
  UNION                                    -- UNION (without ALL) = deduplicated
  SELECT p.parent, a.d
  FROM ancestor a JOIN parent p ON p.child = a.a
)
SELECT d, COUNT(DISTINCT a) AS num_ancestors FROM ancestor GROUP BY d;
-- semantics: fixed point; at each iteration, only the tuples
-- produced at the previous iteration are expanded (semi-naive evaluation).
Example 2.8 — SQLite and SQLAlchemy in Python 
import sqlite3
from sqlalchemy import create_engine, MetaData, Table, Column, Integer, String, ForeignKey, select

# --- 1. SQLite: everything lives in one file, ACID transactions included
con = sqlite3.connect("school.db")
con.execute("PRAGMA foreign_keys = ON")        # optional but recommended
con.executescript("""
CREATE TABLE IF NOT EXISTS student(
  id INTEGER PRIMARY KEY, name TEXT NOT NULL, major TEXT);
CREATE TABLE IF NOT EXISTS course(
  code TEXT PRIMARY KEY, title TEXT, credits INTEGER CHECK (credits > 0));
CREATE TABLE IF NOT EXISTS enrolled(
  id INTEGER REFERENCES student(id),
  code TEXT REFERENCES course(code),
  year INTEGER, PRIMARY KEY (id, code));
""")
con.executemany("INSERT OR IGNORE INTO student VALUES (?,?,?)",
                [(1043, "Anna", "DS"), (1088, "Bruno", "AI"), (2101, "Chloé", "DS")])

# average per student, with a window to rank each one's courses
q = """
SELECT e.name, c.title, i.year,
       RANK() OVER (PARTITION BY e.id ORDER BY i.year) AS year_rank,
       COUNT(*) OVER (PARTITION BY e.id)                AS num_courses
FROM enrolled i
JOIN student e ON e.id = i.id
JOIN course   c ON c.code = i.code
WHERE c.credits >= 3
"""
for row in con.execute(q):
    print(row)

# explicit transaction: all or nothing
try:
    con.execute("BEGIN")
    con.execute("UPDATE student SET major='AI' WHERE id=2101")
    con.execute("INSERT INTO enrolled VALUES (2101, 'DB', 2026)")
    con.commit()
except sqlite3.IntegrityError as err:        # e.g. foreign key violated
    con.rollback()
    print("cancelled:", err)

# execution plan (useful for ch. 8):
for row in con.execute("EXPLAIN QUERY PLAN " + q):
    print(row)

# --- 2. SQLAlchemy Core: composable queries, DBMS-independent
engine = create_engine("sqlite:///school.db", echo=False)
md = MetaData()
student = Table("student", md, Column("id", Integer, primary_key=True),
                 Column("name", String), Column("major", String))
enrolled = Table("enrolled", md, Column("id", Integer, ForeignKey("student.id"),
                 primary_key=True), Column("code", String, primary_key=True),
                 Column("year", Integer))
with engine.connect() as cn:
    stmt = (select(student.c.name, enrolled.c.code)
            .join(enrolled, student.c.id == enrolled.c.id)
            .where(enrolled.c.year == 2025).order_by(student.c.name))
    print(cn.execute(stmt).fetchall())
Note — Views and constraints A view is a named, stored query, reused like a table (re-evaluated or materialized depending on the engine): an abstraction on a par with a function. Constraints (PRIMARY KEY, FOREIGN KEY, CHECK, UNIQUE, NOT NULL) are checked at every write: postponing validation until after loading (the "data lake" approach of ch. 10) shifts the cost, it does not remove it.
