8. Deployment: ONNX, quantization, edge

8.1. The deployment pipeline

From notebook to product, the canonical steps:

  1. export: the trained model (PyTorch) is exported as a frozen graph — ONNX (Open Neural Network Exchange), a common format accepted by most runtimes;
  2. graph optimization: operator fusion (conv + batchnorm → single conv; conv + activation), dead-layer elimination, kernel selection;
  3. targeted compilation: TensorRT (NVIDIA), Core ML (Apple), TF Lite / LiteRT (mobile), OpenVINO (Intel) — these generate hardware-specialized engines;
  4. calibration/quantization: move to INT8 (below);
  5. measurement: P50/P99 latency, throughput, memory, energy — on the target hardware, never on the development workstation alone.
import torch

model = DetectorWrapper()          # PyTorch, eval mode
model.eval()
dummy = torch.randn(1, 3, 640, 640)

torch.onnx.export(
    model, dummy, "detector.onnx",
    input_names=["image"], output_names=["boxes", "scores", "labels"],
    dynamic_axes={"image": {0: "batch"},                # variable batch
                  "boxes": {0: "batch", 1: "num_boxes"}},  # variable N
    opset_version=17)              # recent opset for special ops

# runtime side: onnxruntime (CPU/GPU), TensorRT, Core ML...
import onnxruntime as ort
sess = ort.InferenceSession("detector.onnx", providers=["CPUExecutionProvider"])
boxes, scores, labels = sess.run(None, {"image": dummy.numpy()})

8.2. INT8 quantization

Definition 8.1 — Affine quantization scheme To a floating tensor \(x\) we associate a signed 8-bit integer via $$Q(x) = \mathrm{clip}\!\left(\mathrm{round}\!\left(\frac{x}{s}\right) + z,\; -128,\; 127\right), \qquad x \approx s\,(Q(x) - z),$$ with the scale \(s > 0\) and the zero point \(z\) chosen by calibration (min-max of the activations on a representative sample, or percentile to limit the effect of extreme values). The weights are quantized once and for all; the activations are quantized at runtime.
Note — PTQ vs QAT Post-training quantization (PTQ): fast, no retraining, sufficient for many CNNs; quantization-aware training (QAT, Jacob et al. 2018): during training the quantization is simulated with fake operations (rounding on the forward pass, exact gradients on the backward pass — straight-through estimator), so the model learns to be robust to rounding; this is the solution when PTQ degrades too much (sensitive architectures, small models). Typical benefit: memory ÷4 (FP32→INT8) and throughput ×2–4 on targets with INT8 kernels — at the price of a few tenths of a mAP point to monitor.

8.3. Compressing: pruning and distillation

  • pruning: zero out the lowest-magnitude weights (unstructured pruning — no gain without a sparse library) or whole channels (structured — actually accelerates); follow the accuracy/size curve;
  • knowledge distillation (Hinton et al., 2015): a small student imitates the output distribution of a large teacher — the loss combines the ground truth and the KL divergence with the teacher's logits "softened" by a temperature \(T\): $$\mathcal{L} = \alpha\, \mathrm{CE}(y, z_s) + (1 - \alpha)\, T^2\, \mathrm{KL}\!\big(\mathrm{softmax}(z_t / T)\,\|\,\mathrm{softmax}(z_s / T)\big)$$ (covered in detail in the Advanced Deep Learning module (P2), chapter 6).

8.4. Latency budgets and profiling

Example 8.2 — Budget of a "real-time detection" application 30 fps camera → 33.3 ms per-frame budget. Typical breakdown on an embedded module (Jetson Orin class): acquisition + decoding 3 ms; preprocessing (resizing, normalization, NV12→RGB) 4 ms; INT8 inference 18 ms; post-processing (NMS + rendering) 3 ms; margin 5 ms. Three lessons: (i) pre/post-processing is not negligible — keep it on the GPU (DALI/TensorRT-PLUGIN pipeline) if possible; (ii) target P99 latency (worst frame, with numerous detection batches), not the average; (iii) if the budget bursts, the levers in industrial order: input resolution ↓, smaller model (distillation), INT8, skip-frame + interpolation (detection at 15 Hz, tracking at 30 Hz — chapter 4 exists precisely for that).

8.5. Operations, drift and privacy

  • monitoring: log score distributions, detection rates, "world" alerts (dirty camera, night); detect domain drift and plan retraining (the data loop of chapter 6);
  • privacy: process on-device as much as possible (no image leaves the sensor); if a stream is sent: blurring/anonymization of faces and plates (…detected by… the models of chapter 3!), minimal retention;
  • versioning: model + code + data + thresholds = a reproducible artifact — the methodology of the Advanced Deep Learning module (P2), chapter 8 applies mutatis mutandis.
