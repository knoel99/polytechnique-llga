10. Training in practice

A network that does not learn almost always has a mundane bug. This chapter is the diagnostic protocol we will apply in the labs, in the order in which it must be applied.

10.1. The training recipe, in order

  1. Shape sanity check: one forward pass without errors, the dimensions of every activation verified (rule of ch. 0: gradients have the shape of their variable).
  2. Overfit a single batch: 32 examples, train until the loss is \(\approx 0\). If the model cannot do it, the bug is structural (data, loss, initialization, wild learning rate) — no point training longer. A model unable to memorize 32 examples is broken or too small; this is THE test that avoids weeks of silent error.
  3. LR range test (Smith, 2015): \(\eta\) increasing geometrically from \(10^{-7}\) to \(10^{0}\), plot the loss: plateau → descent → divergence. Take the \(\eta\) at the dip (or slightly before): it sets AdamW/SGD in one epoch.
  4. Small full training run on ~10% of the data, with the train/val curves: check that the dynamics are healthy before scaling up.
  5. Scaling + regularization: larger batch (or gradient accumulation), mixed precision, data augmentation, dropout, weight decay — in that order of payoff (ch. 3).
  6. Checkpointing: save regularly (weights + optimizer state + current step + data generator seed), to resume exactly.

Tools: tensorboard/wandb; systematically log the loss, accuracy, gradient norm, weight norm, the fraction of zero activations (dying ReLU), and the activation histograms of a few layers.

10.3. GPU: the levers that matter

  • Mixed precision (bf16 preferably): ~2× throughput, memory divided by ~2 — the first reflex (ch. 2).
  • Batch and accumulation: saturate the GPU (measure utilization); if memory runs out, accumulate small batches; adjust the BatchNorm statistics accordingly.
  • DataLoader: workers > 0, pin_memory, prefetch — a GPU waiting for data is a wasted GPU (CPU preprocessing is often the real bottleneck).
  • torch.compile, fused kernels (FlashAttention, ch. 6), avoid CPU→GPU synchronizations inside the loop (the .item() / prints at each step).

10.4. Reproducibility

import torch, numpy as np, random

def seed_everything(seed=42):
    random.seed(seed); np.random.seed(seed); torch.manual_seed(seed)
    torch.cuda.manual_seed_all(seed)

seed_everything(42)
torch.backends.cudnn.deterministic = True    # determinism (speed cost)
torch.backends.cudnn.benchmark = False       # disable non-deterministic autotuning

Set the seeds (python/numpy/torch/cuda), the data shuffling, and record the library versions; some CUDA kernels remain non-deterministic by nature (atomics); aim for reproducibility up to a tolerance rather than bit-for-bit, and document configurations and seeds in every experiment. Reproducibility is also a debugging tool: a random bug you know how to reproduce is half fixed.
