1. The game loop and the real-time budget

Definition 1.1 — Game loop, tick, frame budget A real-time game repeats a game loop indefinitely: read the inputs → simulate the world state (logic, physics, AI) → render the frame. A tick is one simulation iteration; at 60 frames/s, the total budget is \(1000/60 \approx 16{,}67\) ms for all tasks combined — graphics included. The AI typically gets only a fraction of it (1–3 ms), shared among all agents: this is the module's primary constraint.
Example 1.2 — Budget arithmetic 100 NPCs, an AI budget of 2 ms per frame at 30 fps (total budget 33 ms): on average 20 microseconds per NPC per tick. No complete pathfinding fits; hence the strategies of chapter 9: staggered updates (10 NPCs "think" per frame), asynchronous paths (the NPC keeps moving straight ahead while waiting), AI levels of detail (far from the player: a trivial state machine).

1.1. Fixed timestep and accumulator

Proposition 1.3 — Fixed-step loop: determinism and stability The "accumulator" loop below slices real time into constant simulation steps \(\Delta t\); two runs with the same inputs produce exactly the same sequence of states (determinism, required for replays and lockstep networking), and the physics remains stable (integration at a constant step).
The elapsed time \(r\) is accumulated: each frame one executes \(k = \lfloor r_{\text{acc}} / \Delta t \rfloor\) complete ticks, subtracting \(k\,\Delta t\). The number of ticks executed at frame \(n\) is \(k_n = \lfloor (R_n - k_{<n}\Delta t)/\Delta t \rfloor\) where \(R_n\) is the cumulative real time: it depends only on the actual frame durations and on \(\Delta t\), never on the order of execution; each tick receives the same \(\Delta t\), so the updates (positions, velocities, decisions) form a deterministic functional sequence of the inputs. With a variable step, on the contrary, \(x \mathrel{+}= v \cdot \delta t\) with a floating-point \(\delta t\) that varies changes the roundings at every run and can diverge for large \(\delta t\) (unstable explicit integration). ∎ 
DT = 1.0 / 30.0            # fixed simulation step (30 Hz)
acc, last = 0.0, now()
while not quit:
    t = now()
    acc += t - last
    last = t
    k = 0
    while acc >= DT and k < 5:      # anti-"spiral of death" bound
        for entity in world: entity.tick(DT)   # AI, physics, etc.
        acc -= DT
        k += 1
    render(alpha=acc / DT)          # visual interpolation between states

1.2. ECS: separating data and processing

Definition 1.4 — Entity Component System (ECS) A simulation architecture where an entity is a mere identifier; components are bags of pure data (Position, Velocity, Health, Target); systems process every frame all the entities carrying a signature of components (e.g. PlacementSystem = entities × (Position, Velocity)). No code lives inside the entities: data (arrays of structures, contiguous in memory) and processing (systems) are orthogonal.

Benefits for real-time AI: the queries "all entities with Position and ActiveAI" become traversals of contiguous arrays (cache-friendly; see data-oriented design); AI systems plug into the loop like ordinary systems, with their own budget; composition replaces inheritance — a "chasing and shooting enemy" = Chasing + Shooting components, reused by other types of agents. The architecture popularized by the Overwatch GDC talk (2017) is now the pattern of modern engines (Unity DOTS, Bevy, EnTT; the concept goes back to the first "component"-based games, around Dungeon Siege, 2002).

Note — AI LOD (level of detail) Rendering adapts mesh refinement to distance; AI does the same: close to the player: full behavior tree, planning, expression animations; medium: simple state machine; far / out of sight: statistical simulation ("the village produces 3 units/min"). The player sees no difference; the budget does. These patterns and those of chapter 9 (staggering, asynchronous) are the heart of the module's engineering.
