3. Behaviors: state machines, behavior trees, utility

3.1. Finite state machines (FSM)

Definition 3.1 — FSM A finite state machine is a quintuple \((S, s_0, E, \delta, \lambda)\): a finite set of states (Patrol, Chase, Attack, Flee), an initial state \(s_0\), events/conditions \(E\), a transition function \(\delta : S \times E \to S\), and actions \(\lambda(s)\) executed in state \(s\) (on entering the state, every tick, on exit).

The FSM is the oldest and most readable of tools — the AI of Pac-Man (1980) is a famous counter-example (the ghosts follow different targeting rules, without states), while the guards of the Metal Gear series or the units of Warcraft are archetypes of it. Its limit is well known: the combinatorial explosion of transitions as soon as states are added (20 states ⇒ up to 400 transitions to maintain), and "siloed" behaviors (an NPC cannot patrol and listen for a noise at the same time). 3.2. Behavior trees (BT)

Definition 3.2 — Behavior tree A BT is a tree whose leaves are conditions (test) and actions (act: move, shoot, play an animation), and whose internal nodes are composites:
  • Sequence (≈ AND): executes the children in order; fails as soon as one child fails; succeeds when all succeed;
  • Selector / fallback (≈ OR): tries the children in order; succeeds as soon as one child succeeds; fails if all fail;
  • Decorators: invert, repeat, time, lock ("once", cooldown), timeout.
Every tick, the signal starts at the root and propagates downward; each node returns Success, Failure or Running; long actions stay "running" over several frames. The order of the children encodes priority: a selector tests survival first (flee if hit), then combat, then patrol.
Proposition 3.3 — BTs "subsume" FSMs Any behavior expressible by an FSM can be expressed by a BT: the states become branches of a root selector, the transition conditions become the guard conditions of the branches — the transition is replaced by the re-evaluation of the selector at every tick.
(Constructive sketch.) For an FSM with states \(\{s_1, \dots, s_k\}\): build Selector(Sequence(guard_1, action_1), …, Sequence(guard_k, action_k)) where \(\mathrm{guard}_i\) is the conjunction of the conditions that make \(s_i\) active (current state + events). At every tick, the selector evaluates the guards in order and activates the first satisfied one — exactly the FSM transition (the current state included in its own guard for persistence). The converse is false in practice: a BT re-evaluates all its guards every tick (interruptible), whereas an FSM leaves a state only through its explicit outgoing transitions — BTs are more reactive, at the price of the tick. ∎ 
# Minimal behavior tree: composites + actions by hand
class Node:
    SUCCESS, FAILURE, RUNNING = "S", "F", "R"
    def tick(self, agent): raise NotImplementedError

class Action(Node):
    def __init__(self, name, fn): self.name, self.fn = name, fn
    def tick(self, agent): return self.fn(agent)      # "S"/"F"/"R"

class Sequence(Node):                                # AND: first failure stops
    def __init__(self, *children): self.children = children
    def tick(self, agent):
        for c in self.children:
            r = c.tick(agent)
            if r != Node.SUCCESS: return r
        return Node.SUCCESS

class Selector(Node):                                # OR: first success wins
    def __init__(self, *children): self.children = children
    def tick(self, agent):
        for c in self.children:
            r = c.tick(agent)
            if r != Node.FAILURE: return r
        return Node.FAILURE

# --- usage: a combined guard ---------------------------------------------
bt = Selector(
    Sequence(Action("hurt?",      lambda a: Node.SUCCESS if a.hp < 30 else Node.FAILURE),
             Action("flee",       lambda a: a.flee() or Node.SUCCESS)),
    Sequence(Action("sees enemy?", lambda a: Node.SUCCESS if a.neighbor() else Node.FAILURE),
             Action("attack",     lambda a: a.attack())),   # returns RUNNING while...
    Action("patrol", lambda a: a.patrol()))
# every frame: bt.tick(agent) — the "hurt" branch interrupts "patrol".
Note — Why studios adopted BTs Modularity (reusing the "self-heal" branch for several types of agents), graphical tooling, reactivity (interruptibility), readability of priorities. BTs were introduced to the industry by Halo 2 (Isla, GDC 2005) and formalized academically by Colledanchise & Ögren (2018); engines integrate them natively (Unreal — Behavior Tree; Unity — packages). GOAP (F.E.A.R., 2006) and STRIPS-style planners occupy an intermediate slot: the AI plans a sequence of actions toward a goal via an A* search in the space of world states — powerful, less predictable for game design.

3.3. Utility AI: deciding with continuous scores

Definition 3.4 — Utility system At every tick, each candidate action \(a\) receives a score \(U(a) = f_a(\text{world}) \in [0, 1]\) obtained by combining response curves (linear, sigmoid, soft thresholds) applied to the world variables (health, distance, hunger, threat), then the maximum-score action is chosen — or a weighted draw. Two anti-oscillation ingredients: inertia (a bonus for keeping the current action) and hysteresis (different entry/exit thresholds).
Example 3.5 — Two curves and a trade-off \(U_{\mathrm{flee}} = \mathrm{sigmoid}(30 - \mathrm{hp})\) and \(U_{\mathrm{pick\,up}} = \mathrm{sigmoid}(50 - \mathrm{ammo})\); with hp = 45 and ammo = 20: flee ≈ sigmoid(−15) ≈ 0.18, pick up ≈ sigmoid(30) ≈ 0.99 → the agent goes for ammunition; at hp = 15: flee ≈ sigmoid(15) ≈ 0.998 wins. The interest: transitions are continuous and tunable by game designers (moving a threshold = editing a curve), whereas a BT requires an explicit rule. The Sims are the best-known showcase (every "need" is a curve); the practice is documented in the Game AI Pro volumes (Mark, Graham).
