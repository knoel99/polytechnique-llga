6. RAG Ops: freshness and continuous evaluation

Reminder — LLMs module ch. 7 (RAG)
Pipeline: chunking → embeddings → vector index → retrieval (hybrid BM25 + dense, cf. NLP ch. 2 and 7) → reranking → conditioned generation. This chapter treats that pipeline as a data system with freshness and evaluation contracts — not as a demo.

6.1. Incremental indexing and freshness

The enterprise corpus moves: Confluence pages edited, contracts signed, FAQs enriched. The index must follow with an explicit freshness SLA ("a published document is queryable within 15 minutes"). The standard pattern: change data capture (webhooks/API of the document repository) → event queue → incremental upsert into the index, key = (source, doc_id, version). Subtleties:

  • Idempotence: replaying the same event twice must create only one batch of vectors; deduplicate by key, mark obsolete chunks (soft delete) so as not to break the evaluation links;
  • Per-document atomicity: the chunks of a document v2 replace those of v1 as a block (otherwise retrieval mixes the versions);
  • Embeddings ↔ index coupling: changing the embedding model requires re-embedding the whole corpus (the spaces are mutually incompatible); dual-boot of the index during the migration, then switchover — the index is a versioned artifact in the sense of ch. 1;
  • Freshness ≠ total reindexing: measure the cost (summary tokens, GPU time) and aim for incremental everywhere possible.

6.2. Evaluating a RAG without humans: RAGAS

Definition 6.1 — RAGAS metrics (Es et al., 2023) Four reference-free metrics, computed by LLM decomposition: faithfulness (is every claim of the answer attested by the context? — anti-hallucination), answer relevancy (does the answer answer the question?), context precision (are the relevant chunks indeed ranked first?) and context recall (are the necessary chunks retrieved? — requires a reference answer). The last two isolate the retrieval, the first two the generation: this is the diagnostic grid missing from a global F1. 
from ragas import evaluate
from ragas.metrics import (faithfulness, answer_relevancy,
                           context_precision, context_recall)
from datasets import Dataset

ds = Dataset.from_dict({
    "question":     q_list,          # golden set (ch. 1: version this set!)
    "answer":       answers,         # outputs of the candidate pipeline
    "contexts":     retrieved_chunks,
    "ground_truth": ref_answers,     # for context_recall
})
report = evaluate(ds, metrics=[faithfulness, answer_relevancy,
                               context_precision, context_recall])
# CI gate: faithfulness >= 0.85; weekly panel: the 4 time series
Reading a RAGAS report like an engineer Low recall, high faithfulness: retrieval is failing — improve chunking, hybrid, reranker. High recall, low faithfulness: the model invents despite the context — prompt, stronger model, forced citation. Low relevancy: off-topic or verbose answer. The trap of reference-free metrics: their judge has the biases of ch. 5 — one calibrates them on a hand-annotated sample before making them CI thresholds.

6.3. The graph to the rescue of RAG

Vector RAG fails on global questions ("what are the recurring themes of the 2025 reports?") that require aggregating the whole corpus; GraphRAG (Edge et al., 2024; cf. Graph ML module ch. 11) builds an entity graph (LLM extraction), partitions it into communities (Leiden) and summarizes each community — the global answer becomes a map-reduce over the summaries. The ops cost: LLM indexing is expensive (every document goes through extraction calls), hence incremental by necessity; communities are recomputed periodically. The arbitration (vector vs graph vs hybrid) belongs in the system's ablation table — and must be re-measured at every model migration (ch. 2).
