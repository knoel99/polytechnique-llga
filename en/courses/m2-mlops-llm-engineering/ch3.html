3. LLM serving: continuous batching, P99 latency

Reminder — LLMs module ch. 6 (inference)
Autoregressive decoding generates one token per forward pass; attention requires retaining the keys/values of all past tokens (KV cache); quantization reduces the weights and the KV; the per-token complexity grows with the context length. This chapter moves from "how it computes" to "how it holds a load".

3.1. Batching: from one request to N

A GPU executes a decoding step in a time nearly independent of the number of sequences present in the batch (as long as memory and bandwidth allow): the operations are parallel and the GPU is memory-bound on the weights. Serving \(B\) sequences simultaneously therefore divides the cost per token by almost \(B\) — this is the economic argument for shared serving. Naive batching (static batching) waits to have \(B\) requests, processes them as a block, and leaves the GPUs idle as soon as a short sequence finishes: yet a 20-token request ends quickly, and the batch becomes sparse.

Definition 3.1 — Continuous batching (Orca, OSDI 2022) Schedule serving at the iteration level rather than the request level: at every decoding step, finished sequences leave the batch and waiting requests enter it. The GPU no longer idles between two requests. Combined with selective batching (batched operations where possible, per-request loops elsewhere), Orca claims up to 36.9× the throughput of prior systems at equal latency. 
# Continuous batching loop (simplified) -- the heart of every modern LLM server
running, queue = [], deque()

def step():
    # 1) decoding: one iteration for ALL active sequences (a single GPU call)
    outputs = model.forward_batch([s.tokens for s in running])
    # 2) remove finished sequences (EOS or max length)
    for s in [s for s in running if s.finished(outputs)]:
        running.remove(s); s.finalize()
    # 3) admit new requests as long as the KV memory allows
    while queue and kv_pool.has_room(queue[0].prompt_len):
        running.append(queue.popleft().prefill())
    # 4) preemptive scheduling: if the KV saturates, evict (recompute/swap)

3.2. Memory: the KV cache and PagedAttention

Proposition 3.2 — KV cache size For a transformer with \(L\) layers, \(h_{\text{kv}}\) key/value heads (GQA) of dimension \(d_h\), in precision \(b\) bytes, the cache of a sequence of \(T\) tokens occupies: $$M_{\text{KV}} \;=\; 2 \cdot L \cdot h_{\text{kv}} \cdot d_h \cdot b \cdot T \;\text{bytes}.$$ Example (Llama-3-8B: \(L=32\), \(h_{\text{kv}}=8\), \(d_h=128\), fp16 \(b=2\)): \(2\times32\times8\times128\times2 = 131,072\) bytes ≈ 128 KiB per token, i.e. 1 GiB for 8,192 tokens — more than some models weigh in significant bits.
Direct counting. Each layer \(l\) stores, for each token \(t\), a key \(k_t^{(l)}\) and a value \(v_t^{(l)}\), each a vector of \(h_{\text{kv}} \cdot d_h\) coefficients (the "query" attention heads may be more numerous — GQA — but only the K/V heads are cached). Each coefficient costs \(b\) bytes: per layer and per token, \(2\,h_{\text{kv}}d_h b\) bytes; multiplying by \(L\) layers and \(T\) tokens gives the formula. ∎

Continuous batching therefore makes memory occupancy oscillate at every iteration (sequences entering/leaving). Allocating the KV as one maximal contiguous block (maximum output length reserved in advance) wastes: vLLM (SOSP 2023) treats the KV cache like the virtual memory of an OS — pages of 16 tokens, allocated on demand, non-contiguous, shareable between sequences derived from the same prefix (system prompt shared by thousands of requests): waste reduced to ~4% versus more than 60% for static allocation, throughput 2-4× prior systems. Ops consequence: the real capacity of a server is measured in "available KV tokens", not in concurrent requests.

3.3. Latency: TTFT, TPOT, P99

Definition 3.3 — LLM serving SLO TTFT (time to first token): request → first token delay — dominated by the prefill (prompt) and the waiting queue. TPOT (time per output token): generation cadence — dominated by decoding and batch contention. P99: 99th percentile of a latency distribution — the relevant contractual commitment; the average masks queues. A typical interactive assistant SLO: TTFT P99 < 1.5 s, TPOT P99 < 80 ms/token.
Theorem 3.4 — Little's law In a stable system in steady state, with \(L\) average clients present, \(\lambda\) clients arriving per second on average and \(W\) mean sojourn time: $$L \;=\; \lambda\, W.$$ Serving corollary: at an imposed generation cadence (\(W\) fixed by the number of tokens and the TPOT), the number of concurrent requests supported is \(L = \lambda W\) — the necessary concurrency grows linearly with the targeted throughput.
Proof by an output argument (direct). Over an interval \([0, t]\), let \(A(t)\) be the number of arrivals and \(D(t)\) the number of departures. The mean number of clients present is written \(L_t = \frac{1}{t}\int_0^t N(u)\,du\), where \(N(u)\) = present at instant \(u\). Each request contributes to this integral exactly its sojourn time: \(\int_0^t N(u)\,du = \sum_{i \,\text{departed by} \leq t} W_i + \) (residuals of requests still present). Dividing by \(t\) and letting \(t\to\infty\) (stability: \(A(t)/t \to \lambda\), bounded residuals become negligible), one obtains \(L = \lambda\, W\) — the argument requires no independence or distribution assumption; it is purely accounting. ∎
Throughput versus latency: the batch trade-off Increasing \(B\) (target batch) improves throughput (amortized cost/token) but lengthens the waiting queue — hence the TTFT P99. Modern servers expose this trade-off: max_num_seqs, token budgets per step, and preemption policies (recompute vs swap). Rule of thumb: size the target batch so that KV occupancy stays below ~90%, and let the autoscaler (ch. 3.4) absorb spikes rather than growing the batch beyond the SLO.

3.4. Autoscaling

The relevant signal for scaling an LLM server is not CPU but: the waiting queue length (requests pending admission), the mean waiting time (TTFT − prefill time) and the KV occupancy rate. Horizontal autoscaling (HPA on a custom Prometheus metric) adds replicas; watch out for warm-up spikes (weight loading: tens of seconds to minutes — pre-pull the images, or pay the P99). For multi-GPU models (tensor parallel; cf. Emerging ML module ch. 2 on distributed computing), each replica is a group of GPUs; scaling changes the granularity of parallelism, not just the number of pods.

# Async benchmark: TTFT / TPOT P50-P99 as a function of concurrency
import asyncio, time, statistics, httpx

async def one(client, prompt, n_out=256):
    t0 = time.perf_counter(); first = None; n = 0
    async with client.stream("POST", "/v1/chat/completions",
            json={"model": "...", "messages": [{"role": "user", "content": prompt}],
                  "max_tokens": n_out, "stream": True}) as r:
        async for chunk in r.aiter_lines():
            if chunk.startswith("data:") and '"content"' in chunk:
                first = first or time.perf_counter() - t0   # TTFT
                n += 1
    return first, (time.perf_counter() - t0 - first) / n    # (TTFT, TPOT)

async def main(conc=64):
    async with httpx.AsyncClient(base_url="http://localhost:8000",
                                 timeout=300) as c:
        res = await asyncio.gather(*[one(c, "Summarize this report in 5 points.")
                                     for _ in range(conc)])
    p = lambda x, q: sorted(x)[int(q * len(x))]
    ttft = [r[0] for r in res]; tpot = [r[1] for r in res]
    print(f"conc={conc}  TTFT p50/p99 = {p(ttft,.5):.2f}/{p(ttft,.99):.2f}s"
          f"  TPOT p99 = {p(tpot,.99)*1e3:.0f}ms")

for conc in (1, 4, 16, 64, 256): asyncio.run(main(conc))
