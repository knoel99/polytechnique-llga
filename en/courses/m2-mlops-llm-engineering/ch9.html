9. Operational security: secrets, sandbox, supply chain

Scope The attacks against the model (jailbreaks, injections, poisoning, extraction) are the subject of the M2 module Explainability, Security, Privacy of LLMs. Here: the security of the system around the model — the ops of an LLM application; the reference checklist of the field is the OWASP Top 10 for LLM Applications.

9.1. Secrets and identities

  • API keys, database passwords, index tokens: never in the code nor the images — a vault (Vault, Secret Manager) injected at startup; periodic rotation; repository scanners in CI (a secret committed = compromised, even "just on a branch");
  • Each service has its identity (service account) and least privilege: the RAG engine does not need write access to the corpus; the agent does not need the credentials of the administrative database;
  • The outputs of the LLM are data, never instructions: a model's response must never be evaluated/executed (eval, shell, SQL) without validation — the flaw class "the model generated the code, we execute it" is a special case of indirect injection (Security module ch. 5).

9.2. Sandbox and isolation

When the agent executes code (notebooks, "calculator" tools, plugins), execution must be confined: an ephemeral container, a temporary file system, outbound network blocked by default, CPU/RAM limits, a hardened runtime (e.g. gVisor/Firecracker for kernel-level isolation), and filtering of exfiltrations — including over slow channels (DNS queries, timing): an agent compromised by injection will try to exfiltrate via the only channel it was left (the tools! the mail! the displayed output?). Hence the duo permissions (ch. 8) + sandbox: the same principle as in system security — compromise is likely, blast radius minimal.

9.3. Supply chain

  • Model weights: downloaded from verified sources, sha256 fingerprint recorded in the registry (ch. 1) — an open-weight model is a dependency like a library, with "logical" CVEs (backdoors; cf. Security module ch. 5) and no automatic scanner;
  • Dependencies: lockfiles, SBOM, classic vulnerability scans in CI (same as any app);
  • Prompts and adapters: mandatory review — a prompt is code in disguise; a LoRA trained on unvalidated data is an opaque dependency;
  • Logs: the traces contain user text (personal data?) — limited retention, anonymization, controlled access; cf. Security module ch. 8-10 and the AI Act (ch. 10).
