8. Agents in production: tracing and guardrails

Reminder — LLMs module ch. 8 (agents)
An agent = an LLM in a loop (observation → reasoning → action via tools), with memory and possibly multi-step planning. This chapter adds no intelligence: it adds observability, the budgets and the permissions without which an agent is undebuggable and dangerous.

8.1. Tracing: the tree of calls

An agent request unfolds in dozens of nested LLM and tool calls. The central datum is the trace: a tree of spans (one span per call: input, output, token cost, latency, model, attempt), OpenTelemetry-compliant — the vendors Langfuse/W&B Weave plug into it. Without a trace: no ability to answer "why did the agent send this email?". With a trace: deterministic replay (by logging the seeds/times), bottleneck analysis (which tool dominates the latency?), per-step costs, and detection of behavioral anomalies (loops: same tool, same arguments, N times).

8.2. Guardrails: in layers, around the loop

LayerMechanismExample
Inputvalidation, injection classifiers, quotablock 500 kB prompts, injection detector (Security module ch. 5-6)
Loopmaximum budgetsmax 15 steps, max 0.10 €/task, global timeout
Actionper-tool permissions, scopingread-only on Confluence; sending e-mails = human confirmation
Outputformat and content validatorsstrict JSON schema; no bank details in the answers
Executionsandbox (ch. 9)code run in an ephemeral container with no outbound network
Observationbehavioral alertsloop rate, success per task, cost drift
Example 8.1 — The budget as the first guardrail A monitoring agent performs on average 6 LLM calls + 3 tool calls per task. A malicious user (or a booby-trapped document — indirect injection, cf. Security module ch. 5) can make it loop: each iteration re-injects a bit of context. Cap per task: steps ≤ 15, tokens ≤ 50 k, cost ≤ 0.10 € — and cut off cleanly (degraded answer: "I could not finish"): the failure becomes a bounded cost instead of a billing incident.
Proposition 8.2 — Per-task success collapses with length If each step succeeds independently with probability \(p\), a task of \(k\) steps succeeds with \(p^k\): \(p = 0.95\) and \(k = 20\) give 36%. Hence: (i) shorten the chains (more reliable tools, shallower plans); (ii) local retries and reflexivity; (iii) evaluate agents per complete task, never per step.

8.3. Evaluating an agent

Agent metrics: success rate per task (on scripted tasks with an initial state and a success criterion — e.g. "the ticket is created with the right fields"), average cost per task (tokens × price + tools), end-to-end P95 latency, human intervention rate. The evaluation environments must be replayable: simulated tools (mock Confluence, mock mail) for CI, a sampled real environment for production — the simulation runs hundreds of tasks for a few cents.
