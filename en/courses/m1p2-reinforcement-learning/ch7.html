7. Autonomous agents in the era of LLMs

Definition 7.1 — POMDP: when the state is not observable A POMDP is a tuple \((\mathcal{S}, \mathcal{A}, \mathcal{O}, P, \Omega, r, \gamma)\): like an MDP, but the agent only observes \(O_t \sim \Omega(\cdot \mid S_{t+1}, A_t)\) — not the latent state. The central object is the belief \(b_t(s) = \mathbb{P}[S_t = s \mid O_1, \dots, O_t, A_1, \dots, A_{t-1}]\), updated by Bayes at each observation. Fundamental result: the POMDP rewrites as an MDP over the (continuous) space of beliefs, with reward \(\bar r(b, a) = \sum_s b(s) r(s, a)\) — optimality preserved, but a continuous state space and a PSPACE-hard problem in general. Every real agent is a POMDP: perception is always partial (noisy sensors, screen, text).
  • Defining an agent: perceive → decide → act → observe, in a loop (the agent = policy \(\pi\) over a POMDP); perception = context (text, memory), action = tool calls, APIs, code. The memory/state estimation of the POMDP materializes as: context window (short-term memory — bounded), vector memories (similarity retrieval = approximate belief estimation), recurrent networks/hidden state (literally a learned filter);
  • LLM + tools: the LLM is the decision engine; the "prompt" = observation; function calling = action space. The ReAct loop (Yao et al., 2023) alternates explicit reasoning and actions:
# ReAct trace (excerpt, translated) -- question: "Did the stock price of X
# go up after supplier Y's latest flagship product?"
Thought: I must identify Y's latest flagship product, then the release
  date, then compare the price of X around that date.
Action: search[Y's recent products]
Observation: Y launched product P on March 14, 2026.
Thought: I now look up the price of X around March 14, 2026.
Action: lookup[stock X price March 2026]
Observation: X traded at 102.4 on March 13; 109.9 on March 15.
Thought: I have both data points, I can conclude (+7.3% in two sessions).
Action: finish[yes, up ~7%]

The function calling / tool use format declares the action space (JSON structuring, validated schemas):

{
  "name": "get_stock_price",
  "description": "Closing price of a stock",
  "parameters": {
    "type": "object",
    "properties": {
      "ticker": {"type": "string"},
      "date":   {"type": "string", "format": "date"}
    },
    "required": ["ticker"]
  }
}
// agent's reply: {"ticker": "X", "date": "2026-03-15"}
// -> the orchestrator executes, reinjects the result as an observation
  • Memory and RAG: the state exceeds the context window ⇒ external memory (vector stores). GraphRAG: index knowledge as a graph (entity-relation) and query by neighborhood/multi-hop — retrieval becomes a query over a knowledge graph; exact intersection of the master's program: NLP × Graph ML × LLM (cf. Graph Machine and Deep Learning for Generative AI module, chapter 8, and the NLP module for retrieval-conditioned generation);
  • Multi-agent: agent systems = graphs — nodes: specialized agents (each with its own context and prompt), edges: information flows, DAG or cyclic topology (orchestrator-workers, debates, verifiers). Self-play (the agent learns against itself — AlphaGo/AlphaZero, Silver et al.) is the training version; LLM agent teams (generator/critic/verifier) are its inference version. Current "deep research" workflows orchestrate >100 agents in parallel phases; this "graph engineering" is one of the career paths of the master's program (cf. LangGraph, AutoGen); orchestration is itself a policy — a meta-level sequential decision (cross-reference chapter 4);
  • Distribution, robustness, confidentiality of multi-agent systems: when workers are distributed (or malicious), aggregating their outputs raises the same questions as aggregating gradients — cf. Emerging Subjects in ML module, chapters 2 (distributed) and 4 (Byzantine);
  • Evaluating agents: environments (tool-use benchmarks), verifiable rewards (test programs, formal constraints — RLVR link, chapter 6), costs (tokens, calls, latency — an agent = an MDP whose every step is costly: optimize the return per token);
  • Safety: per-tool permissions (whitelist of allowed actions = action space restriction), execution sandboxing (code, network), human supervision at critical points (human-in-the-loop = policy with interruption), full trajectory logging for audit.
Guiding lab Code a mini "deep research" agent: an orchestrator (LLM) that decomposes a question into subtasks, workers that search and summarize, a verifier that demands sources, a writer that compiles — the whole represented and executed as a DAG of agents (cf. Refresher CS, topological sort); measure success rate, token cost, depth of the DAG.
